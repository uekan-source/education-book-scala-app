## データはやり直せない

コードは何度でも書き直せます。関数を分割しても、クラス名を変えても、テストが通れば終わりです。間違えても、間違えた事実は残りません。

データは違います。テーブルからカラムを 1 本消すことは、**そこに入っている過去を消すこと** です。そして厄介なのは、消すことより足すことです。

具体例で考えます。注文明細（`OrderItem`）に「注文したときの単価」を持たせるかどうか、という設計判断があるとします。持たせずにリリースしたとしましょう。半年後、こういう問い合わせが来ます。

> 「3 月の注文履歴の金額が、いまの価格で表示されているんですが」

原因は明らかです。注文明細が商品 ID しか持っていないので、金額を出すには商品マスタのいまの価格を見るしかない。4 月に値上げしたので、3 月の注文が値上げ後の金額で表示されている。

ここでカラムを足すこと自体はできます。`ALTER TABLE` を 1 本書けば終わりです。**問題は、足したカラムに入れる値がどこにもないこと** です。3 月時点の価格は、もう誰も知りません。商品マスタの現在値を入れれば、それは嘘の履歴になります。

> **設計の失敗は、時間が経つほど「直せない」ではなく「直しても意味がない」に変わります。**
>
> 直せないだけなら、時間と気合いで押し切れます。意味がない状態は、押し切れません。

## 裏返し — いまなら、いくらでも壊せる

ここまでは制約の話です。しかし大事なのは、その裏返しの方です。

**同じ判断でも、いつ下すかでコストがまったく違います。**

![モデルを作り直す判断のコストが、フェーズによって跳ね上がることを示す棒グラフ。左から順に、フェーズ1「モデル定義中（まだ case class しかない）」はコスト数十分で、やることは「ファイルを書き換える」だけ。ここに「いま、ここ」の印が付いている。フェーズ2「テーブル作成後（DDL・テーブル定義・リポジトリが乗った）」はコスト半日から数日で、モデルの書き換えに加えて DDL の書き直し、テーブル定義の修正、リポジトリの修正、開発 DB の作り直しが必要になる。フェーズ3「本番投入後（本物のデータが 1 行でも入った）」はコスト数週間、ときに不可能で、フェーズ2 の作業すべてに加えて移行スクリプト、移行の検証、ダウンタイム調整、切り戻し手順、旧データの解釈、顧客への説明が必要になり、失われた情報はもう復元できない。判断の内容は 3 つとも同じで、違うのはその時点で何が積み上がっているかだけ。破壊的変更の許可証には有効期限があり、いま引っかかっていることはいま壊すべきで、「あとで直す」と書いたメモはフェーズ2 とフェーズ3 では請求書に変わる](./img/change-cost.svg)

いま我々がいるのは、いちばん左です。**モデルを全部捨てて書き直しても、失うのは数十分** です。`sbt compile` が通るかどうかしか、確かめるものがありません。

そして実際に、**この章では 02 章の成果物が大きく壊れます。**

| | 02 章が出した答え | 03 章で行き着く答え |
|---|---|---|
| コンテキスト | `udb` / `common/menu` / `shop` / `sales` の 4 つ | `common` / `shop` / `customer` の 3 つ |
| 注文の置き場 | `sales`（注文コンテキスト） | `shop`（店舗の所持物） |
| クーポン | **今回はなし**（スコープ外と判断） | `Coupon` / `CouponOffer` / `CustomerCoupon` |
| スタンプカード | **今回はなし**（章末の演習に回した） | `StampCard` / `CustomerStampCard` / `CustomerStampCardItem` |
| モデル数 | 15 前後 | **25** |

なぜこうなったのか。ヒアリングが進んで前提が変わり、想定するサービス規模が見えたからです。その中身は [02_ACTORS.md](./02_ACTORS.md) で扱います。

ここで確認しておきたいのは、次の一点だけです。

> **02 章が間違っていたわけではありません。** あの時点で持っていた情報では、あれが最善の答えでした。情報が増えたら設計が動く——それは事故ではなく、**設計という作業がそもそもそういうもの** です。

## 初期設計に拘ることが、いちばんの失敗

人は自分が書いたものを守りたくなります。とくに一度レビューを通したものは守りたくなります。「前回これで合意したので」と言いたくなる。

しかし、拘ると何が起きるか。**破綻に気づいたまま、直せない場所まで運んでしまいます。** 気づいた時点がフェーズ1 なら数十分だったものを、フェーズ3 まで運んでから直すことになります。

とくに設計を動かす要因として、初心者が見落としがちなものが 1 つあります。**想定するサービス規模** です。

| | 3 店舗の個人経営 | 300 店舗のフランチャイズ |
|---|---|---|
| メニュー構成 | 店ごとに手で組んでよい | 本部がテンプレートを作り、店舗に配る仕組みが要る |
| 価格改定 | 3 回書き換えれば済む | 1 回の操作で全店に反映されないと運用が回らない |
| 店舗独自の商品 | そもそも概念が要らない | 「本部の商品」と「店舗の商品」を型で区別する必要がある |

**要件は同じ「ハンバーガーショップのオンラインサービス」でも、規模が違えば正しいモデルが違います。** そして規模は、要求の文章には書かれていません。聞かないと出てきません。聞くべきは「いま何店舗ですか」ではなく「このサービスは、どこまで大きくなる想定ですか」です。

> 拘ってよいのは **ユビキタス言語（言葉）** だけです。業務の人と合意した言葉は、勝手に変えてはいけません。**モデルの形は、いくらでも変えてよい。**

## テーブルを一緒に書きたくなる

モデルを書いていると、テーブル定義がほぼ機械的に書けることに気づきます。`case class` のフィールドを並べ替えるだけです。だから「ついでに書いた方が速い」と感じます。**この直感は正しく、そして罠です。**

![フェーズを切ることを示した図。左のフェーズ1「モデルを確定する（この章）」には edu/common/model が 7 ファイル、edu/shop/model が 11 ファイル、edu/customer/model が 7 ファイル入っており、レビュー範囲は case class だけで約 1,000 行、やり直しのコストはファイルを書き換えるだけで、何度でも壊してよい。右のフェーズ2「永続化を配線する（04 章）」には flyway マイグレーション（DDL）、SlickTable（テーブル定義）、Repository と DI 登録が入っており、レビュー範囲は 3 か所が一致しているかの確認つきで、やり直しのコストはマイグレーションと DB 再作成となり、壊すのに手続きが要る。2 つのフェーズの間には赤い破線の境界線があり、そこを越えると戻れなくなる。一緒に書かない理由は、レビュアーが 1 度に読む量が 3 倍になって指摘 1 件の修正が 3 か所に波及すること、そして「API が動いた」という事実がモデルが正しいことの証明に見えてしまうこと。動くことと正しいことは別](./img/design-phase-order.svg)

理由は 3 つです。

| 理由 | 何が起きるか |
|---|---|
| **レビュー範囲が 3 倍になる** | 人は 1,000 行なら通しで読みますが、3,000 行になると細部しか見ません。**見落としは、量が増えた瞬間に増えます。** |
| **指摘 1 件が 3 か所に波及する** | フィールドを 1 本足す指摘が、モデル・DDL・テーブル定義の 3 ファイル修正になります。面倒になると「まあいいか」が生まれます。 |
| **「動いた」が「正しい」に見える** | API が 200 を返したことは、**モデルが業務を表しているかどうかとは何の関係もありません。** それなのに、動くと確認した気になります。 |

実際、この章のモデルは確定するまでに **3 回、大きく作り替わっています**。注文明細に単価を持たせ → それが揮発データだと分かって決済側に移し → 割引の参照先を商品から明細行に変えました。3 回ともフェーズ1 の出来事なので、コストはファイルの書き換えだけでした。テーブルを先に作っていたら、3 回ともマイグレーションです。

## 「確定」とは、レビューを通ること

モデルが「固まった」とは、自分が書き終えたことではありません。**他人が通しで読んで、指摘が出尽くしたこと** です。

だから範囲を絞ります。25 ファイル × 約 40 行 ＝ 約 1,000 行。これは 1 回のレビューで通しで読める量です。そして通しで読めると、こういう指摘が出ます。

> 「`PaymentDiscount` は割引の内訳を写して持っているのに、`OrderItem` は商品 ID しか持っていない。**割引の履歴は残るのに、何を売ったかの履歴が残らないのでは？**」

これは **並べて読んだから出た指摘** です。`OrderItem` を単体でレビューしても出てきません。それだけ見れば、何もおかしくないからです。

> **不整合は、ファイルの中ではなくファイルの「間」にあります。** 1 ファイルずつ承認していく進め方だと、絶対に見つかりません。範囲を絞る本当の目的は、**間を読ませること** です。

## この章の進め方

ここまでが「なぜモデルだけなのか」でした。ここからは手順です。02 章と同じく 5 ステップですが、入口と出口が違います。02 章は要求から概念の一覧を作りました。この章は概念の一覧から、確定したモデルを作ります。

![モデル設計の 5 ステップを左から右へ並べた図。①アクター（誰がこのサービスを使うのかを並べる。運営者を忘れない）→②境界を引く（アクターの利用範囲がそのまま境界になる＝コンテキスト）→③所持物を確認（各アクターの所持物が境界に収まっているか。はみ出しを探す）→④流して検証（業務の流れを 4 本、端から端まで通す。穴はここで出る）→⑤確定（case class を書き、レビューを通す。全 25 モデル）。④で穴が出たら②の境界まで戻ってやり直す破線の矢印があり、この段階なら無料と書かれている。この工程の成果物は、アクターの一覧とそれぞれの所持物、コンテキストの一覧（そのままパッケージ名になる）、25 個の EntityModel（case class ／ EntityId ／ EnumStatus ／値オブジェクト）、モデル間の参照（どれがどれを Id で参照するか）。まだやらないことは、テーブル定義・マイグレーション・リポジトリ・DI 登録で、モデルが固まるまで 1 行も書かない](./img/model-design-steps.svg)

読む順序は次のとおりです。

| ステップ | 何をするか | どこで |
|---|---|---|
| ① アクターを洗い出す | このサービスに登場する人を並べる。**運営者を立て忘れると、まったく違うものができます** | [02_ACTORS.md](./02_ACTORS.md) |
| ② 境界を引く | アクターの利用範囲が、そのままコンテキスト境界になる | [02_ACTORS.md](./02_ACTORS.md) |
| ③ 所持物を確認する | 各アクターの所持物が、引いた境界に収まっているか確認する | [02_ACTORS.md](./02_ACTORS.md) |
| ④ ワークフローで検証する | 商品管理・購入・決済・分析の 4 本を端から端まで流し、境界の穴を探す | [03_WORKFLOWS.md](./03_WORKFLOWS.md) |
| ⑤ モデルを確定する | `case class` に落とし、25 モデルを通しでレビューする | 次章 |

④ で穴が見つかったら、② まで戻ります。戻ることは失敗ではありません。むしろ ④ を飛ばして ⑤ に行くと、穴を抱えたままフェーズ2 に進むことになります。

## やりがちな失敗

| 失敗 | なぜダメか | どうする |
|---|---|---|
| **いきなりテーブルを設計する** | 「1 テーブル = 1 概念」に引きずられ、業務ではなく実装の都合でモデルが決まる | モデルが確定するまで DDL を書かない |
| **初期の設計案を守ろうとする** | 破綻に気づいたまま、直せない場所まで運んでしまう | 情報が増えたら設計が動くのは正常。捨てる練習をする |
| **アクターを「画面を使う人」だけで数える** | 運営者は画面を持たないことがある。それでも **所持物は持つ** | 「誰が変更する権限を持つか」で数える |
| **想定規模を聞かない** | 要件が同じでも、規模が違えば正しいモデルが違う | 「どこまで大きくなる想定か」を最初に聞く |
| **モデルを 1 ファイルずつレビューする** | 不整合はファイルの間にある。単体では誰も違和感を持たない | 全モデルを 1 度に、通しでレビューする |
| **「あとで直す」とメモする** | そのメモは、フェーズ2 と フェーズ3 では請求書に変わる | いま引っかかったことは、いま壊す |
| **モデルとテーブルを同時に書く** | レビュー範囲が 3 倍になり、動いたことが正しさに見える | フェーズを切る。この章では model だけ |

## まとめ

- コードは何度でも書き直せるが、データは書き直せない。失敗は時間が経つほど「直せない」から「**直しても意味がない**」に変わる。
- その裏返しとして、モデル定義中のいまは、何を壊しても数十分で済む。壊すなら、いま。
- 02 章の成果物は、この章で大きく壊れる。ヒアリングと想定規模で前提が変わったから。それは 02 章が間違っていたのではなく、設計がそういうものだから。
- **想定するサービス規模がモデルを決める**。3 店舗と 300 店舗では、同じ要件でも正解が違う。
- 拘ってよいのはユビキタス言語（言葉）だけ。モデルの形は、いくらでも変えてよい。
- テーブルを一緒に書かない。レビュー範囲が 3 倍になり、「動いた」が「正しい」に見えてしまう。
- 「確定」とは自分が書き終えることではなく、他人が通しで読んで指摘が出尽くすこと。**不整合はファイルの間にある。**

## 業態のコンテクストを考える

「ハンバーガーショップのオンラインサービス」と聞いて、何を思い浮かべたでしょうか。

- 商店街にある 1 店舗の個人店のアプリか
- チェーン店の公式アプリか

この 2 つは、まったく違うものになります。個人店なら、店主が商品を登録し、店主が注文を受け、それで終わりです。チェーン店なら、**店舗の外側に「メニューを決める人」がいます**。

02 章で受け取った要求文には、こう書かれていました。

> 「店舗は複数あって、店によって売り切れも出る」

**複数店舗があるということは、それを束ねている人がいる** ということです。ここから業態が決まり、業態が決まると登場人物が決まります。

> 要求の文章に「本部」という言葉は 1 度も出てきません。**出てこない登場人物を、要求文から起こすのがこの節の仕事** です。

## ① 登場人物を並べる

業態が決まったので、登場人物を並べます。この題材では 3 人と、外部サービスが 1 つです。

![登場人物（アクター）とその所持物を 3 枚のカードで示した図。左は運営者（本部）で、販売のしかたを設計する人、触るものは本部の管理画面、コンテキストは edu.common、所持物は 7 モデル（商品／販売テンプレート／クーポン／スタンプ台帳）、変わるのは年に数回。中央は店舗（店長・スタッフ）で、日々の販売を運用する人、触るものは店舗のタブレット、コンテキストは edu.shop、所持物は 11 モデル（店舗／独自メニュー／除外／注文／決済）、注文は毎分つくられる。右は顧客（会員）で、注文して受け取る人、触るものはスマホアプリ、コンテキストは edu.customer、所持物は 7 モデル（アカウント／カート／保有クーポン／スタンプカード）、自分の分だけを持つ。下段には決済サービス（外部）があり、アクターではあるが所持物を持たず、こちらのモデルは 1 つも増えない。結果だけを Payment.transactionId と Payment.state に写して受け取る。最下段の注記は、アクターを 1 人立て忘れると、その所持物は「作り忘れる」のではなく存在に気づかない、運営者を立てなければ販売テンプレートもクーポンもスタンプ台帳もそもそも発想されない](./img/actor-map.svg)

| アクター | 何をする人か | 触るもの | 所持物 |
|---|---|---|---|
| **運営者（本部）** | **販売のしかたを設計する** | 本部の管理画面 | 商品 / 販売テンプレート / クーポン / スタンプ台帳 |
| **店舗（店長・スタッフ）** | 日々の販売を運用する | 店舗のタブレット | 店舗 / 独自メニュー / 除外 / 注文 / 決済 |
| **顧客（会員）** | 注文して受け取る | スマホアプリ | アカウント / カート / 保有クーポン / スタンプカード |
| **決済サービス（外部）** | 決済を実行する | — | **なし** |

最後の行が大事です。**アクターだからといって、必ず所持物を持つわけではありません。** 決済サービスは我々のシステムの外にいるので、こちら側のモデルは 1 つも増えません。`Payment.transactionId` と `Payment.state` に結果だけを写して受け取ります。

> アクターを数えるときの問いは「**画面を使うのは誰か**」ではなく「**データを変更する権限を持つのは誰か**」です。運営者は画面を持たないこともあります（CSV 取り込みだけ、ということもある）。それでも所持物は持ちます。

## 運営者を忘れるとどうなるか

思考実験をします。顧客と店舗の 2 人だけでこのサービスを設計したとしましょう。

商品を登録するのは誰か。店舗しかいません。だから商品は店舗の所持物になります。`Shop` の下に商品がぶら下がる形です。一見、動きます。個人店ならこれで正解です。

しかし 300 店舗になると、次のことが起きます。

| 起きること | なぜ |
|---|---|
| **全店一斉の価格改定ができない** | 300 件を個別に更新することになる。途中で失敗した店だけ旧価格のまま残る |
| **同じ商品が 300 レコードに増殖する** | 「てりやきバーガー」「テリヤキバーガー」「てりやきバーガー（新）」と表記がゆれ、集計できなくなる |
| **本部がキャンペーンを打てない** | 「今週は全店でポテト half price」を、システムとして実行する手段がない |
| **そもそも概念が生まれない** | 販売テンプレート・クーポン・スタンプ台帳という **発想自体が出てこない** |

4 つ目が本質です。

> **アクターを 1 人立て忘れると、その所持物は「作り忘れる」のではなく、存在に気づきません。**
>
> 作り忘れなら、レビューで「あれが足りない」と指摘されます。気づかない場合は、**誰も指摘できません。** 全員が同じ前提で見ているからです。

運営者を立てて初めて、「この人は何を持っているべきか」という問いが立ちます。そこから `SalesTemplate`（店舗に配るメニュー構成のひな型）、`Coupon` / `CouponOffer`（割引の定義と配り方）、`StampCard`（スタンプの付与ルール）が出てきます。**02 章の要求文には、どれ 1 つとして書かれていません。**

## ② コンテキスト境界 = アクターの利用範囲

02 章では、コンテキストを分ける基準を 3 つ挙げました。

| 基準 | 問い |
|---|---|
| 変更の理由 | この 2 つは、同じ理由で一緒に変わるか？ |
| ライフサイクル | 作られてから消えるまでの時間軸は同じか？ |
| 担当者 | 誰が管理するデータか？ |

**この 3 つは独立していません。** アクターで切ると、残り 2 つが自動的に揃います。

| アクター | 変更の理由 | ライフサイクル |
|---|---|---|
| 運営者 | 本部の販売方針が変わったとき | **年に数回**。商品は数年生きる |
| 店舗 | 店の都合（品切れ・独自商品・日々の注文） | **注文は毎分**つくられ、数十分で終わる |
| 顧客 | 本人の操作（カート編集・クーポン取得） | カートは数分〜数日。アカウントは年単位 |

運営者が触るものは運営者の都合でしか変わらないので、変更の理由がひとりでに揃います。運営者のマスタは年単位、店舗の注文は分単位なので、ライフサイクルもひとりでに揃います。

> つまり **「担当者」が上位の基準** です。3 つを別々に検討するのではなく、**アクターで切ってから、残り 2 つが揃っているかを確認する**。これがこの章の進め方です。

結果、コンテキストは 3 つになります。

```
edu/common/model/     … 運営者（本部）の所持物
edu/shop/model/       … 店舗の所持物
edu/customer/model/   … 顧客の所持物
```

## ③ 所持物チェック

境界を引いたら、**25 モデルを 3 列に並べて、はみ出しがないか確認します**。

![25 モデルを 3 つのアクター列に並べた所持物マップ。左の運営者（本部・edu.common・7 モデル）には Product、SalesTemplate、SalesTemplateMenu、SalesTemplateMenuItem、Coupon、CouponOffer、StampCard が並び、「販売のしかた」の定義だけで実際に売れた記録は 1 つも持たない。中央の店舗（店長・スタッフ・edu.shop・11 モデル）には Shop、ExcludedMenu、ExcludedProduct、CustomMenu、CustomMenuItem、CustomProduct、Order、OrderItem、Payment、PaymentItem、PaymentDiscount が並び、本部のマスタは書き換えず「除外」と「独自」で差分だけを持つ。右の顧客（会員・edu.customer・7 モデル）には Customer、CustomerPassword、CustomerSession、Cart、CustomerCoupon、CustomerStampCard、CustomerStampCardItem が並び、自分に属するものだけを持ち、確定した注文はもう持っていない。Product、SalesTemplateMenu、SalesTemplateMenuItem、Coupon、StampCard、CustomMenu、CustomMenuItem、CustomProduct、CustomerCoupon、CustomerStampCard には菱形の印が付いており、別のアクター側に対になるモデルがあることを示す。所持物チェックの 2 つの問いは、①このモデルを消したら誰が困るか、②このモデルを変更する権限を持つのは誰か。「作った人」は持ち主ではなく、注文を作るのは顧客だが注文は店舗の所持物になる。2 人のアクターに等しく必要なモデルが出てきたら、それは 1 つではなく 2 つに割れる合図](./img/context-ownership.svg)

判定に使う問いは 2 つだけです。

> **① このモデルを消したら、誰が困るか。**
> **② このモデルを変更する権限を持つのは、誰か。**

そして、いちばん間違えやすいのがこれです。

> **「作った人」は持ち主ではありません。**

注文を作るのは顧客です。しかし注文は店舗の所持物です。理由は次の節で扱います。

はみ出しの見つけ方も 1 つ覚えてください。**2 人のアクターに等しく必要なモデルが出てきたら、それは 1 つではなく 2 つに割れる合図** です（図の ◆ 印の行）。

## 迷ったもの 4 つ

### 商品は誰のものか

**答え：運営者。ただし店舗も商品を持つので、別のモデルにする。**

`Product` は本部が定義し、全店で共通です。しかし「この店だけの限定バーガー」も現実にはあります。ここで **`Product` に `shopId` を足して「店舗のものなら Some」とするのは失敗** です。全店共通のはずのマスタに、店舗固有の行が混ざります。

分けます。`Product`（運営者）と `CustomProduct`（店舗）は、同じ「商品」でも別のモデルです。

### 注文は誰のものか

**答え：店舗。顧客が作るが、顧客の所持物ではない。**

判定の問いに戻ります。注文を消したら、誰が困るか。顧客も困りますが、決定的に困るのは店舗です。売上の記録であり、調理の指示書だからです。

`Order.Status` を見ると、はっきりします。

```scala
case IS_CANCELED extends Status(code = -1) // キャンセル
case IS_ACCEPTED extends Status(code =  1) // 受付
case IS_COOKING  extends Status(code =  2) // 調理中        ← 店舗が動かす
case IS_READY    extends Status(code =  3) // 受取準備完了  ← 店舗が動かす
case IS_HANDED   extends Status(code =  4) // 受渡し完了    ← 店舗が動かす
```

**5 つの状態のうち 3 つは、店舗しか動かせません。** 顧客がするのは「注文を出す」ところまでです。出したあとの注文は、店舗のオペレーションを駆動する道具になります。

顧客側に残るのは `Cart` だけです。カートは確定前のもので、店舗は見る必要すらありません。

### クーポンは誰のものか

**答え：3 人にまたがる。だからモデルも 3 つに分かれる。**

| モデル | 持ち主 | 何を表すか |
|---|---|---|
| `Coupon` | 運営者 | 割引の**内容**（何をいくら引くか） |
| `CouponOffer` | 運営者 | **配り方**（いつ・誰に・何枚まで） |
| `CustomerCoupon` | 顧客 | 顧客が保有している **1 枚**（有効期限・使用日時つき） |
| `PaymentDiscount` | 店舗 | 会計で**実際に引いた記録** |

1 つの「クーポン」という言葉が、4 つのモデルに分かれました。02 章で学んだ「1 つの言葉が 2 つのものを指していたら、モデルが 2 つある合図」の、いちばん極端な例です。

### スタンプカードは誰のものか

**答え：台帳は運営者、カードは顧客。**

`StampCard` は本部が定義する台帳です（「会計 10 回でクーポン 1 枚」というルール）。`CustomerStampCard` は顧客が持つ 1 枚、`CustomerStampCardItem` は押されたスタンプ 1 個です。

そして `CustomerStampCardItem` は `paymentId` を持っています。どの会計で押されたかを記録するためです。顧客の所持物でありながら、店舗の所持物を ID で参照している——コンテキストをまたぐ参照は ID だけという原則が、ここで効いています。

## 同じ名前が 2 つに割れるパターン

◆ を付けた行を並べると、2 つのパターンが見えます。

| 運営者側 | 相手側 | パターン |
|---|---|---|
| `Product` | `CustomProduct`（店舗） | **同じ役割を、別のアクターがそれぞれ持つ** |
| `SalesTemplateMenu` | `CustomMenu`（店舗） | 同上 |
| `SalesTemplateMenuItem` | `CustomMenuItem`（店舗） | 同上 |
| `Coupon` | `CustomerCoupon`（顧客） | **定義と実体** |
| `StampCard` | `CustomerStampCard`（顧客） | 定義と実体 |

### 見分け方

| | 定義と実体 | 同じ役割を別のアクターが持つ |
|---|---|---|
| 関係 | 1 対 多（1 つの定義から何枚も生まれる） | 対応なし（どちらも独立に作られる） |
| 相手側の性質 | **消費される**（`expiredAt` / `usedAt` を持つ） | 相手側も**マスタ**（作られて売られ続ける） |
| 例 | クーポン 1 枚は使えば終わり | 店舗独自商品は、本部商品と同格に売られる |

### まとめてはいけない

どちらのパターンでも、**1 つのモデルにまとめてはいけません**。まとめると、こういう列が必要になります。

```scala
ownerType: Short,        // 1 = 本部, 2 = 店舗
ownerId:   Option[Long], // 本部なら None
```

こうすると **境界がコードから消えます**。型で「これは本部のもの」と言えなくなり、実行時に `ownerType` を見るまで分かりません。`CustomMenuItem` が参照を 2 本持っているのは、この妥協を避けた結果です。

```scala
productId:       Option[Product.Id],       // 本部商品
productCustomId: Option[CustomProduct.Id], // 店舗独自商品
```

> 列が 1 本増えるのと、境界が消えるのと、どちらが高くつくか。**境界の方が高い** というのが、このプロジェクトの判断です。

## 02 章の境界を捨てる

ここまでで引いた境界を、02 章の答えと並べます。

### ヒアリングで前提が変わった

02 章では、要求を受け取ったあと質問リストを作り、スコープを切りました。その回答が、その後のヒアリングでこう変わりました。

| 02 章の質問 | 02 章の回答 | ヒアリング後 |
|---|---|---|
| クーポン・ポイントは | **今回はなし**（ポイントは章末の演習で洗い出す） | **販促の主軸**。クーポンとスタンプカードの両方が必要 |
| 店舗スタッフ用の画面は | **今回はなし**（注文の状態遷移だけ用意しておく） | 調理の状態遷移は**必須**。`IS_COOKING` / `IS_READY` / `IS_HANDED` |
| 会員登録は必要か | 必要。ログインは雛形の `user` を使う | 会員が**販促の対象**になるので、`Customer` として独立させる |

02 章の判断が甘かったわけではありません。**あの時点で聞けた範囲では、あれが正しいスコープでした。** 変わったのは前提の方です。

### 想定規模でモデルが変わる

もう 1 つ、要求文には書かれていなかったものが出てきました。このサービスがどこまで大きくなるかです。

| | 3 店舗の個人経営 | 300 店舗のフランチャイズ |
|---|---|---|
| メニュー構成 | 店ごとに手で組んでよい | **`SalesTemplate`** が要る（本部が組み、店舗に配る） |
| 店舗の事情 | 直接メニューを直せばよい | **`ExcludedMenu` / `ExcludedProduct`** で差分だけ持つ |
| 店舗独自の商品 | 概念が要らない | **`CustomProduct` / `CustomMenu`** で型ごと分ける |

**要件は同じでも、規模が違えば正しいモデルが違います。** 3 店舗なら `SalesTemplate` は過剰設計です。300 店舗なら、無いと運用が破綻します。

### その結果、境界が動いた

02 章のアクター表は、こうでした。

| アクター | 何をする | コンテキスト |
|---|---|---|
| 会員（購入者） | カートに入れる / 注文する / 支払う | `sales` |
| 店舗スタッフ・店長 | 調理を進める / 売り切れにする / 臨時休業にする | `shop` |
| 本部 | 商品を追加する / 価格を改定する | `common/menu` |
| 会員本人 | パスワードを変える | `udb` |

**本部だけ、扱いが違っていました。** 他の 3 行は「その人が何をするか」で書かれているのに、本部だけ「商品を追加する / 価格を改定する」——マスタを管理する人としてしか見ていません。主役として見ると、本部は販売のしかたそのものを設計する人です。そこから所持物が 3 つ増えました。

そして、境界が 2 か所動きました。

| 変化 | 理由 |
|---|---|
| **`sales` が消え、注文が `shop` に入った** | 注文を動かすのは店舗。顧客がするのは「出す」ところまで。顧客側に残るのは `Cart` だけ |
| **`udb` が `customer` に統合された** | 「会員（購入者）」と「会員本人」は **同じ人**。アクターで切れば 1 つ。02 章自身が「分けすぎない」と書いていた基準が、ここで効く |

### 捨てたコストはいくらだったか

**Markdown 数ページです。**

02 章の成果物は、業務フローとユビキタス言語の表とコンテキストの一覧でした。書き直しても、動かなくなるものは何もありません。

もし 02 章の直後にテーブルまで作っていたら、同じ判断のコストはこうなっていました。

- `sales_order` を `shop_order` にリネームするマイグレーション
- `udb_user` を `customer` にリネームするマイグレーション
- `SalesTemplate` / `Coupon` / `StampCard` 系 8 テーブルの追加
- それぞれの `SlickTable` と `Repository`、DI 登録

[01_GUIDE.md](./01_GUIDE.md#裏返し--いまならいくらでも壊せる) の変更コストの図で、フェーズ1 とフェーズ2 の差そのものです。

- 業態を掴む。「複数店舗」と書かれていたら、それを束ねる人がいる。要求文に出てこない登場人物を起こすのが最初の仕事。
- アクターを数える問いは「画面を使うのは誰か」ではなく「データを変更する権限を持つのは誰か」。
- **アクターを立て忘れると、その所持物は「作り忘れる」のではなく存在に気づかない。** 誰も指摘できないので、レビューでも見つからない。

- 02 章の境界は捨ててよかった。捨てたコストは Markdown 数ページ。テーブルを作っていたら、8 テーブルの追加と 2 本のリネームだった。

## なぜ流してみるのか

前章の所持物マップは、静止画です。25 個のモデルが 3 つの箱に収まっていて、どこにも矛盾がないように見えます。

しかし、モデルの不整合は **時間の中にしか現れません**。

- 本部が商品を追加したあと、店舗のメニューはどうなるか
- 顧客がカートを確定した瞬間、カートの中身はどこへ行くか
- 決済が失敗したあと、その記録は残るのか消えるのか
- 半年後、この注文の金額を再現できるか

どれも「いつ・何が・どうなるか」を追わないと答えられません。だから流します。

> 流すときの問いは、いつも同じ 3 つです。
>
> **① 境界をまたぐのはどこか。② そのとき、データはコピーされるのか参照されるのか。③ 片方が消えたら、もう片方は無事か。**

## ① 運営 & 店舗：商品を管理する

商品が顧客の画面に並ぶまでに、運営者と店舗の 2 人が順番に手を入れます。運営者がひな型を作って配り、店舗がそれを受け取って、出せないものを外し、この店だけの品を足す——という流れです。

![運営者と店舗の商品管理フローを 2 段のレーンで示した図。上段は運営者（本部）のレーンで、①Product（全店共通の商品マスタ）→②SalesTemplate（店舗に配るひな型）→③SalesTemplateMenu（注文画面のタブ）→④SalesTemplateMenuItem（タブに商品を並べる）の 4 ステップ。そこから下向きの矢印が伸び、Shop.templateId で 1 つだけ参照する（コピーしない）と注記される。下段は店舗（店長）のレーンで、⑤ひな型を受け取る（Shop.templateId）、⑥外す（ExcludedMenu ／ ExcludedProduct）、⑦足す（CustomMenu ／ CustomProduct）の 3 ステップ。その結果、顧客に見えるメニューはテンプレート引く除外足す独自となり、この計算はアプリ側で毎回おこない結果をどこかに保存したりはしない。最下段の注記は、テンプレートを店舗ごとにコピーして持たせると本部が商品を 1 つ足しても 300 店舗のどこにも届かない、差分だけを持てば本部の更新は何もしなくても流れる](./img/wf-product-management.svg)

### 流れ

| # | 誰が | 何をする | モデル |
|---|---|---|---|
| ① | 運営者 | 商品を登録する | `Product` |
| ② | 運営者 | 店舗に配るひな型を作る | `SalesTemplate` |
| ③ | 運営者 | ひな型にタブを作る | `SalesTemplateMenu` |
| ④ | 運営者 | タブに商品を並べる | `SalesTemplateMenuItem` |
| ⑤ | 店舗 | ひな型を 1 つ選ぶ | `Shop.templateId` |
| ⑥ | 店舗 | 出せないものを外す | `ExcludedMenu` / `ExcludedProduct` |
| ⑦ | 店舗 | この店だけの品を足す | `CustomMenu` / `CustomMenuItem` / `CustomProduct` |

### 検証：店舗は本部のデータを書き換えているか

**していません。** 店舗が書くのは `Excluded*` と `Custom*` だけで、どちらも店舗自身の所持物です。`Product` にも `SalesTemplate*` にも、店舗が触る列は 1 つもありません。

### なぜ「コピー」ではなく「除外」なのか

いちばん素直な設計は、テンプレートを店舗ごとにコピーすることです。店舗が自分のメニューを自由に編集できて、分かりやすい。

**しかしそれをやると、本部が商品を 1 つ足しても、300 店舗のどこにも届きません。** コピーした時点で縁が切れているからです。届けるには 300 件の一括更新が必要で、店舗が編集した箇所とぶつかります。

差分だけを持てば、本部の更新は何もしなくても流れます。

```
顧客に見えるメニュー ＝ テンプレート － 除外 ＋ 独自
```

この計算はアプリ側で毎回おこないます。結果を保存しません。保存した瞬間、それはコピーになり、同じ問題が戻ってきます。

> 02 章では、売り切れを `ShopMenuStock`（店舗 × 商品）に持つ、と決めていました。**差分だけを持つ** という発想は同じです。規模が上がって、対象が「売り切れ」から「メニュー構成そのもの」に広がりました。

## ② カスタマー：商品を購入する

この流れには、境界をまたぐ地点がちょうど 1 つあります。注文確定です。その前後で、同じ内容が別のアクターの所持物に変わります。

![顧客の購入フローを、境界をまたぐ形で示した図。左は Cart（顧客の所持物）で、token で識別し、customerId は Option なのでログイン前でも使える。中には items（Seq[BuyItem]）と coupons（Seq[UseCoupon]）を持ち、state は IS_EDITING。中央には赤い破線の境界があり、注文確定によって所持物が移ることを矢印で示す。右は Order ／ OrderItem（店舗の所持物）で、確定した注文であり金額は持たない。状態は IS_ACCEPTED → IS_COOKING → IS_READY → IS_HANDED と並び、後ろの 3 つは色が付いていて店舗しか動かせない。顧客はもう内容を変えられず、受渡しが終われば役目を終える揮発データである。最下段の注記は、境界を越えるとき中身はコピーされ参照ではないこと、Cart は IS_ORDERED になって役目を終え以後店舗はカートを見ず顧客は注文を書き換えられないこと、「調理開始後はキャンセルできない」という業務ルールがそのまま境界と状態遷移として表れていること](./img/wf-customer-purchase.svg)

### 検証：境界をまたぐ瞬間に、何が起きるか

3 つの問いに答えます。

| 問い | 答え |
|---|---|
| **境界をまたぐのはどこか** | 注文確定の 1 点だけ |
| **コピーか参照か** | **コピー**。`Cart.items` の中身が `OrderItem` の行として作り直される |
| **片方が消えたら** | `Cart` が消えても `Order` は無事。逆も同じ |

**参照にしてはいけません。** `Order` が `Cart.Id` を持って中身を借りていると、顧客がカートを編集した瞬間に確定済みの注文が変わってしまいます。境界をまたぐときにコピーするのは、書き換え権限を渡さないためです。

### ログイン前のカート

```scala
case class Cart(
  token:      Token,               // カート自身の識別子
  customerId: Option[Customer.Id], // ログイン後に紐づく
  ...
```

カートは誰のものかではなく、カート自身の `token` で識別されます。だから会員登録の前から使えて、ログインしたときに `customerId` が後から埋まります。

「カートは顧客の所持物」と言いながら `customerId` が `Option` なのは、矛盾ではありません。まだ持ち主が決まっていない所持物を表しています。

### 業務ルールが、そのまま境界になっている

02 章の業務フローに、こういう 1 行がありました。

> 調理開始後はキャンセルできない

これは `if` 文で守るルールに見えます。しかし実際には、**境界と状態遷移として表れています**。

- 注文は店舗の所持物なので、顧客はそもそも書き換えられない
- `IS_COOKING` 以降に遷移させられるのは店舗だけ

> **業務ルールを `if` で守る前に、そもそも触れない構造になっていないかを見る。** 境界が正しければ、ルールの半分は自動的に守られます。

## ③ 決済

決済には、これまでの 3 本になかった要素があります。**自分たちの外側に、応答を待つ相手がいる** ことです。待つあいだの状態と、返ってきた結果の受け取り方が、この節の中身になります。

![決済のフローと構造を示した図。上段は状態の流れで、IS_DRAFT → IS_PENDING と進み、そこから破線で囲まれた決済サービス（外部・transactionId を返す）へ渡り、結果として IS_COMPLETED か IS_FAILED に分岐する。失敗した行は消さず、再試行は「新しい Payment の行」として IS_DRAFT から作り直す。下段は 3 つのモデルの構造で、Payment（請求の合計）は bill＊（計算した内訳：SubTotal / DiscountTotal / TaxTotal）と pay＊（実際に動いた額：BilledTotal / RefundedTotal）を持つ。PaymentItem（何を、いくらで売ったか）は productName / productUnitPrice / productSubTotal をマスタから写した値として持つ。PaymentDiscount（どの行から、いくら引いたか）は discountItemId / discountUnitValue / discountSubTotal を持ち、商品ではなく明細行を指す。矢印は参照の向きで、Id を持っている側から指されている側へ向かう。この 3 つが揃ってはじめて会計が再現でき、billSubTotal = SUM(productSubTotal)、billDiscountTotal = SUM(discountSubTotal) が成り立つ。合計だけを持っていると、あとから「なぜこの金額になったのか」に答えられない](./img/wf-payment.svg)

### 検証：外部サービスとの境界

決済サービスはアクターですが、所持物を持ちません。こちら側のモデルは 1 つも増えません。受け取るのは結果だけです。

```scala
transactionId: Option[TransactionId],  // 決済サービス側の取引Id
state:         Status,                 // こちら側で解釈した状態
```

`transactionId` が `Option` なのは、**まだサービスを呼んでいない状態（`IS_DRAFT`）が存在するから** です。外部との境界は、こういう「まだ何も起きていない」状態を必ず持ちます。

### なぜ失敗した行を消さないのか

`Payment.Status` のコメントに、こう書かれています。

```scala
case IS_FAILED extends Status(code = -1) // 失敗: 決済サービスが拒否。再試行は新しい行
```

失敗した行を消して作り直せば、テーブルは綺麗になります。**しかし「3 回失敗して 4 回目に成功した」という事実が消えます。** これは問い合わせ対応でも、不正検知でも、決済サービスとの突き合わせでも必要になる情報です。

> **消していいのは、消えても誰も困らないデータだけです。** 迷ったら残す。ディスクは安く、失われた事実は買い戻せません。

### 3 つのモデルが揃って、はじめて会計が再現できる

| モデル | 答えられる問い |
|---|---|
| `Payment` | いくら請求したか |
| `PaymentItem` | **何を、いくらで売ったか** |
| `PaymentDiscount` | **どの行から、いくら引いたか** |

そして次の 2 つが成り立ちます。

```
billSubTotal      = SUM(PaymentItem.productSubTotal)
billDiscountTotal = SUM(PaymentDiscount.discountSubTotal)
```

合計だけを持っていると、あとから「なぜこの金額になったのか」に答えられません。内訳は、計算し直すのではなく、そのとき写して持ちます。

> なお 3 つのモデルはどれも `shopId` を持っています。`paymentId` をたどれば店舗は分かるので、一見すると重複です。なぜ持たせているのかは [APPENDIX_03_SCOPE_KEY.md](./APPENDIX_03_SCOPE_KEY.md) で扱います。

## ④ 分析：揮発データとストックデータ

これまでの 3 本は「誰が何をするか」を追いました。最後の 1 本は人ではなく、時間を追います。半年後に残っているものと、消えているものを分けます。

![揮発データとストックデータを左右に並べた図。左は揮発データ（作業用）で、破線の枠に Cart、Order、OrderItem が入り、受渡しが終われば役目を終える。商品への参照と個数だけを持ち、金額は 1 円も持たない。中央の矢印は「会計の瞬間に写す」。右はストックデータ（履歴）で、実線の緑枠に Payment、PaymentItem、PaymentDiscount が入り、消さず分析はここだけを見る。商品名・単価・割引額を写して持ち、マスタが変わってももう動かない。下段の警告は、なぜ揮発側にスナップショットを置いてはいけないのか、消えるデータに履歴を持たせても消えた時点で履歴も消えるので、「注文明細に単価を持たせる」は一見正しく見えて置き場所を間違えている、写す先は消さないと決めたテーブルだけ。最下段は、同じ判断が別の場所にも出ているとして、CustomerStampCardItem が持つのは orderId ではなく paymentId であり、スタンプの根拠は「注文した」ではなく「会計した」だからと説明する](./img/data-lifecycle.svg)

### データを 2 種類に分ける

| | 揮発データ | ストックデータ |
|---|---|---|
| モデル | `Cart` / `Order` / `OrderItem` | `Payment` / `PaymentItem` / `PaymentDiscount` |
| 役目 | 受渡しまでの **作業用** | 売れた事実の **履歴** |
| 寿命 | 数分〜数十分 | **消さない** |
| 金額 | 持たない | 写して持つ |
| 分析 | 見ない | **ここだけを見る** |

分析が見たいのは「売れた事実」であって、調理中だったか受取準備完了だったかではありません。作業の途中経過は、終わったら要らなくなります。

### スナップショットは、消えない側に置く

ここが、この章でいちばん間違えやすいところです。

「注文したあとに商品の価格が変わっても、注文の金額は変わらない」という業務ルールを満たすには、そのときの単価を写して持つ必要があります（＝スナップショット）。

では、どこに写すか。素直に考えると `OrderItem` です。注文の 1 行なのだから、そこに単価を持たせればいい。

**これは間違いです。** `OrderItem` は揮発データだからです。

> **消えるデータに履歴を持たせても、消えた時点で履歴も消えます。**
>
> 写す先は、**消さないと決めたテーブルだけ** です。

だから `PaymentItem` が `productName` / `productUnitPrice` / `productSubTotal` を持ち、`OrderItem` は商品への参照と個数しか持ちません。

### 同じ判断が、別の場所にも出ている

`CustomerStampCardItem`（押されたスタンプ 1 個）が持っているのは、`orderId` ではなく `paymentId` です。

```scala
paymentId: Payment.Id,  // どの会計で押されたか
```

スタンプの根拠は「注文した」ではなく「**会計した**」だからです。そして会計は消えず、注文は消えます。**消えるものを根拠にすると、根拠ごと消えます。**

## 検証で見つかった穴と、その修正

この 4 本を流した結果、モデルは 3 回作り替わりました。順に見ます。

### 1 回目：割引だけ履歴が残っていた

`PaymentDiscount` は割引の内訳（種別・単価・小計）を写して持っているのに、`OrderItem` は商品 ID と個数しか持っていませんでした。

> **割引の履歴は残るのに、何を売ったかの履歴が残らない。**

これは 25 モデルを並べて読んだから出た指摘です（[01_GUIDE.md](./01_GUIDE.md#確定とはレビューを通ること)）。

### 2 回目：写す先を間違えていた

そこで `OrderItem` に単価を足しました。そして、ワークフロー④ を流して間違いに気づきました。 `OrderItem` は揮発データなので、そこに履歴を置いても消えます。

`PaymentItem` を新しく作り、`OrderItem` は元に戻しました。

### 3 回目：割引が「商品」を指していた

`PaymentDiscount` は「どの商品に効いた割引か」を商品 ID で持っていました。しかし `PaymentItem` ができたことで、**明細行を直接指せる** ようになりました。

```scala
// 変更前：どの商品に効いたか（3 列）
discountProductId:       Option[Product.Id]
discountProductCustomId: Option[CustomProduct.Id]

// 変更後：どの明細行に効いたか（1 列）
discountItemId: PaymentItem.Id
```

3 列が 1 列になり、本部商品か店舗独自商品かの区別は `PaymentItem` 側が持つので、二重管理が消えました。

### この 3 回のコストは、ファイルの書き換えだけだった

| 回 | もしテーブルを作っていたら |
|---|---|
| 1 回目 | `shop_order_item` に 4 カラム追加 |
| 2 回目 | その 4 カラムを削除し、`shop_payment_item` テーブルを新規作成 |
| 3 回目 | `shop_payment_discount` の 3 カラムを 1 カラムに置き換え |

マイグレーション 3 本と、開発 DB の作り直しです。モデルだけで進めていたので、実際にかかったのは `sbt compile` を 3 回通す時間でした。

> **④ を飛ばして ⑤ に行っていたら、この 3 つはフェーズ2 で見つかっていました。** ワークフローを流す工程は、遠回りに見えて、いちばん安く穴を見つける方法です。

## まとめ

- 所持物マップは静止画。不整合は時間の中にしか現れないので、業務の流れを端から端まで流す。
- 流すときの問いは **①境界をまたぐのはどこか ②コピーか参照か ③片方が消えたらもう片方は無事か**。
- **境界をまたぐときはコピーする。** 参照にすると、書き換え権限まで渡ることになる。
- 本部のマスタは店舗に「配る」のであってコピーさせない。店舗は差分（除外と独自）だけを持つ。コピーした瞬間、本部の更新が届かなくなる。
- 業務ルールを `if` で守る前に、触れない構造になっているかを見る。境界が正しければ、ルールの半分は構造が守る。
- 消していいのは、消えても誰も困らないデータだけ。失敗した決済も残す。
- データには **揮発** と **ストック** がある。**スナップショットは、消えない側に置く**。消えるデータに持たせた履歴は、消えたら終わり。
- この検証で、モデルは 3 回作り替わった。フェーズ1 だったので、コストは `sbt compile` 3 回だった。
