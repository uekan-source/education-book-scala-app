## 記入例

> **「店舗ごとに、曜日で営業時間を変えたい。平日は 10 時から 22 時、日曜だけ 21 時まで、という店がある。**
> **年末年始や設備メンテナンスで臨時に休む日がある。休みの日は注文を受け付けたくない。**
> **急に決まることもある。その日の朝に店長が『今日は閉める』と決めることがある。逆に『今日は 19 時で閉める』もある。**
> **会員には、いつ開いているかをアプリで見せたい。」**

| 質問 | 今回の回答（仮） |
|---|---|
| 深夜 2 時まで、のような日をまたぐ営業はあるか | **なし** |
| 昼休みなど、1 日に 2 回開ける店はあるか | **なし**（1 日 1 区間） |
| 祝日はシステムが自動で判定するか | **しない**。休む日は店ごとに手で登録する |
| 臨時休業にした日に、すでに入っている予約注文はどうするか | **今回は自動で何もしない** |
| 営業時間を変えた履歴は残すか | **残さない** |

> 5 問で十分。**答えの出ない質問を 20 個並べるより、「今回はこうする」と決めた 5 行のほうが役に立ちます。**

```
[店長]
 1. 店舗の曜日ごとの営業時間を設定する（月〜日の 7 通り）
 2. 年末年始など、休む日を事前に登録する
 3. 急に休みが決まったら、その日の分を当日登録する
 4. 「今日は 19 時で閉める」のように、その日だけ短くすることもある

[会員]
 5. 店舗を選ぶとき、今日の営業時間と「営業中／本日休業」を見る
 6. 受け取り時間を選ぶとき、営業時間内の時刻しか選べない

[システム]
 7. 注文を確定するとき、受け取り時間が営業時間内か、その日が休みでないかを再チェックする

[例外・ルール]
 - その日だけの設定は、曜日の設定より優先される
 - 休みの日は、受け取り時間を 1 つも選べない
 - 営業時間外の受け取り時間では注文を確定できない
 - 過去の日付の設定は変えない
```

**例外の 1 行目が、このあとの設計をほぼ決めます。**

## 記入例（抜粋）

**動詞の振り分け**

| 種類 | 動詞 | 行き先 |
|---|---|---|
| **状態を変える** | 休みにする / 短くする | 特定日の設定を **登録する** ことで表す（新しい状態遷移は増えない） |
| **値を返す** | その日の営業時間を返す / いま営業中か判定する | モデルのメソッド |

> **「状態を変える動詞が 1 つも `EnumStatus` の遷移にならなかった」** ことに注目。動詞を拾ったら必ず状態遷移になる、わけではありません。

**ふるい分け**

| 名詞 | 仕分け | 理由 |
|---|---|---|
| 店舗 | **既存エンティティ**（`Shop`） | 新しく作らない |
| 曜日ごとの営業時間 | **エンティティ（新規）** | `Shop` とは別の画面・別の頻度で編集する。`1:1`（曜日は**列**で持つ） |
| その日だけの設定 | **エンティティ（新規）** | 特定日ごとに増減する＝ライフサイクルがある。`1:*` |
| 開店時刻 / 閉店時刻 | 属性 | 営業時間の一部 |
| 営業中 / 本日休業 | **対象外（＝計算結果）** | 保存しない |
| 祝日 | **対象外** | 自動判定しない |
| 受け取り時間 | **既存の属性**（`Order`） | 判定に使うだけ |

> ⚠️ **「臨時休業」と「時短営業」を、2 つのエンティティにしませんでした。** どちらも **「その日は、曜日の設定ではなくこの設定に従う」** という同じ事実で、**同じ画面で、同じ人が、同時に編集します**。

> ⚠️ **「対象外」が 1 つも出てこない仕分けは、たいてい仕分けをしていません。**

**名前を並べて確認する**

```
Shop                        ← 既存
ShopBusinessHour            ← 今回追加
ShopBusinessHourOverride    ← 今回追加
ShopMenuStock               ← 既存
```

最初は `ShopBusinessHour` / `ShopBusinessDay` を考えたが失敗。`Hour` と `Day` を並べると **「時間」と「日付」という粒度の対比** に見えるが、本当の対比は **「通常の規則」と「特定日の上書き」**。**名前が示す対比軸と、実際の対比軸がズレていた。**

語幹を `BusinessHour` にそろえ、**差分を `Override` の 1 語だけ** にすると、優先ルールも名前のまま読み上げられる。

**単数形にできるのは `1:1` だから。** もし曜日ごとに 7 行持つなら `Shop.businessHours` と複数で扱うことになり、名前も変わる。**多重度が変われば、名前も変わります。**

## 提出版（04）の実物

### 1. 概要

店舗ごとに、曜日単位で営業時間を設定できるようにする。あわせて、特定の 1 日だけ営業時間を上書きする仕組みを用意し、臨時休業・時短営業・臨時開店をまかなう。既存の `Shop` は変更しない。`shop` コンテキストにエンティティを 2 つ追加する。

### 2. 用語

| 呼称 | 何を指すか | 言い換えない |
|---|---|---|
| 通常営業時間 | 曜日ごとに決めた、その店の平常の営業時間 | 基本営業時間、レギュラー営業 |
| 営業時間の上書き | 特定の 1 日だけ、通常営業時間に代えて使う設定 | 特別営業日、イレギュラー設定 |
| 定休日 | 毎週きまって営業しない曜日 | 休業日 |
| 臨時休業 | その日 1 日だけ、終日営業しないこと | 休業、クローズ |
| 時短営業 | その日 1 日だけ、通常より短い時間で営業すること | 短縮営業 |
| 臨時開店 | 定休日に、その日 1 日だけ営業すること | 特別営業 |

会議で使われる「休み」は 3 つの別物を指す。定休日（毎週）、臨時休業（その日だけ）、長期休業（`Shop.state`）を呼び分ける。

> **「言い換えない」列が、この表の本体。** 何と呼ぶかを決めるだけでは足りない。何と呼ばないかを決めないと、次の会議で言い換えが起きる。

> ⚠️ **呼称の数と、モデル・区分値の数は一致しません。** 「時短営業」と「臨時開店」は業務では別の言葉だが、モデルの上では同じ 1 つの区分値。

> ⚠️ **ユビキタス言語は、サービス全体で 1 つ。個別の仕様書で用語を定義してはいけない。** ここに書くのは「全体の用語集に追加してください」という申請だけ。

### 4. モデル定義

```scala
case class ShopBusinessHour(
  id:        Option[Id],                     // 管理 ID（永続化前は None）
  shopId:    Shop.Id,                        // どの店舗の設定か（1 店舗 1 行）
  openMon:   Option[(LocalTime, Duration)],  // 月曜の開店時刻と営業の長さ。None ＝ 定休日
  openTue:   Option[(LocalTime, Duration)],  // 火曜。以下、日曜まで同じ形
  openWed:   Option[(LocalTime, Duration)],
  openThu:   Option[(LocalTime, Duration)],
  openFri:   Option[(LocalTime, Duration)],
  openSat:   Option[(LocalTime, Duration)],
  openSun:   Option[(LocalTime, Duration)],
  updatedAt: LocalDateTime = Now,
  createdAt: LocalDateTime = Now
) extends EntityModel[Id]

object ShopBusinessHour:
  type   Id = Id.Repr
  object Id extends Entity.Id[Long]
```

```scala
case class ShopBusinessHourOverride(
  id:        Option[Id],
  shopId:    Shop.Id,
  openDate:  LocalDate,                      // 上書きする日（shopId との組で一意）
  openTime:  Option[(LocalTime, Duration)],  // その日の開店時刻と営業の長さ。休業なら None
  openState: Status,                         // その日の扱い
  note:      Option[String] = None,          // 備考。判定には使わない
  updatedAt: LocalDateTime  = Now,
  createdAt: LocalDateTime  = Now
) extends EntityModel[Id]

object ShopBusinessHourOverride:
  type   Id = Id.Repr
  object Id extends Entity.Id[Long]

  /** その日 1 日の扱い */
  enum Status(val code: Short) extends EnumStatus[Short]:
    case IS_CLOSED extends Status(code = 0) // 臨時休業（終日）
    case IS_OPEN   extends Status(code = 1) // 時短営業 / 臨時開店
```

**型では守れない決めごと**

- 営業の長さは 0 より大きく、24 時間以内
- `openState` と `openTime` の組み合わせは 4 通りあるが、有効なのは次の 2 通りのみ。生成時に検証する

  | `openState` | `openTime` | 扱い |
  |---|---|---|
  | `IS_OPEN` | `Some(...)` | 有効。時短営業 / 臨時開店 |
  | `IS_CLOSED` | `None` | 有効。臨時休業（終日） |
  | `IS_OPEN` | `None` | 無効。営業するが開店時刻が不明 |
  | `IS_CLOSED` | `Some(...)` | 無効。休業なのに営業時間がある |

- `(shopId, openDate)` は一意

**保存されるデータの例**

| 店舗 | 月 | 火 | 水 | 木 | 金 | 土 | 日 |
|---|---|---|---|---|---|---|---|
| 渋谷店 | 10:00 ＋ 12h | 10:00 ＋ 12h | None | 10:00 ＋ 12h | 10:00 ＋ 12h | 10:00 ＋ 12h | 10:00 ＋ 11h |

| openDate | openState | openTime | note | 業務での呼び名 |
|---|---|---|---|---|
| 2026-01-01 | `IS_CLOSED` | None | 年末年始 | 臨時休業（終日） |
| 2026-02-10 | `IS_OPEN` | 10:00 ＋ 9h | 設備点検 | 時短営業（通常は 12h） |
| 2026-02-11 | `IS_OPEN` | 11:00 ＋ 9h | 祝日営業 | 臨時開店（水曜は通常 定休日） |

**3 行とも同じモデル・同じ形。** 業務の呼び名が 3 つあっても、モデルは 1 つで足ります。

### 5. その日の営業時間を決める順序

1. その日付の上書きがあるか。`IS_CLOSED` → 営業しない。`IS_OPEN` → `openTime` が営業時間
2. 無ければ、通常営業時間のその曜日。`None` → 定休日。`Some(...)` → それが営業時間

分岐はこの 4 つで全部。業務フローの例外 1 行目が、そのまま 2 段階の判定になっている。

# 付録B：判断の記録（記入例）

## 論点1：曜日ごとの営業時間を、どこに・どう持つか

**判断：`Shop` とは別のモデルにする。曜日は行に割らず、列で持つ（`1:1`）。**

`Shop` は店名・住所といった店舗そのものを表す。ここに 14 列を足すと、店舗一覧を引くだけで営業時間まで読むことになる。触る画面も頻度も違う。**`1:1` でもモデルを分ける理由は「いつも一緒に読むわけではないから」。**

7 行に割らないのは、曜日が 7 種類で固定であること、「月曜の行だけ無い店舗」を DB が防げないこと、店長が月〜日をまとめて 1 回で保存すること。

**代償：** 「昼休みで 1 日 2 区間」が来たら列が 28 本になる。そのときに行へ倒す。**いま来ていない要求のために、先に行へ割らない。**

## 論点2：臨時休業と時短営業を分けるか

**判断：分けない。1 つのモデルで両方を表す。**

分けると、同じ日に両方が登録できてしまい、**テーブルが違えば DB の制約では止められない。** 1 つにまとめれば `UNIQUE(shop_id, target_date)` を張るだけで、矛盾の防止がアプリの仕事から DB の仕事になる。

代案（`openState` を持たず `openTime` の有無だけで表す）は、無効な組み合わせが作れなくなる点では強いが、**業務が「臨時休業」を状態として呼んでいる**ため採らなかった。

> **同じ人が、同じ画面で、同時に編集するものは 1 つにまとめる。** 業務の言葉が 2 つあることは、モデルを 2 つにする理由になりません。逆に **1 つの言葉が 2 つのものを指していたら分ける**（`Cart` と `Order`）。

## 論点3：「営業中 / 本日休業」を保存するか

**判断：保存しない。設定と現在時刻から毎回計算する。**

保存すると日付が変わった瞬間に嘘になる。毎日書き換えるバッチが必要になり、そのバッチが落ちた日は、店が開いているのに「本日休業」と表示される。**保存するのは、そのとき確定した事実で、あとから再計算されては困るものだけ。**

## 論点4：「開店・閉店の 2 時刻」か「開店時刻 ＋ 営業の長さ」か

**判断：開店時刻と長さで持つ。閉店時刻は持たない。**

閉店時刻を持つと「開店 < 閉店」の検査が 8 か所で必要になる。また `02:00` が同じ日か翌日か判別できない。長さで持てば **そもそも無効な組が作れず**、日またぎも一意に定まる。

**持つ値の数は変わらない。同じコストなら、無効な状態を表現できないほうを選ぶ。**

なお開店時刻と長さは 2 つに分けず、1 つの `Option` にまとめる。分けると組み合わせが 4 通りになり、うち 2 通りが無効。**曜日は 7 つあるので、分ければ同じ検証を 7 回書くことになる。**

> **一緒にしか意味を持たない値は、束ねて 1 つの `Option` にする。** 別々に `None` になれるということは、**別々に存在できるという意味**。

## 論点5：新しいコンテキストを作るか

**判断：作らない。既存の `shop` に入れる。**

日常的に書き換えるのは店長で、`ShopMenuStock` と同じ担当者・同じ画面。`common` には条件 3（参照されるだけ）で置けない——`Shop.Id` を参照する側なので依存が逆流する。

# 付録C：1:1 と 1:* をどう決めるか

> **繰り返しの個数が「決まっていて・増えず・いつもまとめて読み書きする」なら `1:1`（列で持つ）。**
> **「決まらず・増減し、1 つずつ生まれて消える」なら `1:*`（行で持つ）。**

覚え方は **「8 曜日目は来るか？」**。

## `1:1`（列）にすると、DB 管理がどう楽になるか

1. **「7 曜日そろっている」を DB が保証してくれる。** 7 行に分けると「月曜の行だけ無い店舗」が作れる。**「7 行そろっていること」を表現できる制約は SQL にない**
2. **「定休日」と「未設定」が区別できる。** 7 行だと「行が無い」の意味が 2 つになり、結局 `is_closed` フラグを足すことになる。**同じ意味を 2 通りに書ける構造は、必ずどちらか片方を書き忘れる**
3. **保存が 1 回の UPDATE で終わる。** 7 行だと途中で落ちれば「月〜水だけ新しい時間」が残る
4. **読み出しが素直になる。** `1:*` は結果をアプリ側で畳む必要がある

## `1:*`（行）にしないと成立しないもの

1. **個数が決まらない。** `override_date_1` … `override_date_50` は作れない
2. **ライフサイクルがある。** 「1 年より古い例外を消す」が `DELETE` 1 文で書ける
3. **一意制約が、矛盾を DB の側で止めてくれる**

## 「曜日を 14 列に並べるのは正規化違反では？」

第1正規形が問題にしているのは **「個数が可変な繰り返し」**。

| 列で持ってはいけない例 | 列で持ってよい例 |
|---|---|
| `tel1, tel2, tel3` | `open_mon_* … open_sun_*` |
| 何本必要かは業務都合で決まらない | 曜日は **閉じた 7 要素** |
| どの列も **同じ意味** | 各列が **別の意味** |
| 「2 番目の番号で検索」に OR が必要 | 曜日を指定して 1 列を見る |

**判断は「8 個目が来る可能性があるか」の 1 問だけ。**

> **どちらに倒しても、後から移し替えられます。** 14 列を 7 行に展開するのも、7 行を 14 列に畳むのも `INSERT ... SELECT` 1 回。**恐れて「将来どちらにも対応できる汎用テーブル」を作るほうが、はるかに高くつきます。**
