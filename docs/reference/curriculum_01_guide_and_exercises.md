# 01_GUIDE — ドメインの洗い出し

「ハンバーガーショップのオンラインサービスを作りたい」——実務で渡される要求は、だいたいこのくらいの粒度です。ここからコードにたどり着くまでの **最初のひと仕事** が、ドメインの洗い出しです。

## なぜコードの前に洗い出すのか

ドメインモデルとは「業務の世界をコードで表したもの」。では **業務の世界そのものは、どこにあるのか**。要求を出す人（発注者・店舗の人）の頭の中にあります。そして彼らは **プログラムの言葉では話しません**。

先にコードを書き始めると、次のことが起きます。

- **足りない概念に、実装の途中で気づく**。「あ、店舗ごとに売り切れが違う」→ すでに書いたテーブルを作り直し。
- **業務にない概念を作ってしまう**。画面の都合で `OrderView` のような、業務の誰も知らない名前が生まれる。
- **同じものに 2 つの名前が付く**。ある画面では「商品」、別の画面では「メニュー」。あとで統合できなくなる。

洗い出しは、**手戻りを前倒しで潰す作業** です。紙とテキストエディタでやれば数時間、コードで気づけば数日かかります。

## 5 つのステップ

① 業務フロー（誰が・いつ・何をするかを時系列で書き出す。日本語の文章でよい）→ ② 名詞と動詞（名詞は概念の候補、動詞は操作・状態変化。ただ拾うだけ）→ ③ ふるいにかける（エンティティ / 値 / ただの属性 / 対象外 の 4 つに仕分け）→ ④ 用語をそろえる（同義語を 1 つに統一し英語名を決める＝ユビキタス言語）→ ⑤ 境界を引く（変わる理由が違うもので分ける＝コンテキスト）。

成果物は、ユビキタス言語の表、コンテキストとエンティティの一覧、エンティティ間の関連、状態の一覧。**この工程ではまだ、テーブル設計・カラムの型・画面レイアウト・API のパスは決めない。**

## ① 業務フローを時系列で書き出す

**登場人物ごとに「いつ・何をするか」を時系列で並べる**。図も UML も要りません。箇条書きの日本語で十分です。

```
[会員]
1. アプリを開き、受け取る店舗を選ぶ
2. メニューを見る（カテゴリごとに商品が並ぶ）
3. 商品を選び、オプション（サイズ・トッピング）を決めてカートに入れる
4. カートの中身と合計金額を確認する
5. 受け取り時間を選び、注文を確定する
6. 支払う
7. 店舗で受付番号を見せて商品を受け取る
```

コツは 3 つ。

- **主語を必ず書く**（会員 / 店舗スタッフ / システム）。誰の行動かで、あとでコンテキストを分ける手がかりになります。
- **例外・分岐も書く**。「売り切れていたら選べない」「調理が始まったらキャンセルできない」。**業務ルールはたいてい例外側に隠れています**。
- **知らないことは質問リストにする**。想像で埋めず、確認すべき項目として残します。

## ② 名詞と動詞を拾う

書き出したフローから、**名詞** と **動詞** を機械的に拾います。この段階では取捨選択しません。

| 拾うもの | 意味 | 例 |
|---|---|---|
| **名詞** | 概念（モデル）の候補 | 店舗、メニュー、商品、オプション、カート、注文、受付番号、会員、支払い |
| **動詞** | 操作 と 状態変化 の候補 | 選ぶ、カートに入れる、確定する、支払う、調理する、受け渡す、キャンセルする |

動詞はあとで 2 種類に分かれます。

- **状態を変えるもの**（確定する・キャンセルする・受け渡す）→ `EnumStatus` の状態遷移になる。
- **値を返すだけのもの**（合計を計算する・受け取れるか判定する）→ モデルのメソッドになる。

## ③ 名詞をふるいにかける

| 仕分け | 判断基準 | 例 |
|---|---|---|
| **エンティティ** | ID で区別する。中身が変わっても「同じもの」であり続ける。ライフサイクルがある | 店舗、商品、注文、カート |
| **値オブジェクト** | 値そのもので区別する。同じ値なら交換可能。変化しない | 金額、数量、営業時間 |
| **ただの属性** | 単独では存在せず、他のものの一部分 | 商品名、住所、電話番号 |
| **対象外** | 業務の外、または今回のスコープ外 | クレジットカード会社、ポイント（今回作らない） |

判断に迷ったら、この問いを使ってください。

> **「中身が全部同じでも、別のものとして区別する必要があるか？」**
>
> - 同じ内容の注文が 2 件あったら → **別の注文として扱う** → **エンティティ**
> - 590 円という金額が 2 つあったら → **区別する意味がない** → **値オブジェクト**

もう 1 つの目安は **「履歴を追う必要があるか」**。追う必要があるならエンティティ。

> ⚠️ **全部エンティティにしない**。初学者がいちばんやる失敗です。エンティティは ID とテーブルとリポジトリを引き連れてくる、重い存在です。

## ④ 用語をそろえる（ユビキタス言語）

| 決めること | 例 |
|---|---|
| 同義語の統一 | 「商品」「メニュー」「品目」→ **商品（MenuItem）** に統一 |
| 曖昧語の分解 | 「注文」が「カートの中身」と「確定した注文」の両方を指している → **カート（Cart）** と **注文（Order）** に分ける |
| 英語名の決定 | 商品 = `MenuItem`、注文 = `Order`、受付番号 = `Order.Code` |

**曖昧語の分解** はとくに重要です。1 つの言葉が 2 つのものを指していたら、それはモデルが 2 つある合図です。

> **英語名は、業務の言葉の直訳でなくてよい**が、**業務の人が聞いて納得する名前**にしてください。`Order` を `Transaction` と名付けると、コードと会話が噛み合わなくなります。

## ⑤ 境界を引く（コンテキスト）

| 基準 | 問い | 例 |
|---|---|---|
| **変更の理由** | この 2 つは、同じ理由で一緒に変わるか？ | メニューの改定と、注文の受付ルールは別々に変わる → 別コンテキスト |
| **ライフサイクル** | 作られてから消えるまでの時間軸は同じか？ | 商品は数年、注文は数十分 → 別コンテキスト |
| **担当者** | 誰が管理するデータか？ | 商品は本部が管理、注文は会員が作る → 別コンテキスト |

```
edu/<記号>/model/...          … パッケージ
<記号>_<テーブル名>            … テーブル名
```

> **コンテキストをまたぐ参照は ID だけ**にします。こうしておくと、片方のコンテキストの変更がもう片方に波及しにくくなります。

## やりがちな失敗

| 失敗 | なぜダメか | どうする |
|---|---|---|
| **いきなりテーブルを設計する** | 「1 テーブル = 1 概念」に引きずられ、値オブジェクトや状態遷移が消える | 概念の一覧が固まるまで DDL を書かない |
| **画面から設計する** | 画面は変わりやすい。画面都合の概念が混ざる | 画面は最後。まず業務フロー |
| **全部エンティティにする** | ID とテーブルが増え、モデルが重くなる | 「区別する必要があるか」で判定する |
| **英語名を後回しにする** | あとから決めると、人によってバラバラの名前が付く | 洗い出しの時点で表に書き込む |
| **例外を後回しにする** | 業務ルールの大半は例外側にある | 「〜できない場合」を必ず書き出す |
| **すべてを 1 コンテキストに入れる** | 変更が全体に波及し、名前も衝突する | 変更理由・ライフサイクル・担当者で切る |

# 03_EXERCISES — 演習

**要件だけを渡します。** クラス名も構成も指定しません。5 ステップを自分で回し、同じ形の成果物を作ってください。

## 提出物の形式

コードはまだ書きません。Markdown で、**問題ごとに 3 ファイル** 書きます。

```
（自分のリポジトリ）/docs/domain/<問題名>/
├── 01_requirements.md    … ① 要件定義（受け取った要求 / 質問リスト / 業務フロー）
├── 02_analysis.md        … ② 思考過程（名詞と動詞 / ふるい分け / 用語 / コンテキスト）
└── 03_design.md          … ③ 詳細要件定義（エンティティ一覧 / やらないこと ＋ 付録：判断の記録）
```

各問について、最低限これを書いてください。

| ファイル | 書くもの |
|---|---|
| **① 要件定義** | 1. **受け取った要求**（要約せず引用）<br>2. **確認したいこと**（質問と、今回の回答（仮））<br>3. **業務フロー**（主語つき・**例外 3 行以上**） |
| **② 思考過程** | 4. **名詞と動詞の一覧**<br>5. **ふるい分けの表**（エンティティ / 値オブジェクト / ただの属性 / 対象外 と、その理由）<br>6. **名前を並べて確認**（既存に混ぜて名前順。**接頭辞をそろえる**） |
| **③ 詳細要件定義** | 7. **ユビキタス言語の表**（日本語 / 英語名 / 意味 / **多重度**）<br>8. **エンティティ一覧**（追加する / 既存で足りる / 既存から動かす）<br>9. **どのコンテキストに置くか**（**「誰が日常的に触るか」で判断し、理由を書く**）<br>10. **今回やらないこと**<br>11.（**付録として末尾に**）**判断の記録**（迷ったところと、その決着） |

> **② は実務では提出しませんが、研修では提出してください。** 結論だけ真似したのか、自分で仕分けたのかは ② に出ます。

> 答えは 1 つではありません。**理由が書けているかどうか** が評価軸です。

> ⚠️ 02_BURGER_DOMAIN でエンティティが 15 個出てきたのは、**何もないところからの初回の洗い出し** だったからです。この演習は **すでにあるモデルへの追加** です。**多くは既存で足ります。**

## 問題1：スタンプカード（ポイント）

> **「注文1回につきスタンプを1個押したい。**
> **10個たまったら、次の注文でハンバーガー1つが無料になる。**
> **スタンプは店舗をまたいで共通。有効期限は最後の注文から1年。**
> **お客さんは、いま何個たまっているかをアプリで見たい。」**

### 考えるべき問い

- **「いま何個たまっているか」を数値として保存するか、押した記録（履歴）から数え上げるか。**
- 「10個たまったら無料」の **無料になった1回** は、何として記録されるか。次に見たとき「使用済みの10個」と「たまり始めた新しい1個」を区別できるか。
- 有効期限「最後の注文から1年」は、どのタイミングで、どう判定するか。**期限切れを表す状態を持つのか、日付から計算するのか。**
- 注文がキャンセルされたら、スタンプはどうなるか（要求に書かれていません。あなたの判断と、その理由を書いてください）。
- **どのコンテキストに置くか。** `common` の 3 条件に照らすとどうですか。

### 受け入れ条件

- 「いつ・どの注文で」スタンプが押されたかを、後から一覧できる。
- 数え上げの結果と画面の表示が食い違わない構造になっている。**二重管理をするなら、どちらが正なのかを明記すること。**
- 「1年で失効」の判定に必要な情報が、モデルに揃っている。

## 問題2：店舗スタッフ向けの調理管理

> **「店舗のタブレットで、入った注文を見られるようにしたい。**
> **『調理中』『できあがり』を押していく。**
> **混んでいるときは、受け取り時間の近いものから作りたい。**
> **急に材料が切れたら、その場で商品を売り切れにしたい。**
> **お客さんが来なかった注文は、閉店時に一括で『未受け取り』として片付けたい。」**

### 考えるべき問い

- ここで出てくる概念のうち、**すでに洗い出し済みのもの** はどれか。
- 注文の状態に、足りないものはないか。既存の 5 つ（受付 / 調理中 / 受取準備完了 / 受渡し完了 / キャンセル）で足りますか。
- 「受け取り時間の近い順」は、モデルに何か持たせる必要があるか。それとも並び替えだけの話か。
- 「その場で売り切れにする」は、どのエンティティのどの状態を変える操作か。
- **店舗スタッフは会員（`User`）と同じものか、別のものか。**
- **どこまでを今回のスコープにするか。**

### 受け入れ条件

- 既存のエンティティで済むものと、新しく必要なものが、**区別して**書かれている。
- 「未受け取り」を追加する場合、既存の状態遷移との関係が書かれている。
- 新しいコンテキストを作る／作らないの判断に、理由が付いている。

## 自己レビュー

- [ ] エンティティにしたものすべてに、「なぜ ID で区別する必要があるか」の答えがあるか
- [ ] 値オブジェクトにしたものすべてに、「なぜ区別しなくてよいか」の答えがあるか
- [ ] 1 つの言葉が 2 つのものを指していないか（指していたら分けたか）
- [ ] 同じものに 2 つの名前が付いていないか
- [ ] **英語名の接頭辞がそろっているか。** 並べ替えたとき、関連するものが隣り合うか
- [ ] **名前を「なんとなく」で決めていないか。** 対になる 2 つを作ったなら、その差が名前から読めるか
- [ ] **テーブル名が単数形でそろっているか**
- [ ] コンテキストの判断に **「誰が日常的に触るか」** が使われているか
- [ ] **コンテキストを増やしすぎていないか。** 既存に入れられないか一度考えたか
- [ ] コンテキストをまたぐ参照が、ID だけになっているか。向きは一方向か
- [ ] 「今回やらないこと」が明記されているか
- [ ] **「既存で足りるもの」を書いたか。** 何も足さなくてよいと確認した事実も、成果物です
- [ ] テーブル名・カラム型・画面の話が混ざっていないか

**新しいエンティティが 5 個を超えていたら、まとめられないか一度疑ってみること。**

## 分量の目安（記入例より）

| | 記入例 | 演習での目安 |
|---|---|---|
| **新しいエンティティ** | 2 個 | **0〜3 個** |
| **新しいコンテキスト** | 0 個 | **原則 0** |
| **判断の記録** | 5 件 | **3〜5 件**（1 件 ＝ 判断 1 行 ＋ 理由 3〜6 行） |
| **業務フローの例外** | 4 行 | **3 行以上** |

全体では **3 ファイル合わせて A4 で 2〜3 ページ**。

書き忘れやすいのは 3 つ。**「対象外」にした名詞**（0 件なら仕分けをしていない）、**「既存で足りるもの」**、**「今回やらないこと」**。

## いくつ作るかで迷ったときの問い

| 迷い | 問い | いいえ なら |
|---|---|---|
| **エンティティにするか、属性にするか** | これは、他のものと **別々に作られ、別々に更新され、別々に消える** か？ | 属性にする |
| **1 つにするか、2 つに分けるか** | **同じ人が、同じ画面で、同時に編集する** か？ | 分ける（**はい なら 1 つにまとめる**） |
| **`1:1` にするか `1:*` にするか** | 繰り返しの **8 個目が来る可能性がある** か？ | `1:1`（列で持つ） |
| **新しいコンテキストを作るか** | **日常的に書き換える人** が、既存のどれとも違うか？ | 既存に入れる |

> **足りないより、増やしすぎのほうが直しにくい。迷ったら、少ないほうに倒してください。**

## AI で資料を作るときの進め方

**1 回のお願いで清書までやらせない。** 段階ごとに頭の使い方が違うので、混ぜると必ず崩れます。

| 段階 | 頭の使い方 | やること |
|---|---|---|
| **① 調査中** | **散らかしてよい** | 分かったことを、どんどん走り書きする |
| **② 渡す前** | **読者の目で組み直す** | 構成・用語・粒度をそろえる |
| **③ 最後** | **ノイズを消す** | AI っぽさ・過剰な装飾・未確定情報を削る |

> **AI に「きれいにして」と一言で頼まないでください。** ①②③ のどれをやってほしいのかを指定します。指定しないと、たいてい **③（見た目の整形）だけが返ってきて、②（構成と粒度）が手付かずのまま残ります。**

## 名前で迷ったら

| | いくつ作るか | **何と名付けるか** |
|---|---|---|
| 後から直せるか | **直せる** | **極めて高くつく。** モデル・DDL・テーブル・リポジトリ・API・画面・すでに入ったデータの全部に波及する |
| 間違いに気づけるか | 見れば分かる | **指摘されるまで誰も気づかない** |
| いつ決まるか | 仕分けの途中で決まる | **後回しにされがち** |

> **名前は、好みで決めない。評価で決める。**
