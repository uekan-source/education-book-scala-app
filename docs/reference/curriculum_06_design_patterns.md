## なぜチェックリストなのか

普通のレビューは、**書かれたものを見て指摘する** 作業です。おかしなモデルがあれば気づけます。

しかしアクターの見落としは、**書かれていないもの** です。

> 運営者を立て忘れた設計をレビューしても、誰も「本部がいませんね」とは言いません。**全員が同じ前提で見ているから** です。書かれていないものは、レビューの視界に入りません。

だから、**思い出す** のではなく **数え上げ** ます。以下の問いに順番に答えてください。考える必要はありません。答えられなければ「いない」と書けば済みます。

## ステップ1：候補を機械的に出す

| # | 問い | 出てくるもの |
|---|---|---|
| 1 | このデータを **最初に作る** のは誰か | 登録者・入稿者 |
| 2 | **日常的に変更する** のは誰か | 運用担当・現場 |
| 3 | **止める・承認する** 権限を持つのは誰か | 管理者・承認者 |
| 4 | **お金を受け取る／払う** のは誰か | 事業者・顧客・決済代行 |
| 5 | **集計を見る** のは誰か | 経営・分析・本部 |
| 6 | **問い合わせを受ける** のは誰か | CS・サポート |
| 7 | **人ではないが動く** ものは何か | バッチ・外部 API・Webhook |

ハンバーガーショップで、この 7 問に答えるとこうなります。

| # | 答え |
|---|---|
| 1 | 商品を最初に作るのは **本部**（← ここで運営者が出る） |
| 2 | 売り切れ・独自商品を変更するのは **店長** |
| 3 | メニューの公開を止めるのは **本部** |
| 4 | 払うのは **顧客**、受け取るのは **店舗**、実行するのは **決済サービス** |
| 5 | 売上を見るのは **本部** |
| 6 | 今回は **なし**（スコープ外と明記する） |
| 7 | **決済サービス**（外部） |

**問い 1 だけで運営者が出てきます。** 「誰が最初に作るか」は、それだけ強い問いです。

## 見落としやすいアクター 6 類型

7 問に答えてもなお漏れるものがあります。**この 6 つは、毎回わざわざ確認してください。**

### ① 運営者・本部

| | |
|---|---|
| **見落とすとどうなるか** | マスタが現場の所持物になり、全体を一括で変えられなくなる |
| **兆候** | 「店舗ごとに商品を登録する」という仕様が自然に見えている |
| **典型的な所持物** | マスタ、テンプレート、ルール定義、キャンペーン |

**今回の題材で見落としていたのが、これです。** 複数拠点・複数店舗・複数テナントが出てきたら、必ず「それを束ねる人」がいます。

### ② 承認者・監査

| | |
|---|---|
| **見落とすとどうなるか** | 「誰がいつ承認したか」が残らず、あとから証明できない |
| **兆候** | 状態が `下書き → 公開` の 2 つしかない |
| **典型的な所持物** | 承認履歴、申請、監査ログ |

### ③ CS・サポート

| | |
|---|---|
| **見落とすとどうなるか** | 問い合わせ対応のために、本番 DB を直接見る運用になる |
| **兆候** | 「返金」「取り消し」の操作を、誰がするか決まっていない |
| **典型的な所持物** | 対応履歴、メモ、代理操作の記録 |

### ④ 経営・分析

| | |
|---|---|
| **見落とすとどうなるか** | 揮発データを消せなくなる（消すと集計が壊れるから） |
| **兆候** | 「あとで集計したいので、とりあえず全部残す」 |
| **典型的な所持物** | **なし**（読むだけ）。ただし **何を消してよいかを決める** |

**所持物を持たなくても、立てる価値のあるアクターです。** 分析が何を見るかが決まると、[03_WORKFLOWS.md](./03_WORKFLOWS.md#-分析揮発データとストックデータ) の揮発／ストックの線が引けます。

### ⑤ システム自身（バッチ・スケジューラ）

| | |
|---|---|
| **見落とすとどうなるか** | 「誰も操作していないのに状態が変わる」経路が設計に出てこない |
| **兆候** | 有効期限切れ・自動キャンセルを、状態として持っていない |
| **典型的な所持物** | 実行履歴。多くは既存モデルの状態を動かすだけ |

### ⑥ 外部サービス

| | |
|---|---|
| **見落とすとどうなるか** | 外部の応答待ち・失敗・再試行という状態が抜ける |
| **兆候** | 状態に「処理中」がない。失敗を削除で表している |
| **典型的な所持物** | **なし**。ただし **相手側 ID と結果を写す列** が要る |

## ステップ2：所持物を書き出す

アクターが出たら、1 人ずつ「持っているもの」を書きます。**この時点でモデル名は英語にしなくてかまいません。**

| アクター | 触るもの | 所持物（概念） | 変更の頻度 |
|---|---|---|---|
| 運営者 | 本部の管理画面 | 商品 / 販売テンプレート / クーポン / スタンプ台帳 | 年に数回 |
| 店舗 | 店舗のタブレット | 店舗 / 独自メニュー / 除外 / 注文 / 決済 | 毎日〜毎分 |
| 顧客 | スマホアプリ | アカウント / カート / 保有クーポン / スタンプカード | 本人の操作ごと |
| 決済サービス | — | **なし** | — |

判定に使う問いは 2 つだけです。

> **① このデータを消したら、誰が困るか。**
> **② このデータを変更する権限を持つのは、誰か。**

**「作った人」は持ち主ではありません。** 注文を作るのは顧客ですが、注文は店舗の所持物です。

## ステップ3：はみ出しをチェックする

| チェック | 見つかったら |
|---|---|
| **2 人のアクターが、同じものを対等に変更する** | **2 つに割れる合図**。`Product` と `CustomProduct` のように分ける |
| **1 つのアクターの所持物が、他より極端に多い** | そのアクターが 2 人に分かれていないか疑う |
| **所持物が 0 のアクターがいる** | 正常。外部サービスと分析は 0 でよい |
| **「どちらの所持物か」で 5 分以上迷った** | 概念が 2 つ混ざっている。分けると迷わなくなる |

最後の行は、経験則として強く効きます。**迷うのは、あなたの判断力の問題ではなく、モデルが 2 つ入っているからです。**

## 逆引きテスト：アクターは足りているか

モデルの一覧が先にできている場合は、こちらから確認できます。

| テスト | 不合格なら |
|---|---|
| すべてのモデルについて「**これを最初に作るのは誰か**」に答えられるか | 答えられないモデルがある＝**アクターが足りない** |
| すべてのモデルについて「**消えたら誰が困るか**」に答えられるか | 答えられない＝そのモデルが要らないか、アクターが足りない |
| ある画面が **すべてのコンテキストを書き換える** ことになっていないか | なっている＝境界が業務と合っていない |
| 状態の遷移を **すべてどれかのアクターが起こす** と言えるか | 言えない＝バッチ／外部サービスを立て忘れている |

1 行目がいちばん効きます。02 章の一覧に対してこれをやると、**販売テンプレートに相当する概念がそもそも無い** ことに気づけます。

## AI に手伝わせる

アクター洗い出しは、AI に **candidate を出させる** のに向いています。判断は自分でしますが、**数え上げは任せられます。**

```
あなたは業務システムの設計レビュアーです。
以下の要求からアクター（登場人物）を洗い出してください。

# 要求
（ここに要求文をそのまま貼る）

# 出力形式
| アクター | 何をする人か | 触る画面 | 所持物になりそうな概念 |

# 制約
- 要求文に明示されていないアクターも、業態から推測して挙げてください
- とくに次の 6 つが存在しないか、1 つずつ検討してください
  運営者・本部 / 承認者・監査 / CS・サポート / 経営・分析 /
  バッチ・スケジューラ / 外部サービス
- 「いない」と判断したものは、いないと明記し、その理由を書いてください
- 所持物が 0 のアクターも挙げてください
```

**「いないと明記させる」のが要点です。** 出力に現れなかったものは、検討したのか漏れたのか分かりません。

### 任せてはいけないところ

| 任せてよい | 自分でやる |
|---|---|
| 候補を数え上げる | **採否を決める** |
| 一般論としての類型を挙げる | **この案件の規模で必要かを判断する** |
| 所持物の候補を出す | **どちらのアクターのものかを決める** |

規模の判断は、AI には出せません。要求文に書かれていないからです（[01_GUIDE.md](./01_GUIDE.md#初期設計に拘ることがいちばんの失敗)）。**「どこまで大きくなる想定か」は、人に聞くしかありません。**

## なぜ写すのか

マスタと履歴は、違う時制を表しています。

| | 表しているもの | 例 |
|---|---|---|
| **マスタ** | **いま** どうなっているか | `Product.price` は、いまの価格 |
| **履歴** | **あのとき** どうだったか | この注文は、あのときいくらだったか |

ID で参照するだけの履歴は、マスタの「いま」を読みに行きます。だから半年前の注文を開くと、半年前の商品名と、いまの価格が並んで表示されます。

> **参照は「いま」を返します。履歴が知りたいのは「あのとき」です。** この 2 つは、ID では絶対につながりません。

## 3 つの問い

スナップショットの設計は、この 3 問だけです。

> **① いつ写すか　② 何を写すか　③ どこに置くか**

3 番目がいちばん間違えやすく、間違えたときのダメージも大きいところです。

## いつ写すか

**値が確定した瞬間** に写します。「確定した」とは、**あとから変わっては困る、と業務が言っている瞬間** のことです。

| 業務の瞬間 | 何が確定するか | この教材での例 |
|---|---|---|
| 会計した | 売った商品・単価・割引額 | `PaymentItem` / `PaymentDiscount` |
| 請求した | 消費税率 | `Payment.billTaxRate` |
| クーポンを取得した | 有効期限 | `CustomerCoupon.expiredAt` |

注意すべきは、**「注文した」と「会計した」は違う瞬間** だということです。この教材では会計の瞬間を採りました。注文は取り消せますが、会計は取り消せません（返金という別の記録になります）。

> 迷ったら、**取り消せなくなる瞬間** を探してください。そこが確定点です。

### ルールではなく、結果を写す

`CustomerCoupon.expiredAt` は、いい例です。

```scala
// マスタ側（運営者）: ルールを持つ
validDays: Short,           // Coupon: 取得後の有効日数

// 実体側（顧客）: 結果を持つ
expiredAt: LocalDateTime,   // CustomerCoupon: 有効期限。取得時に確定
```

`validDays` を参照して毎回計算すると、本部が有効日数を 30 日から 14 日に変えた瞬間、**すでに配ったクーポンの期限まで縮みます**。取得時に計算して `expiredAt` として持てば、配ったあとのクーポンは動きません。

写すのは値だけではありません。計算の結果も写します。

## 何を写すか

| 写す | 理由 |
|---|---|
| **表示に使う値** | 名前・カテゴリ。マスタが変わっても、あのときの表示を再現できる |
| **金額計算に使う値** | 単価・小計・税率・割引額 |
| **計算の結果** | 有効期限のように、ルールから導いた値 |

| 写さない | 理由 |
|---|---|
| **参照 ID** | 写すのではなく **そのまま残す**（次項） |
| **説明文・画像 URL などの大きいもの** | 履歴の表示に要らない。要るなら「要る」と決めてから写す |
| **他の行から集計できる値** | `SUM` で出せるものを持つと、合わなくなったときに直せない |

### ID は消さない

スナップショットを入れると、「もう ID は要らないのでは」と考えたくなります。両方持ってください。

```scala
productId:        Option[Product.Id],       // 参照：いまのマスタへたどる
productName:      String,                   // 写し：あのときの名前
productUnitPrice: Int,                      // 写し：あのときの単価
```

| 持っているもの | 何ができるか |
|---|---|
| **ID だけ** | 商品ごとの集計ができる。履歴は再現できない |
| **写しだけ** | 履歴は再現できる。**商品ごとの集計ができない**（名前が変わったら別商品になる） |
| **両方** | どちらもできる |

「てりやきバーガーの累計売上」を出すには ID が要ります。**写しは、参照の代わりではなく、参照に足すものです。**

## どこに置くか

> **消さないと決めたテーブルにだけ置きます。**

これが 3 問のうち、いちばん間違えやすいところです。

| | 揮発データ | ストックデータ |
|---|---|---|
| 例 | `Cart` / `Order` / `OrderItem` | `Payment` / `PaymentItem` / `PaymentDiscount` |
| 寿命 | 受渡しが終われば役目を終える | 消さない |
| スナップショット | **置かない** | **ここに置く** |

**消えるデータに履歴を持たせても、消えた時点で履歴も消えます。**

この教材でも、最初は `OrderItem` に単価を持たせました。注文の 1 行なのだから自然に見えます。しかし `OrderItem` は揮発データなので、そこに置いた履歴は、注文と一緒に消えます。

置き場所を決める問いは 1 つです。

> **このテーブルは、3 年後も残っているか。**
>
> 残っていないなら、そこにスナップショットを置いてはいけません。

### 根拠にするのも、消えない側

同じ判断が別の場所にも出ています。`CustomerStampCardItem`（押されたスタンプ 1 個）が持つのは `orderId` ではなく `paymentId` です。

```scala
paymentId: Payment.Id,  // どの会計で押されたか
```

スタンプの根拠は「注文した」ではなく「会計した」だからです。**消えるものを根拠にすると、根拠ごと消えます。**

## よくある失敗 5 つ

| # | 失敗 | 何が起きるか |
|---|---|---|
| 1 | **揮発データに置く** | 履歴が、元データと一緒に消える |
| 2 | **ID を消して写しだけにする** | 商品ごとの集計ができなくなる。名前が変われば別商品扱い |
| 3 | **レコード全体を JSON で丸ごと写す** | マスタの構造変更に引きずられ、読めない過去データが生まれる |
| 4 | **合計だけ写して内訳を写さない** | 「なぜこの金額か」に答えられない。返金の按分もできない |
| 5 | **写す瞬間を決めていない** | 人によって注文時／会計時がばらつき、数字が合わなくなる |

3 番は補足します。丸ごと写すのは、一見いちばん安全に見えます。しかしマスタに列が増減すると、過去の JSON と現在のコードが噛み合わなくなり、「読めるが解釈できない」データが増えます。要る列を選んで、型のある列として写してください。

## マスタ側で解決しようとする誘惑

スナップショットを避けようとすると、たいてい次の 2 つに行き着きます。どちらも、より高くつきます。

### 誘惑1：価格改定のたびに、新しいマスタ行を作る

古い商品を `IS_DISCONTINUED` にして、新価格の商品を新規登録すれば、過去の注文は古い行を指したままになります。履歴は保てます。

**代償：** 同じ「てりやきバーガー」が何行にも増えます。累計売上を出すには、どの行が同じ商品なのかを人が知っている必要があります。メニュー編成もそのたびに組み直しです。

### 誘惑2：マスタを絶対に消さない（論理削除）

削除しなければ参照は切れません。しかし **参照が生きていることと、値が変わらないことは別です。** 名前と価格は更新され続けるので、履歴の問題は 1 つも解決しません。

> どちらの誘惑も、**マスタに履歴の役目を負わせようとしています。** マスタは「いま」を表す場所です。役目を 2 つ持たせると、どちらも中途半端になります。

## 非正規化とは違う

スナップショットは、形だけ見ると非正規化とよく似ています。目的が違います。

| | 非正規化 | スナップショット |
|---|---|---|
| 目的 | **速度**（JOIN を減らす） | **正しさ**（あのときを再現する） |
| 元の値が変わったら | **追随させる**（同期する） | **追随させない**（そこが要点） |
| 消してよいか | よい（JOIN で復元できる） | **だめ**（復元できない） |

**「元が変わったら追随させるべきか」で判別できます。** 追随させたいなら非正規化、させたくないならスナップショットです。この 2 つを同じ列でやろうとすると、必ずどちらかが壊れます。

## 判断チェックリスト

新しいモデルにスナップショットを入れるとき、この順で確認してください。

```markdown
- [ ] 確定する瞬間はどこか（取り消せなくなる瞬間はどこか）
- [ ] そのテーブルは 3 年後も残っているか（残らないなら置かない）
- [ ] 参照 ID は残してあるか（写しは参照の代わりではない）
- [ ] 表示に使う値・金額に使う値を、列として写しているか
- [ ] ルールではなく、計算した結果を写しているか
- [ ] 合計だけでなく、内訳も写しているか
- [ ] 元が変わったら追随させたいか（させたいなら、それは非正規化）
- [ ] 集計で出せる値を、重複して持っていないか
```

## この教材での実例

| 写した先 | 写した値 | 元 | 確定の瞬間 |
|---|---|---|---|
| `PaymentItem` | `productName` / `productCategory` / `productUnitPrice` / `productSubTotal` | `Product` / `CustomProduct` | 会計 |
| `PaymentDiscount` | `discountType` / `discountUnitValue` / `discountSubTotal` | `Coupon` | 会計 |
| `Payment` | `billTaxRate` | **マスタが存在しない**（税制） | 請求 |
| `CustomerCoupon` | `expiredAt` | `Coupon.validDays`（ルール） | クーポン取得 |

そして `OrderItem` には、スナップショットが 1 つもありません。これも設計判断です。揮発データだからです。

# 付録：冗長に見える列 — `shopId` はデータではなく、境界の鍵

## 蛇足に見える列

`PaymentDiscount` の先頭 3 フィールドです。

```scala
id:        Option[Id],   // 管理Id
shopId:    Shop.Id,      // 店舗Id      ← これは要るのか？
paymentId: Payment.Id,   // 決済Id
```

`paymentId` から `Payment` を引けば、`Payment.shopId` が分かります。同じ値を 2 か所に持つのは、正規化の観点では重複です。第二正規形の説明でまず削られる形をしています。

しかもこの重複は、`edu.shop` の全体に及んでいます。

| モデル | `shopId` |
|---|---|
| `Shop` | — （自分自身） |
| `CustomMenu` / `CustomMenuItem` / `CustomProduct` | あり |
| `ExcludedMenu` / `ExcludedProduct` | あり |
| `Order` / `OrderItem` | あり |
| `Payment` / `PaymentItem` / `PaymentDiscount` | あり |

`Shop` を除く 10 モデルすべてです。**例外がありません。** うっかり付けたのではなく、規約として付けています。

## 最小のモデルが正しいとは限らない

モデル設計を学び始めると、「重複を削る」ことが正しさだと感じます。正規化はそのための技術ですし、実際、意味のない重複はバグの温床です。

しかし判断の基準は「小ささ」ではありません。

> **モデルの良し悪しは、小ささではなく、運用しやすさで決まります。**

冗長な列を持てば、書き込みが増え、親と食い違う可能性が生まれます。判断すべきは「重複しているかどうか」ではなく、その重複コストに見合う対価があるかです。

`shopId` の場合、対価は 4 つあります。順に見ます。

## 理由1：たどれることと、すぐ引けることは違う

`shopId` を持たない場合、店舗で絞るには必ず `Payment` を経由します。

![「導ける」と「引ける」は違うことを示した図。左は shopId を持たない場合で、PaymentDiscount から paymentId で Payment をたどり、さらに Payment の shopId で Shop に到達する 2 段の鎖になる。SQL は SELECT d.* FROM shop_payment_discount d JOIN shop_payment p ON p.id = d.payment_id WHERE p.shop_id = 42 となり、JOIN を 1 本必ず書く必要がある。書き忘れると他店の行まで返る。正しく書ける人だけが正しく引ける状態で、深夜の障害対応でこの JOIN を思い出せるかという問題が残る。右は shopId を持つ場合で、PaymentDiscount から直接 Shop に届く。paymentId は残したままで、親をたどる道は消していない。SQL は SELECT * FROM shop_payment_discount WHERE shop_id = 42 の 1 行で済み、JOIN の書き忘れという事故がそもそも起こらない。誰が書いても同じ結果になる。代償は 8 バイトと、書き込み時に親と食い違わせない責任](./img/scope-key-derive.svg)

差は JOIN 1 本です。性能の話に見えますが、本質は違います。

JOIN を書き忘れたときに何が返るかです。`WHERE p.shop_id = 42` を書き忘れたクエリは、エラーになりません。全店舗の割引行を返します。そして返ってきた結果は、一見ふつうに見えます。

`shopId` を持っていれば、`WHERE shop_id = 42` の 1 行です。書き忘れる余地が小さくなります。

> 誤解のないように書いておくと、**`paymentId` を消すわけではありません**。親をたどる道はそのまま残します。`shopId` は近道であって、代わりではありません。

## 理由2：アクセス境界の鍵になる

ここが最大の理由です。そして、この理由だけは **他の列で代用できません。**

### 条件が 1 本抜けたとき、何が起きるか

`WHERE shop_id = 42` を書き忘れたクエリは、エラーになりません。**全店舗の行を返します。** 例外も警告も出ないので、画面はふつうに描画されます。

これが何を意味するか。

| 場面 | 起きること |
|---|---|
| 店舗の売上画面 | 他店の売上が、自店の数字として表示される |
| B2B のテナント分離 | **他社のデータが 1 行でも見えたら、報告義務のある事故** |
| 個人情報を含む表 | 流出。しかも「いつから漏れていたか」を後から特定するのが難しい |

2 行目が重い。多くの受託・SaaS の契約では、他テナントのデータが見えた時点でインシデントです。原因が `WHERE` 1 行の書き忘れでも、結果は変わりません。

> **バグの大きさと、被害の大きさは比例しません。** 1 行の抜けが、事業を止める規模の事故になり得ます。

### 「気をつける」では守れない

とはいえ、レビューで毎回見つけ切るのは現実的ではありません。

- クエリは増え続ける。1 年後には数百本になる
- 書く人は入れ替わる。あとから入った人はこの規約を知らない
- **99 本正しくても、1 本漏れれば流出する**

守り方を変えます。条件を **「書き手が毎回書くもの」から「基盤が必ず足すもの」へ移します。**

![アクセス境界を、書き手の注意力から仕組みへ移すことを示した図。条件が 1 本抜けてもエラーは出ず、他人のデータがふつうの顔をして返ってくる。左は「書き手が毎回、条件を書く」場合で、WHERE shop_id = 42 が並ぶなかに 1 本だけ書き忘れた行が混じっている。99 本正しくても 1 本で漏れる。クエリは増え続け、書く人は入れ替わるので、レビューで毎回見つけ切るのは無理がある。右は「基盤が、必ず条件を足す」場合で、境界の条件を1 か所だけで「この表の shop_id ＝ いまの店舗」と宣言しておくと、以降のすべてのクエリに AND shop_id = 42 が自動で足される。書き忘れという事故が起こらず、横断が要るときだけ明示的に境界を外す。中段は、どの仕組みを使っても前提は同じであることを示す。自動で足される条件はその表の列だけで書けなければならず、親をたどってから比べるという条件は書けない。境界の鍵が行の上に無ければ、そもそも仕組みに載せられない。下段には仕組みの例として、DB の行レベルセキュリティ（表ごとにポリシーを 1 つ書く）、ORM の既定スコープ（モデルに既定の絞り込みを付ける）、スコープ付きリポジトリ（取得も更新も範囲を引数で受け取る）の 3 つが並ぶ](./img/scope-key-tenant.svg)

### どの仕組みを使っても、前提は同じ

自動で条件を足す仕組みには、いくつかの層があります。

| 層 | 仕組み | やること |
|---|---|---|
| DB | 行レベルセキュリティ | 表ごとにポリシーを 1 つ書き、DB が全クエリに適用する |
| ORM | 既定スコープ | モデルに既定の絞り込みを付ける |
| アプリ | スコープ付きリポジトリ | 取得も更新も、範囲を引数で受け取る |

どれを選んでも、**足される条件は「その表の列」だけで書けなければなりません。**

```sql
-- 書ける：その行だけを見て判定できる
shop_id = 42

-- 書けない：他の表をたどらないと判定できない
（payment_id から shop_payment を引いて、その shop_id と比べる）
```

理屈は単純です。**この条件は 1 行ごとに評価されます。** 評価のたびに別の表を引きに行くわけにはいきません。

> **境界を仕組みで守りたいなら、境界の鍵は行の上に載っていなければなりません。** これは設計の好みではなく、どの層を選んでも変わらない制約です。

`PaymentDiscount` に `shopId` がなければ、この表はどの仕組みにも載せられません。**「必要になったら足そう」が効かない列** です。

### この教材の基盤の場合

ixias にも、この層の仕組みがあります。範囲を値として渡し、取得も更新も範囲の外に出られないようにする作りです。実際の使い方は、永続化を扱う次の章で見ます。

ここで押さえるのは、**どの基盤を使うにせよ、境界の鍵を行に持たせておかないと選択肢がなくなる** ということだけで十分です。

## 理由3：障害対応と直接集計

アプリケーションが動かないとき、人は SQL を直接叩きます。

```sql
-- 42 番店の、今日の割引の合計
SELECT SUM(discount_sub_total)
  FROM shop_payment_discount
 WHERE shop_id = 42 AND created_at >= CURDATE();
```

このとき手元にあるのは、テーブル定義と経験だけです。モデルの継承関係も、リポジトリの実装も助けてくれません。深夜 2 時に、`JOIN shop_payment ON ...` を正確に思い出せるかという問題になります。

同じことが、日次のバッチ集計や、BI ツールから直接テーブルを見るときにも起きます。集計する人はたいていアプリケーションの実装を知りません。

## 理由4：物理分割の鍵になる

データが増えたとき、いちばん確実な逃げ道は「分ける」ことです。そして分けるには、分割対象の全部の行が同じ列を持っている必要があります。

![物理分割の鍵を示した図。左は現在の 1 台構成で、shop_payment、shop_payment_item、shop_payment_discount の 3 表が同じサーバにある。そこから shop_id で切ると、shop_id 1〜99、100〜199、200〜の 3 つに分かれ、それぞれに payment、payment_item、payment_discount の 3 表がまとまって動く。同じ店の行が必ず同じ側に集まるので、またぐ JOIN が発生しない。下段左は、なぜ「あとから」ではだめなのかの説明で、MySQL のパーティションキーは主キーとすべての一意キーに含まれていなければならず、shop_id を後から足すには主キーの張り替えが要る。数億行のテーブルで主キーを張り替えるのは実質つくり直しと同じ。下段右は、いま持っておけば選択肢が残るという説明で、MySQL のパーティショニング、DB サーバの水平分割（シャーディング）、特定店舗のデータだけ退避や削除、店舗単位のバックアップと復元が挙げられ、どれも使わずに終わってもよいが、使えないことが問題だとまとめる](./img/scope-key-partition.svg)

3 つの表が同じ鍵で切れることが効きます。`shop_payment` だけが `shop_id` を持っていて明細が持っていなければ、決済は分割できても明細は分割できず、分割をまたぐ JOIN が発生します。

### あとから足せない列である

MySQL でパーティショニングを使う場合、**パーティションキーは主キーとすべての一意キーに含まれていなければなりません**。つまり `shop_id` を後から追加してパーティションキーにするには、主キーを張り替える必要があります。

数億行のテーブルで主キーを張り替えるのは、実質つくり直しです。[01_GUIDE.md](./01_GUIDE.md#裏返し--いまならいくらでも壊せる) のフェーズ3 の話がそのまま当てはまります。

> ここで買っているのは **選択肢** です。パーティショニングもシャーディングも、使わずに終わるかもしれません。**使わずに済むのは幸運ですが、使えないのは事故です。** 8 バイトはその保険料としては安い。

## どこまで持ってよいか

「じゃあ何でも持てばいいのか」という話にはなりません。判断の順序を決めておきます。

![冗長な列をどこまで持ってよいかの判断フロー。上から順に見て、最初に当たったところで決める。① その列はアクセス境界の鍵か（この行を見てよい人を決める列。テナント・店舗・組織など）→ はいなら全行に持つ。例外を作らない、1 表でも欠けると成立しない。② 物理分割の鍵になりうるか（あとから足すと主キーの張り替えが要る。数億行では実質不可能）→ はいなら全行に持つ。使わずに終わってもよい、使えないのが困る。③ 障害対応や集計で、その表を単独で引くか（JOIN を 2 段たどらないと出せない状況が起きるか）→ はいなら持ってよい。ただしなぜ持つかをコメントに残す。④ 上のどれでもない（「あると便利そう」「たぶん速くなる」だけが理由になっている）→ 持たない。必要になってから足せる、親をたどれば出る。最下段は、持つと決めたら代償も引き受けるという注意で、冗長な列は親と食い違いうる。決済の shop_id が 42 で明細の shop_id が 43 という行が作れてしまうため、書き込みを 1 か所に集約し同じトランザクションで親から値を写す。この責任を負えないなら持たない方がよい](./img/scope-key-decision.svg)

この教材のモデルを、この基準で読み直すと筋が通ります。

| 列 | どこまで持っているか | 判定 |
|---|---|---|
| `shopId` | `Shop` 以外の **全モデル** | ① と ② に当たる。例外なし |
| `customerId` | `Order` / `OrderItem` / `Payment` まで。`PaymentItem` / `PaymentDiscount` には **ない** | ③ に当たるところで止めた |
| `orderId` | `OrderItem` / `Payment` まで | 同上 |

`customerId` が `PaymentItem` にないことに注目してください。「全部に付ける」わけではありません。

`PaymentItem` は決済金額の内訳であって、顧客を軸に引く行ではありません。「この顧客が何を買ったか」は `Payment` まで絞ってから明細を見れば足ります。一方 `shopId` は、**そもそも見てよいかどうか** を決める列なので、内訳にも要ります。

> 同じ「冗長な列」でも、**境界の鍵と、便利のための近道は重みが違います。** 前者は例外を作れません。後者は必要になってから足せます。

## 持つと決めたら、代償も引き受ける

冗長な列には、必ずこの危険がついてきます。

```
shop_payment          id=1000, shop_id=42
shop_payment_item     payment_id=1000, shop_id=43   ← 作れてしまう
```

型は防いでくれません。どちらも `Shop.Id` だからです。防ぐのは実装の側です。

| 守り方 | 内容 |
|---|---|
| **書き込みを 1 か所に集める** | 明細を作る処理を散らかさない。会計を確定するサービス 1 つに集約する |
| **親から写す** | `shopId` を引数で受け取らず、`payment.shopId` をそのまま使う |
| **同じトランザクションで書く** | 親と子が別トランザクションだと、途中で失敗したときに食い違う |

この責任を負えないなら、**冗長な列は持たない方がましです**。導出できる値を 2 か所に持つというのは、そういう約束です。

## まとめ

- モデルの良し悪しは小ささではなく、運用しやすさで決まる。重複しているかどうかではなく、重複コストに見合う対価があるかで判断する。
- `shopId` の対価は 4 つ。JOIN の書き忘れを防ぐ／アクセス境界の鍵になる／障害時に単独で引ける／物理分割の鍵になる。
- とくに 2 つ目は代用がきかない。境界の条件は **1 行ごとに評価される** ので、その表の列だけで書けなければならない。行に載っていない値では、どの仕組みにも載せられない。
- 4 つ目はあとから足せない。MySQL のパーティションキーは主キーに含まれている必要があるため、後付けは主キーの張り替えになる。ここで買っているのは選択肢。
- 判断の順序は ①境界の鍵か ②分割の鍵か ③単独で引くか ④それ以外。④ は持たない。
- **境界の鍵と、便利のための近道は重みが違う。** `shopId` は例外なし、`customerId` は `Payment` で止めた。
- 持つと決めたら、親と食い違わせない責任を負う。書き込みを 1 か所に集め、親から写し、同じトランザクションで書く。
