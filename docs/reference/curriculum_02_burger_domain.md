## 受け取った要求

> **「ハンバーガーショップのオンラインサービスを作ってほしい。**
> **お客さんがスマホで注文して、店舗で受け取れるようにしたい。店舗は複数あって、店によって売り切れも出る。**
> **商品はカスタマイズできる——サイズを選んだり、ピクルスを抜いたり、パティを追加したり。セットもある。**
> **支払いは外部の決済サービスを使う。店側では、注文が入ったら調理して、できたら受け取りに来たお客さんに渡す。」**

| 質問 | 今回の回答（仮） |
|---|---|
| 支払いは事前決済か、店頭か | **両方**あり得るが、外部サービスの結果を記録するだけにする |
| 受け取り時間は指定できるか | **できる** |
| 配達（デリバリー）はあるか | **今回はなし**（店舗受け取りのみ） |
| 会員登録は必要か | **必要**。ログインは雛形の `user` を使う |
| クーポン・ポイントは | **今回はなし** |
| 店舗スタッフ用の画面は | **今回はなし**（注文の状態遷移だけ用意しておく） |

## ① 業務フロー

```
[会員]
 1. アプリを開き、ログインする
 2. 受け取る店舗を選ぶ（営業時間外の店は選べない）
 3. メニューを見る（カテゴリごとに商品が並ぶ／売り切れの商品は選べない）
 4. 商品を選ぶ
 5. オプションを選ぶ（サイズは 1 つだけ、トッピングは複数可、必須のものもある）
 6. 数量を決めてカートに入れる
 7. カートの中身と合計金額を確認する
 8. 受け取り時間を選ぶ
 9. 注文を確定する  ← ここで金額が確定する
10. 支払う（外部の決済サービスへ）
11. 注文の状態を見ながら待つ
12. 店舗で受付番号を見せて、商品を受け取る

[店舗スタッフ]
13. 入った注文を見る
14. 調理を始める        ← ここから会員はキャンセルできない
15. できあがったら「受け取り準備完了」にする
16. 会員に渡して「受け渡し完了」にする

[例外・ルール]
 - 売り切れの商品はカートに入れられない／注文確定時にも再チェックする
 - 営業時間外の店舗には注文できない
 - 調理開始後はキャンセルできない
 - 注文したあとに商品の価格が変わっても、注文の金額は変わらない
 - 商品が販売終了になっても、過去の注文履歴は正しく表示できる
```

**下 5 行が最重要。** 業務ルールのほとんどは例外側にあります。

## ③ ふるい分け（抜粋）

| 名詞 | 仕分け | 理由 |
|---|---|---|
| 会員 / 店舗 / カテゴリ / 商品 / カート / 注文 / 注文明細 / 支払い | **エンティティ** | ID で区別する |
| 価格 / 数量 | **値オブジェクト** | 590 円は 590 円。区別する意味がない |
| オプション（サイズ / トッピング） | **エンティティ** | 「選択肢のまとまり」と「1 つの選択肢」の 2 階層 |
| セット | 対象外（＝商品の一種） | 中身の選択はオプションで表現する |
| 売り切れ | 属性 | ただし **店舗ごとに違う** ので、店舗と商品の組に対する状態 |
| 決済サービス | 対象外 | 外部システム |
| 調理 | 対象外（＝状態遷移） | 「調理中」という状態として表現する |

> **「セット」を独立したエンティティにしなかった**。セットを別扱いにすると、価格計算・在庫・表示のすべてが二重になります。**業務の言葉をそのままクラスにしない**——これも設計判断です。

## 名前の付け方：接頭辞をそろえて、並べたときに固まるようにする

英語名を決めるとき、**1 つずつ「いちばん自然な英語」を選んではいけません**。全体を並べたときにどう見えるかで決めます。

ここで決めた名前は **ファイル名・クラス名・テーブル名** になり、それらは **ほぼ必ず名前順に並んで表示** されます（`ls` / `SHOW TABLES;` / IDE の補完 / ER 図ツール）。

### 悪い例

```
Cart / Category / Choice / Inventory / Order / Payment / Product / Store
```

英単語としてはどれも正しい。しかし **メニューまわりを直したい人が `Category` / `Choice` / `Product` にたどり着けません。**

### 良い例

```
MenuCategory / MenuItem / MenuItemOptionGroup / MenuOptionGroup / MenuOptionItem / Shop / ShopMenuStock
```

```
common_menu_category / common_menu_item / common_menu_item_option_group
common_menu_option_group / common_menu_option_item / shop / shop_menu_stock
```

`SHOW TABLES;` を上から読むだけで、**「メニュー系が 5 つ、店舗系が 2 つ」** と分かります。

### 接頭辞の決め方

| 決めごと | 例 |
|---|---|
| **親になる概念の名前を接頭辞にする** | `Menu*` / `Shop*` / `Cart*` / `Order*` |
| **明細は「親＋Item」** | `CartItem` / `OrderItem` |
| **明細に付くものは「親＋Item＋種類」** | `CartItemOption` / `OrderItemOption` |
| **多対多の交差は「所有する側 → される側」の順** | `MenuItemOptionGroup` / `ShopMenuStock` |

### テーブル名の作り方

クラス名はパッケージで仕切られますが、**テーブル名はフラットな 1 つの名前空間**。だから **コンテキストのパスを頭に付けます**。

```
edu/common/menu/model/MenuItem.scala   →   common_menu_item
edu/shop/model/Shop.scala              →   shop
edu/sales/model/OrderItem.scala        →   sales_order_item
```

**重複はマージします。** 規則は 1 つ、**「エンティティ名がコンテキスト名で始まるなら、重ねない」**。

| エンティティ | 素直に連結すると | 実際のテーブル名 |
|---|---|---|
| `edu.common.menu` の `MenuItem` | ~~`common_menu_menu_item`~~ | **`common_menu_item`** |
| `edu.shop` の `Shop` | ~~`shop_shop`~~ | **`shop`** |
| `edu.shop` の `ShopMenuStock` | ~~`shop_shop_menu_stock`~~ | **`shop_menu_stock`** |

> **テーブル名はすべて単数形です。** 理由は `curriculum_04_naming.md` を参照。

### 「正しい英語」より「そろった名前」

**接頭辞をそろえると、英語としては不自然な名前になることがあります。それでよいのです。**

| 名前 | 英語として自然か | それでも採用する理由 |
|---|---|---|
| `MenuOptionItem` | ✗ 冗長 | `Menu*` に属することが名前で分かる |
| `ShopMenuStock` | ✗ 在庫「数」は持たない | **店舗 × 商品の交差**だと名前で分かる |
| `MenuItemOptionGroup` | ✗ 長い | 対応であることが名前だけで読める |

判断基準は **「英語として自然か」ではなく「チームの誰が見ても、どこに属する概念か分かるか」**。

> ⚠️ **ただし「英語をいいかげんにしてよい」という話ではありません。**
> - **ローマ字は使わない**（`ShohinKubun` / `Tenpo` は不可）
> - **和製英語・誤用は避ける**
> - **1 つの概念に 1 つの語**。`Shop` と決めたら `Store` を登場させない

### ルールを外すときは、理由を書き残す

`Payment` は規則からすると `OrderPayment` にすべきかもしれませんが、「外部の決済サービスとの境界に立つ、独立した概念」と捉えてそのままにしました。

**規則は思考を節約するためのもので、意味を曲げてまで従うものではありません。** ただし外したときは **理由を残してください。** 理由のない例外は、次の人には「ただの不統一」にしか見えません。

## ⑤ コンテキスト

| コンテキスト | 記号 | 変更の理由 | ライフサイクル | 管理する人 |
|---|---|---|---|---|
| 会員 | `udb` | 認証方式の変更 | 数年 | 会員本人 |
| 商品マスタ | `common/menu` | メニュー改定・価格改定 | 数ヶ月〜数年 | 本部 |
| 店舗 | `shop` | 新店舗・営業時間の変更・**売り切れ** | 店舗は数年、売り切れは **数時間** | 本部（店舗）／店長（売り切れ） |
| 注文 | `sales` | 注文フローの変更・決済手段の追加 | 数十分（履歴としては永久） | 会員と店舗スタッフ |

### 「誰が触るか」で線を引く

> **このデータを、日常的に書き換えるのは誰か？**

| 日常的に書き換える人 | 何を書き換えるか | コンテキスト | その人が見る画面 |
|---|---|---|---|
| **会員（購入者）** | カートに入れる / 注文する / 支払う | `sales` | スマホアプリ |
| **店舗スタッフ・店長** | 調理を進める / 売り切れにする | `shop` | 店舗のタブレット |
| **本部** | 商品を追加する / 価格を改定する | `common/menu` | 本部の管理画面 |
| **会員本人** | パスワードを変える | `udb` | スマホアプリ（設定） |

`shop` と `sales` を分けたのは、**注文を作るのは購入者、売り切れを切り替えるのは店舗の人員**だから。同じ「店舗まわりの話」に見えても、触る人が違えば別のコンテキストです。

**アクターで分けるとうまくいく理由は 3 つ。**

1. **変更のタイミングが揃う** — 仕様変更が 1 コンテキストで収まれば、影響範囲の調査が要りません
2. **画面と権限が揃う** — **作る画面の数を数えると、だいたいコンテキストの数に近くなります**
3. **負荷と障害が波及しない** — 将来 DB を分けるときも、この線がそのまま分割線になります

### 分けすぎない

| 分けすぎると起きること | 具体的に |
|---|---|
| **配線が増える** | パッケージ・`Module`（DI 登録）・`RepositoryFacade`・`app-api` 側が 1 行ずつ増える |
| **結合がアプリ側の仕事になる** | 画面を 1 つ描くのに 3 つのリポジトリを呼んで自分で組み立てる |
| **置き場所に迷う時間が増える** | 「これはどっち？」で手が止まる |

目安は **最初は 3〜5 個**。そして、

> **迷ったら大きめに作って、後から割る。**

**`common` をサブカテゴリにしたのは、この判断です。**

```
コンテキストを増やす           common の中を仕切る（採用）
edu/menu/                      edu/common/menu/
edu/geo/         ← 配線 ×3      edu/common/geo/     ← 配線 ×1
edu/coupon/                    edu/common/coupon/
```

**サブカテゴリで仕切っておくと、独立したコンテキストへの引き上げが「ディレクトリを 1 つ移動する」だけで済みます。**

### `common` — マスタ（参照データ）の置き場

```
edu/common/
├── menu/      … メニュー（この部で作る）
├── geo/       … 都道府県・市区町村（配達を作るときに使う）
└── coupon/    … クーポンの定義（今後）
```

> ⚠️ **`common` は放っておくとゴミ箱になります。** **入れてよいのは、次の 3 つをすべて満たすものだけ。**
>
> 1. **業務の操作では変わらない** — 会員の注文やスタッフの調理で書き換わらない
> 2. **管理者が別にいる** — 本部・運用チームが、業務とは別のタイミングで更新する
> 3. **他のコンテキストから参照されるだけ** — `common` 側から他を参照しない（依存が一方向）
>
> **売り切れ（`ShopMenuStock`）は条件 1 で落ちます** ——店舗スタッフが日々書き換える運用データなので `shop` に置きました。**この判定ができることが、`common` を「共有物置き場」にしないための歯止めです。**

### またぐ参照は ID だけ・一方向

```
Order     ──(User.Id)──▶      User          （sales → udb）
Order     ──(Shop.Id)──▶      Shop          （sales → shop）
OrderItem ──(MenuItem.Id)──▶  MenuItem      （sales → common/menu）
ShopMenuStock ─(MenuItem.Id)─▶ MenuItem     （shop  → common/menu）
```

**`MenuItem` は自分が注文されたことを知りません。** マスタ側が注文を知らないからこそ、メニュー改定が注文に波及しません。

## 設計上の論点と、その判断

### 論点1：カートは DB に持つか、ブラウザに持つか

**判断：DB に持つ。** localStorage だと「スマホで入れた商品が PC で見えない」ことになります。飲食のモバイルオーダーでは、**注文直前の離脱を減らすためにカートを残す** のが定石。

### 論点2：注文明細は商品 ID だけを持てばよいか

**判断：ダメ。注文時点の商品名と単価を写し取って持つ（スナップショット）。**

`OrderItem` が `MenuItem.Id` だけを持つ設計だと、**価格改定した瞬間に過去の注文の金額が書き換わります**。これは会計上の事故です。

逆に `CartItem` は **スナップショットを持ちません**。カートは「これから買うもの」なので、価格が変わったら **新しい価格が反映されるべき** だからです。**同じ「明細」でも、カートと注文で設計が逆になる。**

### 論点3：合計金額は保存するか、毎回計算するか

**判断：`Order` には保存する。`Cart` には保存しない。**

一般に「計算で出せるものは持たない」のが原則ですが、注文の合計金額は **「そのとき確定した事実」** であり、再計算されてはいけません。

### 論点4：売り切れをどこに持つか

**判断：`MenuItem` ではなく `ShopMenuStock`（店舗 × 商品）に持つ。**

売り切れは商品そのものの性質ではなく、**店舗と商品の組み合わせの性質**です。

### 論点5：受付番号に DB の ID を使わないのはなぜか

**判断：`Order.Code` という別の識別子を持つ。**

連番の ID を店頭で呼ぶと注文総数が漏れます。URL に連番が出れば、他人の注文を覗ける実装ミスを誘発します。
