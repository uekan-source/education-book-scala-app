## 1：アクターが増えるか（3 分）

既存システムへの追加なら、アクターはもう立っている。**増えるかだけ見る。**

| 新機能 | 増えるアクター |
|---|---|
| 返金・取消 | CS・サポート |
| 承認フロー | 承認者 |
| 自動失効・締め処理 | バッチ |
| 外部連携 | 外部サービス |
| 集計・レポート | 経営・分析 |
| 複数拠点・テナント | 運営者・本部 |

**立て忘れた人の所持物は、作り忘れるのではなく存在に気づかない。** 誰も指摘できないので、レビューでも出ない。

## 2：前提を 4 つ

**要求文に 1 文字も書かれていないのに、モデルの形を決めてしまうもの。**

| 前提 | 聞くこと | 抜けるとどうなるか |
|---|---|---|
| **規模** | 何件になる想定か | 過剰設計か、運用破綻か |
| **保存期間** | 何年残すか。消していいか | **スナップショットの置き場所が決まらない** |
| **アクセス境界** | 誰が誰のデータを見てよいか | **後から足せない列が抜ける** |
| **既存資産** | 既に何があるか | 「既存で足りる」の判定ができない |

## 3：所持物を演繹する

**「この人が持っているべきものは何か」**を人から問う。名詞を拾う作業とは方向が逆なので、**要求文に無いものが出る。**

規模が未確定なら 2 通りで出させて、差分を質問にする。

```
- 想定規模が不明なので、A（小規模）と B（大規模）の 2 通りで出してください
- 両者で差が出た所持物には印を付けてください
```

**印が付いたものが、そのまま質問になる。** 理由まで言えるので質問として強い。

## 4：業務フロー

**アクターが先、フローが後。** 先にフローを書くと、書いたフローの主語しか登場しない。

- 主語を必ず書く
- **例外は断定せず「〜の場合はどうなりますか」の質問形で書く**（AI に書かせると創作が混ざる）
- チェックは「**すべてのアクターが、どこかで主語になっているか**」

## 5：名詞と動詞 → ふるい分け → 用語

**この段階の詳細は [`../reference/my_discovery_process.md`](../reference/my_discovery_process.md) の ②③ にある（自分で書いたもので、一番厚い）。** ここには要点だけ。

### 動詞を先に拾う

名詞から拾うと迷う。**動詞を先にやると名詞が楽になる。**

- **能動形にそろえる。** 受動形は主語を隠す（「スタンプが押される」→「店舗がスタンプを押す」）
- 動詞を 2 つに分ける ── **「状態を変える（書き込む）」** と **「値を返す（読むだけ）」**
- 動詞の形をしていても操作でないものがある

### 全部拾ってから捨てる

**対象外は「拾ったもの」からしか生まれない。** 拾う段階で取捨選択すると、捨てた理由が残らない。

教材の一覧は**例であって網羅リストではない**ので、そこに無いものも拾う。

### ふるい分けは 4 分類

| | 判定 |
|---|---|
| エンティティ | 単体で探す / 個別に増減する / 同じ値でも別物 |
| 値オブジェクト | 値が同じなら同一。中身が 1 つなら `OpaqueValue`、2 つ以上なら `case class` |
| ただの属性 | 単体で探さない |
| 対象外 | 計算できる / 業務の外 |

**振り分け表に載せるのは「エンティティ」と「対象外」の 2 種類だけ**でいい（問題 2 で得た知見。属性まで全部書くと表が読めなくなる）。

### 用語（ユビキタス言語）

英語名の決め方は `../reference/curriculum_04_naming.md`（評価の 7 軸）。テーブル名の規約は `curriculum_02_burger_domain.md`。

**「何と呼ぶか」だけでなく「何と呼ばないか」も決める。** 書かないと次の会議で言い換えが起きる。

## 6：概念を配る

| 判定 | 意味 |
|---|---|
| **既存で足りる** | **これが書けたら成果** |
| 追加する | 新しく作る |
| 既存から動かす | 置き場所を変える |

配れない行が出たら、それが発見。

| 埋まらない形 | 意味 |
|---|---|
| 2 人の列に同じ概念 | **2 つに割れる合図** |
| 5 分以上迷った | 概念が 2 つ混ざっている |

## 7：モデルの形

**フィールドを 1 本足すたびに、この 4 つを通す。** 理由は [`design_lessons.md`](./design_lessons.md)、原典は `../reference/curriculum_06_design_patterns.md`。

| 判断 | 問い | 迷ったら |
|---|---|---|
| **保存するか計算するか** | ① 後で計算し直して同じ答えが出るか　② SQL で直接使うか | 両方 No なら**計算**。マスタを見て計算した値は**保存** |
| **どこに置くか**（保存する場合） | **そのテーブルは 3 年後も残っているか** | 残らないなら**置かない**。揮発データに履歴を持たせても一緒に消える |
| **冗長な列を持つか** | ①境界の鍵 → 全行に持つ　②分割の鍵 → 全行に持つ　③単独で引く → 持ってよい　**④それ以外 → 持たない** | ①② は**後から足せない**。③ は後から足せる |
| **`enum` かテーブルか** | その値が増えたとき、**コードを書く必要があるか** | 書くなら `enum`（エンジニアが増やす）。書かないならテーブル（運用担当が増やす） |

あわせて 2 つ確認する。

| 確認 | 何を見るか |
|---|---|
| **無効な組み合わせが作れないか** | `Option` の使い方。「片方だけ `Some`」のような**型で防げない組み合わせ**が残っていないか |
| **区分値が隣のフィールドの読み方を決めていないか** | 決めているなら、**型では守れない決めごとに必ず書く**。書かないと実装者ごとに解釈が変わる |

**スナップショットと非正規化は形が同じで目的が逆。**「元が変わったら追随させたいか」で判別する。追随させたいなら非正規化、させたくないならスナップショット。**同じ列で両方やろうとすると必ずどちらかが壊れる。**

## 8：流す

### 新機能のフロー

正常系と例外。ここは普通に流す。

### 既存フロー ← ここが本番

**新モデルが参照している既存モデルに、もともとある流れ。** 手順は 3 つ。

```
1. 新モデルの ○○Id を全部書き出す
2. その参照先に「戻す操作」があるか見る
3. その操作が起きたとき、新モデルがどうなるか答える
```

**3 で答えられなければ、それが穴。**

| 参照している既存モデル | 見るべき既存フロー |
|---|---|
| `Order` | **キャンセル** |
| `Payment` | **決済失敗 / 返金** |
| `Customer` | **退会 / アカウント統合** |
| `Product` | **販売終了 / 値上げ** |
| `Shop` | **閉店 / 休業** |
| `Coupon` | 廃止 / 内容変更 |

**危ないのは「戻す操作」。** 進む方向は新機能のフローで見ている。穴が開くのは逆行するとき。

```
キャンセル / 返金 / 退会 / 取消 / 削除 / 失効 / 復活
```

**進むときは 1 本道でも、戻るときは分岐する。** スタンプカードで踏んだ穴がこれだった。

> 使用済みのクーポンがキャンセルで復活すると、販売終了した商品のクーポンが使える状態に戻る
