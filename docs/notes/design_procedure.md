## 直線ではない

**要件定義とモデル設計は並行して回す。** モデルに落とそうとして初めて決まっていないことが見つかるので、片方を完成させてから次に進むことはできない。

```
                    ┌──────── 顧客とのミーティング ────────┐
                    ↓                                    │
        受け取った要求 / 追加のヒアリング                    │
                    ↓                                    │
   ┌────────────────────────────────────────┐            │
   │  01_requirements.md   前提・質問・業務フロー │            │
   │  02_analysis.md       名詞と動詞・ふるい分け │  ←─ 並行 ─→ │
   │  03_design.md         用語・モデル・決めごと │            │
   └────────────────────────────────────────┘            │
                    ↓  01 と 03 を提出                     │
                    └────────────────────────────────────┘
                    ↓  周を重ねて固まったら
        edu/*/model/*.scala     メソッド・検証・WithNoId を足す
```

| 周 | やること |
|---|---|
| 1 周目 | **粗くていいので端まで通す。** 穴を見つけるのが目的 |
| 2 周目以降 | 見つけた穴を質問し、回答を反映して精度を上げる |
| ミーティングのたび | 前提が変わることがある。**変わるのは正常** |

> ⚠️ **教材もこの文書も、何周も回した後の姿を 1 回で見せている。** あの順に 1 回で出てきたわけではない。**1 周目で完成形を目指すと必ず詰まる。**

実際、決済明細（`PaymentItem`）は 3 回作り替わっている。注文明細に単価を持たせ → 揮発データだと分かって決済側に移し → 割引の参照先を商品から明細行に変えた。**モデルだけで回していたので、コストは `sbt compile` 3 回だった。**

## 1：アクターと所持物

> **目的は、後の業務フローと質問リストを漏れなく洗い出すこと。** アクターが揃っていないと、**フローの主語も、質問の相手も片側に偏る。** スタンプカードで質問が会員側に 4 つ／本部側に 1 つと偏ったのは、本部を主役として立てていなかったから。

既存システムへの追加なら、アクターはもう立っている。**増えるかだけ見る。**

| 新機能 | 増えるアクター |
|---|---|
| 返金・取消 | CS・サポート |
| 承認フロー | 承認者 |
| 自動失効・締め処理 | バッチ |
| 外部連携 | 外部サービス |
| 集計・レポート | 経営・分析 |
| 複数拠点・テナント | 運営者・本部 |

**立て忘れた人の所持物は、作り忘れるのではなく存在に気づかない。** 誰も指摘できないので、レビューでも出ない。

### ゼロから洗い出すとき ── 7 つの問い

思い出すのではなく、**数え上げる。** 答えられなければ「いない」と書けば済む。

| # | 問い | 出てくるもの |
|---|---|---|
| 1 | このデータを **最初に作る** のは誰か | 登録者・入稿者 |
| 2 | **日常的に変更する** のは誰か | 運用担当・現場 |
| 3 | **止める・承認する** 権限を持つのは誰か | 管理者・承認者 |
| 4 | **お金を受け取る／払う** のは誰か | 事業者・顧客・決済代行 |
| 5 | **集計を見る** のは誰か | 経営・分析 |
| 6 | **問い合わせを受ける** のは誰か | CS・サポート |
| 7 | **人ではないが動く** ものは何か | バッチ・外部 API |

**問 1 だけで運営者・本部が出る。**「誰が最初に作るか」はそれだけ強い問い。

そのあと、上の 6 類型を 1 つずつ確認する。**「いない」と判断したものも、いないと明記して理由を書く。** 書かないと、検討したのか漏れたのか後から分からない。

### レビューするとき ── 逆引きテスト

**モデル一覧が既にあるなら、7 問を回しても同じものしか出ない。モデル側から問う。**

| テスト | 不合格なら |
|---|---|
| すべてのモデルについて「**これを最初に作るのは誰か**」に答えられるか | **アクターが足りない** |
| すべてのモデルについて「**消えたら誰が困るか**」に答えられるか | そのモデルが要らないか、アクターが足りない |
| ある画面が**すべてのコンテキストを書き換える**ことになっていないか | 境界が業務と合っていない |
| **状態の遷移を、すべてどれかのアクターが起こす**と言えるか | **バッチ／外部サービスを立て忘れている** |

**4 行目が一番安い。** `state` を上から眺めて「これは誰が動かすか」を言うだけ。言えないものがあれば、そこにバッチか外部サービスがいる。

## 2：前提を 5 つ

**要求文に 1 文字も書かれていないのに、モデルの形を決めてしまうもの。**

| 前提 | 聞くこと | 抜けるとどうなるか |
|---|---|---|
| **規模** | **どこまで大きくなる想定か**（「いま何件」ではない） | 過剰設計か、運用破綻か |
| **保存期間** | 何年残すか。消していいか | **スナップショットの置き場所が決まらない** |
| **アクセス境界** | 誰が誰のデータを見てよいか | **後から足せない列が抜ける** |
| **既存資産** | 既に何があるか | 「既存で足りる」の判定ができない |
| 法規制・監査 | 消してはいけないものがあるか | 「7 年保存」なら消せない。保存期間の線が動く |

規模の効き方は具体的で、**同じ要件でも正しいモデルが変わる。**

| | 3 店舗の個人経営 | 300 店舗のフランチャイズ |
|---|---|---|
| メニュー構成 | 店ごとに手で組んでよい | 本部がテンプレートを作って配る仕組みが要る |
| 店舗独自の商品 | 概念が要らない | 本部の商品と型で区別する必要がある |

## 3：業務フロー

**最初から順番付きで書かない。** 棚卸し → 振り分け → 検算。**広げきってから絞る。**

### やること

- [ ] **棚卸し** ── 段階 1 のアクターを主語に、やることを思いつく限り書き出す
      （**番号を振らない** / **振り分けない** / **行頭に主語** / 分からないことは質問リストへ）
- [ ] **否定形の問い**と **5 軸**を当てて、取りこぼしを拾う（**振り分けた後では新しいものは出ない**）
- [ ] **振り分け** ── 本文（番号付き）と例外・ルールに分ける
- [ ] **検算** ── 重複 / 1 行 1 事実 / 実装の混入 / 主語の網羅 / 既存ルールの再掲

**棚卸しの書き方**（行頭にアクターを置く）

```
- [会員]    アプリを開いてログインする
- [会員]    スタンプ数を確認する
- [システム] 支払い確定でスタンプを 1 個付与する
- [システム] キャンセルされたらスタンプを取り消す
- [-]       スタンプは店舗をまたいで共通        ← 主語なし＝例外行き
```

主語を書くのは 3 つのため。**後で「誰が触るか」の判断材料になる** / **主語が付けられないもの＝例外行きの合図** / **すべてのアクターが主語になっているかを検算できる。**

### 判断基準

**本文か例外か**

| | 判定 |
|---|---|
| その取引が**どう終わるか**の分岐 | **本文** |
| 取引と**無関係に**起きる | **例外** |

例外欄には「本文の時系列に収まらないが守るべきこと」も入る。**時系列で書けないものは全部ここ。**

**取りこぼしを拾う 5 軸**（棚卸しで使う。検算でもう一度使う）

| 数 | 時間 | 打ち消し | 同時 | ゼロ |
|---|---|---|---|---|
| 上限・下限はあるか | 期限・順序はあるか | キャンセル・取り消しは起きるか | 2 つ同時に起きたら | 0 個・空のとき |

**状態遷移がある要求では「打ち消し」と「時間（順序）」が効く。**「押し間違えたら戻せるか」「状態は飛ばせるか」が、そのまま遷移の設計になる。

**書くか書かないか** ── `01` は発注者と話す資料。**実装の話を書かない。**

| 記述 | 判定 |
|---|---|
| 有効期限（付与日から 1 年）を過ぎたスタンプは、保有数から除外される | **業務ルール。書く** |
| **有効なスタンプ数は保存せず、表示のたびに数え上げる** | **実装方針。書かない**（段階 8 で決める） |

**両方とも「1 年で失効する」という同じ話**だが、下は**どう実現するか**。発注者に「数え上げます」と言っても意味がない。

> **「発注者に言って通じるか」で判定する。**

### 落とし穴

| やりがち | 正しくは |
|---|---|
| 最初から順番付きで書く | **棚卸しが先** |
| 書きながら振り分ける | **広げきってから絞る** |
| 否定形を振り分けの基準にする | **発見の道具**であって基準ではない |
| 主語ブロックを時間帯で増やす | **時間軸の違いは例外欄が担う** |
| 主語が付けられなくて悩む | **付かないもの＝例外行きの合図** |
| 行数を目標にする | 下限は「例外 3 行以上」だけ。**例外が本文より多いのは正常** |

### 段階 8 のあとに戻る ── 逆算チェック

**モデルが決まってから `01` に戻る。** ここではできない。

| 見つかるもの | 意味 |
|---|---|
| 例外を書いたが、モデルに何も対応しなかった | 書きすぎ。次回の粒度感覚に反映する |
| **モデルに属性を足したが、対応する例外がなかった** | **例外を書き漏らしている** |

→ 詳細・**書き上がった業務フローの実物**：[`../reference/my_discovery_process.md`](../reference/my_discovery_process.md) ①

## 4：名詞と動詞を拾う

**拾うだけ。取捨選択しない。** 仕分けは段階 5。

> 詳細と**書き上がった一覧の実物**は [`../reference/my_discovery_process.md`](../reference/my_discovery_process.md) の ②（自分で書いたもので、一番厚い）。

### やること

- [ ] **動詞を先に拾う**（名詞から拾うと迷う。動詞をやると名詞が楽になる）
- [ ] **能動形にそろえる**（「スタンプが押される」→「店舗がスタンプを押す」）
- [ ] 動詞を 2 つに分ける
- [ ] **名詞を、思いつく限り拾う**

### 判断基準

**動詞の仕分け**

| | 中身 |
|---|---|
| **状態を変える**（書き込む） | INSERT / UPDATE。**行き先のモデルを書く** |
| **値を返す**（読むだけ） | SELECT。モデルは増えない |

**受動形は主語を隠す。** 能動形に直すと「誰がやるのか」が出てきて、段階 1 のアクターと突き合わせられる。

### 落とし穴

| やりがち | 正しくは |
|---|---|
| 拾いながら捨てる | **対象外は「拾ったもの」からしか生まれない。** 捨てた理由が残らなくなる |
| 教材の一覧を網羅リストだと思う | **あれは例。** そこに無いものも拾う |
| 動詞の形をしていれば操作だと思う | **操作でないものがある**（「〜が必要」「〜に該当する」） |

## 5：名詞のふるい分け

**4 つに仕分ける。** ここで初めて判断が入る。

> 詳細と実例は [`../reference/my_discovery_process.md`](../reference/my_discovery_process.md) の ③。

### やること

- [ ] 拾った名詞を **4 分類**する
- [ ] **「対象外」が 0 件なら、仕分けをしていない**と疑う
- [ ] 表に載せるのは **エンティティと対象外の 2 種類だけ**
- [ ] 「いくつ作るか」で迷ったら、下の問いを当てる

### 判断基準

**4 分類**

| | 判定 |
|---|---|
| **エンティティ** | 単体で探す / 個別に増減する / **同じ値でも別物** |
| **値オブジェクト** | **値が同じなら同一。** 中身が 1 つなら `OpaqueValue`、2 つ以上なら `case class` |
| ただの属性 | 単体で探さない |
| **対象外** | **計算できる** / 業務の外 |

**いくつ作るかで迷ったとき**（**いいえ** なら右へ）

| 迷い | 問い | いいえ なら |
|---|---|---|
| エンティティか属性か | 他のものと **別々に作られ、別々に更新され、別々に消える** か | **属性にする** |
| 1 つか、2 つに分けるか | **同じ人が、同じ画面で、同時に編集する** か | **分ける**（はい なら 1 つ） |
| `1:1` か `1:*` か | 繰り返しの **8 個目が来る可能性がある** か | **`1:1`**（列で持つ） |

> **足りないより、増やしすぎのほうが直しにくい。迷ったら少ないほうに倒す。**

### 落とし穴

| やりがち | 正しくは |
|---|---|
| 業務に言葉があるからモデルにする | **「カード」と「クーポン」は同じモデルの状態違いだった** |
| 属性まで全部を表に書く | **表が読めなくなる。** エンティティと対象外だけ |
| 計算できるものを保存する | 「あと何個か」は**数え上げればいい** |

## 6：ユビキタス言語（用語）

**議論ではなく評価で決める。** 候補は最低 4〜5 案。

### やること

- [ ] 候補を **4〜5 案**出す
- [ ] **7 軸で採点**する（①③④ を重く見る。単純平均にしない）
- [ ] **採用しない案とその却下理由を残す** ── 却下理由が、そのまま採用案の説明になる
- [ ] **「何と呼ばないか」も決める**（書かないと次の会議で言い換えが起きる）
- [ ] 既存の名前に混ぜて**名前順に並べ**、接頭辞がそろっているか見る

### 判断基準 ── 7 軸

| # | 軸 | 問い |
|---|---|---|
| ① | **役割差が読めるか** | 2 つ並べたとき、何がどう違うか名前で分かるか |
| ② | 意味の正確さ | 英単語として誤解を招かないか |
| ③ | **並び・グルーピング** | 名前順に並べたとき、関連するものが隣り合うか |
| ④ | **業務の人に通じるか** | その言葉で会話できるか |
| ⑤ | 長さ | テーブル名が長くなりすぎないか（MySQL は 64 文字まで） |
| ⑥ | 拡張余地 | 将来の要求で名前が壊れないか |
| ⑦ | 多重度が読み取れるか | `1:1` か `1:*` かが名前と矛盾しないか |

**軸が足りないと気づいたら足して、全候補を付け直す。** 増えた軸こそ、その設計でいちばん効いている論点。

テーブル名の規約は `../reference/curriculum_02_burger_domain.md`。

### AI に名前を評価させるプロンプト

```
【対象】これから名前を決めたい 2 つのモデル
- A: （何を表すか。既存モデルとの多重度 1:1 / 1:* まで書く）
- B: （同上）

【評価軸】次の 7 つ。それぞれ 10 段階で点を付け、根拠も 1 行書くこと。
① 2 つ並べたとき役割の差が名前で読めるか
② 英単語として誤解を招かないか
③ 名前順に並べたとき関連するものが隣り合うか
④ 業務の人に通じるか
⑤ 長さ（テーブル名が長くなりすぎないか）
⑥ 将来の要求で名前が壊れないか
⑦ 多重度（1:1 / 1:*）が名前と矛盾しないか
総合点は単純平均にせず、①③④ を重く見ること。

【制約】
- 既存に （既存モデル名） がある。接頭辞をそろえること
- テーブル名は （接頭辞）_ で始め、コンテキスト名と重ねない
- ローマ字禁止。1 つの概念に 1 つの語

【出力】
- 候補を 5 つ以上。採用しない案も必ず含める
- 軸ごとの点・総合点・却下理由を表で
- 1 つに絞らず、全候補を並べたうえで推奨を 1 つ示すこと
```

**3 つとも書かないと使い物にならない。**

- **【対象】に構造を書く** ── `1:1` / `1:*` を書かないと一般論しか返らない
- **【制約】を書く** ── 書かないと「英語として自然な名前」が返ってくる
- **【出力】で「1 つに絞るな」と書く** ── 書かないと却下理由が手に入らない

追い込むとき。

| 場面 | 投げる文 |
|---|---|
| **違和感を言語化できたとき** | 「この指摘は妥当か：〜だと粒度の対比に見えて、実際の〜とズレるのでは」 |
| **構造が決まったとき** | 「`1:1` に決めた。評価軸を追加する必要があるか。あるなら軸を足して全候補を付け直して」 |
| **同点で並んだとき** | 「総合点が並んだ。プロジェクトの原則に照らして、決定打を 1 つだけ挙げて」 |

| 任せてよい | 自分でやる |
|---|---|
| 候補を広く出す | **評価軸を決める・点検する** |
| 軸ごとに点と根拠を書く | **違和感を言語化して投げる** |
| 却下理由を文章にする | **同点の解消（決定打を選ぶ）** |
| 表に整形する | **最終決定** |

## 7：概念を配る

**段階 5 でエンティティと判定したものを、アクター（＝コンテキスト）に割り当てる。**

```
段階 1  人 → 概念（演繹して見つける）
段階 7  概念 → 人（確定した一覧を配る）   ← 方向が逆
```

境界は**アクターの利用範囲がそのまま**なので、ここで引き直すことはない。**やるのは割り当てと、はみ出しの発見。**

### やること

- [ ] 概念を 1 つずつ、**誰のものか**決める
- [ ] 同時に **3 分類**する（追加する / 既存で足りる / 既存から動かす）
- [ ] **配れない行**を拾う ← ここが成果
- [ ] コンテキストを**増やしすぎていないか**見る（**原則 0**。既存に入れられないか一度考える）

### 判断基準

**誰のものか**

> **① これを消したら、誰が困るか**
> **② これを変更する権限を持つのは、誰か**

**「作った人」は持ち主ではない。** 注文を作るのは顧客だが、消えて困るのは店舗（売上の記録であり、調理の指示書）。`Order.Status` の 5 つのうち 3 つは店舗しか動かせない。

**3 分類**

| 判定 | |
|---|---|
| **既存で足りる** | **これが書けたら成果。** 何も足さなくてよいと確認した事実も成果物 |
| 追加する | 新しく作る |
| 既存から動かす | 置き場所を変える |

**配れない行 ＝ 発見**

| 埋まらない形 | 意味 | どうする |
|---|---|---|
| **2 人の列に同じ概念** | **2 つに割れる合図** | 分ける（`Product` / `CustomProduct`） |
| **5 分以上迷った** | 概念が 2 つ混ざっている | 分けると迷わなくなる |
| 1 人の所持物が極端に多い | そのアクターが 2 人に分かれていないか | アクターを疑う |

**割れ方は 2 種類ある。** 分けた後の形が違う。

| | 定義と実体 | 同じ役割を別のアクターが持つ |
|---|---|---|
| 関係 | **1 対 多**（定義から生まれる） | **対応なし**（どちらも独立に作られる） |
| 相手側 | **消費される**（`expiredAt` / `usedAt` を持つ） | 相手も**マスタ** |
| 例 | `Coupon` → `CustomerCoupon` | `Product` ↔ `CustomProduct` |
| **分けた後** | 子が親を `Id` で 1 本参照 | **使う側が `Option` を 2 本持つ** |

### 落とし穴

| やりがち | 正しくは |
|---|---|
| 既存で足りるのに新しく作る | **一番多い失敗。** 迷ったら少ないほうに倒す |
| 既存モデルにフィールドを足して済ませる | `Product` に `shopId` を足すと、**全店共通のマスタに店舗固有の行が混ざる** |
| `ownerType` のようなフラグで 1 つにまとめる | **境界が型から消える。** 実行時にフラグを見るまで分からない |
| コンテキストを増やす | **原則 0。** 増やすのは新しいアクターが立ったときだけ |
| 「作った人」を持ち主にする | **消えたら誰が困るか**で決める |

## 8：モデルの形

**形だけ書く。メソッドと検証は書かない**（実装で足す）。

**書き方の作法**（セクション区切り・コメントの粒度・`code` の振り方）は `../reference/model_templates.md`。写しが古いので、**最新の実物は `upstream/chapter-03` ブランチの `edu/{common,shop,customer}/model/`**。

### やること

- [ ] `case class` とコンパニオンオブジェクト（`Id`・区分値）を書く
- [ ] **フィールドを 1 本足すたびに、4 つの判断を通す**
- [ ] 区分値を設計する
- [ ] 3 つを添える ── **型が語っていること** / **型では守れない決めごと** / **保存されるデータの例**（パターンごとに 1 行、実際に入る値で）

### 判断基準 ── フィールドを 1 本足すたび

| 判断 | 問い | 迷ったら |
|---|---|---|
| **保存するか計算するか** | ① 後で計算し直して同じ答えが出るか　② SQL で直接使うか | 両方 No なら**計算**。マスタを見て計算した値は**保存** |
| **どこに置くか**（保存する場合） | **そのテーブルは 3 年後も残っているか** | 残らないなら**置かない**。揮発データに履歴を持たせても一緒に消える |
| **冗長な列を持つか** | ①境界の鍵 → 全行に持つ　②分割の鍵 → 全行に持つ　③単独で引く → 持ってよい　**④それ以外 → 持たない** | ①② は**後から足せない**。③ は後から足せる |
| **`enum` かテーブルか** | その値が増えたとき、**コードを書く必要があるか** | 書くなら `enum`（エンジニアが増やす）。書かないならテーブル（運用担当が増やす） |

### 判断基準 ── 区分値

| | 規約 |
|---|---|
| 名前 | **`IS_` 始まり** |
| `code` | **正が「生きている」、負が「終わった」** |
| `name` を持たせるか | **業務の人に見せる区分値なら持たせる**（`DiscountType` にはある、内部の `Status` には無い） |
| 値そのものの属性か、業務の設定値か | **設定値は `enum` に入れない。** コンパニオンオブジェクトの定数か API の設定へ |

**状態が 5 つを超えたら、2 つの役目が混ざっている合図。** `UserCoupon` が 5 状態だったのは、貯める役と使う役を 1 つでやっていたから。分けたら 2 状態 ＋ 3 状態になった。

### あわせて確認する 2 つ

| 確認 | 何を見るか |
|---|---|
| **無効な組み合わせが作れないか** | `Option` の使い方。「片方だけ `Some`」のような**型で防げない組み合わせ**が残っていないか |
| **区分値が隣のフィールドの読み方を決めていないか** | 決めているなら、**型では守れない決めごとに必ず書く**。書かないと実装者ごとに解釈が変わる |

### スナップショットを入れるときの 8 項目

**スナップショットと非正規化は形が同じで目的が逆。**「元が変わったら追随させたいか」で判別する。追随させたいなら非正規化、させたくないならスナップショット。**同じ列で両方やろうとすると必ずどちらかが壊れる。**

- [ ] **確定する瞬間はどこか**（取り消せなくなる瞬間はどこか）
- [ ] **そのテーブルは 3 年後も残っているか**（残らないなら置かない）
- [ ] **参照 ID は残してあるか**（写しは参照の代わりではない。消すと商品ごとの集計ができなくなる）
- [ ] 表示に使う値・金額に使う値を、**列として**写しているか（JSON で丸ごと写さない）
- [ ] **ルールではなく、計算した結果**を写しているか（`validDays` ではなく `expiredAt`）
- [ ] **合計だけでなく、内訳も**写しているか（内訳が無いと返金の按分ができない）
- [ ] 元が変わったら**追随させたいか**（させたいなら、それは非正規化）
- [ ] 集計で出せる値を、重複して持っていないか

### 落とし穴

| やりがち | 正しくは |
|---|---|
| **`0` で特別な意味を表す** | `validDays = 0` は「当日に期限切れ」。**「値が無い」は `Option`** |
| 「値が人によって違うから `Option`」 | **行ごとに違うのは当たり前。** `Option` は「値が**存在しない**場合がある」とき |
| フィールドを 1 本だけ型変更する | **計算式でつながるものはまとめて考える**（`validDays` を `Option` にしたら `expiresAt` も） |
| メソッドや検証を書く | **形だけ。** 実装で足す |
| 状態を増やして対応する | **役目が混ざっていないか疑う** |
| 親が子の `Id` を持つ | **多い側が少ない側を持つ。** 列に複数の値は入らない |

## 9：流す

**穴はここでしか出ない。出ないほうが疑わしい。**

所持物マップは静止画で、どこにも矛盾が無いように見える。**不整合は時間の中にしか現れない。**

### やること

- [ ] **新機能のフロー**を流す（正常系 ＋ 例外）
- [ ] **既存フロー**を流す ← 本番
- [ ] **境界をまたぐ地点**を確認する
- [ ] 穴が出たら質問リストへ → **段階 3 に戻る**
- [ ] 段階 3 の**逆算チェック**（例外 ↔ モデルの属性の対応）をやる

### 既存フローの洗い出し

**新モデルが参照している既存モデルに、もともとある流れ。** 手順は 3 つ。

```
1. 新モデルの ○○Id を全部書き出す
2. その参照先に「戻す操作」があるか見る
3. その操作が起きたとき、新モデルがどうなるか答える
```

**3 で答えられなければ、それが穴。**

| 参照している既存モデル | 見るべき既存フロー |
|---|---|
| `Order` | **キャンセル** |
| `Payment` | **決済失敗 / 返金** |
| `Customer` | **退会 / アカウント統合** |
| `Product` | **販売終了 / 値上げ** |
| `Shop` | **閉店 / 休業** |
| `Coupon` | 廃止 / 内容変更 |

**危ないのは「戻す操作」。** 進む方向は新機能のフローで見ている。穴が開くのは逆行するとき。

```
キャンセル / 返金 / 退会 / 取消 / 削除 / 失効 / 復活
```

**進むときは 1 本道でも、戻るときは分岐する。**

### 判断基準

**流すときの 3 つの問い**

| # | 問い | 答え方 |
|---|---|---|
| ① | **境界をまたぐのはどこか** | 1 点に絞れるはず（注文確定など） |
| ② | **コピーか参照か** | **またぐときはコピー。** 参照にすると**書き換え権限まで渡る** |
| ③ | **片方が消えたら、もう片方は無事か** | 無事でなければ、参照の向きが逆 |

**穴が出やすい形**

| 形 | 何が起きるか |
|---|---|
| **定期処理と単発処理が混ざる** | 定期処理は毎回拾い直すので自己修復するが、**単発処理は一度きり。そのとき対象外だった行は永久に取り残される** |
| **キャッシュの「正」が経路ごとに違う** | 原則を決めても、**全経路に適用しないと穴が残る**。決めることと適用することは別作業 |
| **業務ルールを `if` で守ろうとしている** | **触れない構造になっていないか先に見る。** 境界が正しければルールの半分は構造が守る |

### 落とし穴

| やりがち | 正しくは |
|---|---|
| 新機能のフローだけ流す | **既存フローが本番** |
| 進む方向だけ見る | **戻す操作で分岐する** |
| 穴が出ないので完了とする | **出ないほうが疑わしい** |
| 穴をその場で設計で埋める | **決まっていないだけかもしれない。** まず質問リストへ |
| 消せば綺麗になると思う | **消していいのは、消えても誰も困らないデータだけ**（失敗した決済も残す） |

## 原則

| # | 原則 | 理由 |
|---|---|---|
| ① | **迷ったら質問リストへ** | 5 分迷うのは、概念が 2 つ混ざっているから。判断力の問題ではない |
| ② | **1 周目は粗く** | 穴を見つけるのが目的。出ないほうが疑わしい |
| ③ | **作りすぎない** | 一番多い失敗が「既存で足りるのに作る」。次が「既存にフィールドを足して済ませる」 |
