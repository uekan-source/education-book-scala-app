## 分ける・置く

### 分ける軸は並列ではない。アクターが上位にある

最初は「決まりごとか起きたことか」「誰が決めるか」「行が増えるか」「変更の理由」を **並列の判定軸** として整理していた。教材の整理はそうではなかった。

> **アクター（担当者）で切ると、変更の理由とライフサイクルは自動的に揃う。**

| アクター | 変更の理由 | ライフサイクル |
|---|---|---|
| 運営者（本部） | 本部の販売方針が変わったとき | 年に数回。商品は数年生きる |
| 店舗 | 店の都合（品切れ・独自商品・日々の注文） | 注文は毎分つくられ、数十分で終わる |
| 顧客 | 本人の操作 | カートは数分〜数日。アカウントは年単位 |

運営者が触るものは運営者の都合でしか変わらないので、変更の理由がひとりでに揃う。マスタは年単位で注文は分単位なので、ライフサイクルもひとりでに揃う。

**だから手順は「3 軸を別々に検討する」ではなく、「アクターで切ってから、残り 2 つが揃っているか確認する」。** 並列に持っていると、モデルごとに 3 回判断することになる。

### アクター軸と保存期間の軸は、層が違う

ただし **保存期間の軸はアクターに吸収されない。** `Order` も `Payment` も同じ店舗の所持物なのに、片方は消えて片方は残る。

| 軸 | 何を決めるか |
|---|---|
| **アクター** | **どのコンテキストに置くか**（`common` / `shop` / `customer`） |
| **保存期間** | **コンテキストの中でどう割るか**（`Order` と `Payment`） |

アクターで置き場所が決まり、保存期間でその中の分割が決まる。**順番があるだけで、どちらも要る。**

### 所持物の判定は 2 問だけ

> **① このデータを消したら、誰が困るか。**
> **② このデータを変更する権限を持つのは、誰か。**

そして **「作った人」は持ち主ではない。** 注文を作るのは顧客だが、注文は店舗の所持物。`Order.Status` の 5 つのうち 3 つ（`IS_COOKING` / `IS_READY` / `IS_HANDED`）は店舗しか動かせない。

### アクターを立て忘れると、所持物は「存在に気づかない」

作り忘れならレビューで「あれが足りない」と指摘される。**立て忘れは誰も指摘できない。全員が同じ前提で見ているから。**

本部を立てずに設計すると、`SalesTemplate` も `Coupon` も `StampCard` も **発想自体が出てこない。** 実際、要求文に「本部」という言葉は 1 度も出てこなかった。

見落としを潰す 7 つの問いと 6 類型は `docs/reference/curriculum_06_design_patterns.md` にある。**思い出すのではなく数え上げる。**

### 「決まりごと」＝ `common` ではない

`CustomMenu` や `ExcludedProduct` は決まりごとだが `shop` にある。**店舗が決めるものだから。** 決まりごと／起きたことの軸と、誰が決めるかの軸は独立している。

### 保存期間が違うデータは、同じモデルに置かない

注文明細に単価を持たせるべきか迷い `OrderItem` に足す案を出したが、ボスの判断は「**`Payment` 側に新しいモデルを作る**」だった。

| | 性格 | 保存 |
|---|---|---|
| `Cart` / `Order` / `OrderItem` | 調理と受け渡しのための**作業データ** | 揮発性が高い |
| `Payment` / `PaymentDiscount` | **会計の記録**。重く、長期保存が要る | 残す |

**消えるモデルに、消してはいけない金額を置いてはいけない。** 「`PaymentDiscount` が `Payment` 側にあるのに、商品の内訳だけ `Order` 側にあるのは不自然」という読み方のほうが正しかった。

置き場所を決める問いは 1 つ。

> **このテーブルは、3 年後も残っているか。** 残っていないなら、そこにスナップショットを置いてはいけない。

### 掛け算で行が増える形にしない

同じ券を配布経路ごとに `Coupon` を複製すると `name` と `discount` が重複する。セットの中身を組み合わせごとに `Product` にすると、バーガー20 × サイド3 × ドリンク5 で 300 行になる。

**行が掛け算で増えそうになったら、軸を 1 つ外のモデルに出す。** 自分の設計では `requiredStampCount` を `Coupon` に置いたため、「同じ券だがキャンペーンで必要数が違う」が表せなかった。

### 分けると「どっちだったか」を後から言える

`CouponOffer` を分けないと、同じ 200 円券が友達紹介で配られたのかスタンプ交換なのか**どこにも記録されない**。経路別の集計が「面倒」ではなく「不可能」になる。

**エンティティを分けると、その分け目が記録として残る。分けないとその事実は最初から存在しない。** 「状態か履歴か」と同じ構造。

### エンティティか値オブジェクトか

単体で探す / 個別に増減する / 同じ値でも別物 — どれか 1 つでも当てはまればエンティティ。

`Cart.UseCoupon`（値オブジェクト）→ 注文確定 → `PaymentDiscount`（エンティティ）が一番分かりやすい対比。**情報はほぼ同じだが、残す記録になった瞬間に独立した行になる。**

## フィールドの持ち方

### 0 で特別な意味を表さない

`validDays = 0` で「無期限」を表す案を検討して却下した。`expiresAt = createdAt.plusDays(0)` は**配られた当日に期限切れ**を意味し、無期限の対極になるため。

`requiredStampCount = 0`（0 個で配れる）は算術的な意味と一致するので問題ない。**0 に自然な意味があるところへ別の意味を上書きすると、型からも値からも判別できなくなる。** 将来「0 日はバグだろう」と直された瞬間、無期限のつもりのクーポンに期限が生まれる。

→ 「値が無い」は `Option` で表す。

### 「値が人によって違う」と「値が無い」は別

`expiresAt` を `Option` にするか議論したとき、最初の理由が「会員ごとに誕生日が違うから」だった。これは `Option` の理由にならない。**行ごとに違う値が入るのは当たり前**で、`Option` が要るのは「値が存在しない場合がある」ときだけ。

実際に `Option` にしたのは、無期限クーポンを運用する可能性が確認できてからだった。

### 型を変えると連鎖する

`Coupon.validDays` を `Option` にしたら、`expiresAt = createdAt + validDays` という式がある以上、`UserCoupon.expiresAt` も `Option` にする必要があった。**片方だけ変えても成立しない。**

計算式でつながっているフィールドは、まとめて考える。

### 保存するか計算するかの判定

> ① 後で計算し直して同じ答えが出るか　② SQL で直接使いたいか

| 保存する | 計算する |
|---|---|
| `expiredAt`（`validDays` が変わる） | 期限切れかどうか |
| `billSubTotal`（`Product.price` が変わる） | スタンプの個数（`COUNT`） |
| `payBilledTotal`（集計に使う＝②） | 返金可能額 |

**マスタを見て計算した値は保存する。自分の行の中だけで完結する値は保存しない。** 例外は②で、同じ行で計算できても検索・集計に使うなら持つ。

### スナップショットと非正規化は、形が同じで目的が逆

どちらも「導出できる値を持つ」形をしているので混ざりやすい。

| | 非正規化 | スナップショット |
|---|---|---|
| 目的 | **速度**（JOIN を減らす） | **正しさ**（あのときを再現する） |
| 元が変わったら | **追随させる** | **追随させない**（そこが要点） |
| 消してよいか | よい（JOIN で復元できる） | **だめ**（復元できない） |

**「元が変わったら追随させたいか」で判別できる。** 同じ列で両方やろうとすると、必ずどちらかが壊れる。

そして **写しは参照の代わりではなく、参照に足すもの。** ID を消して写しだけにすると、商品ごとの集計ができなくなる（名前が変われば別商品になる）。

### 判定に使うことと、記録に残すことは別

スタンプを押す契機は受け渡し完了（`Order.state == IS_HANDED`）なので `Order` を見る必要がある。だが**見るのは押す瞬間だけ**で、押した後の記録に `orderId` は要らない。

この区別をしないと、**判定に使ったものを全部持ちたくなる。** 判定は一度きり、記録は永続、と分けて考える。

## 参照と重複

### 多い側が少ない側の Id を持つ

親は子の Id を持てない。1 枚のカードにスタンプが 10 個あっても、列には 1 つの値しか入らない。だから `CustomerStampCardItem` が `customerCardId` を持つ。

`Cart.items: Seq[BuyItem]` は例外に見えるが、`BuyItem` は `EntityModel` ではなく**独立した行にならない**ので親が抱えてよい。

### 多対多は中間に行を作る。中間が持つ属性が存在理由

`SalesTemplateMenuItem` の `sortOrder` は、商品にもタブにも属さない「**関係そのものの属性**」。配列で持つとこれを表せず、逆引き（この商品はどのタブに出ているか）もできない。

`ExcludedMenu` / `ExcludedProduct` も「使わない」という関係の中間テーブル。

### 長く残るモデルは、短命なモデルを参照できない

`CustomerStampCardItem` が `orderId` ではなく `paymentId` を持つのはこのため。スタンプの記録は長期保存だが `Order` は消えるので、`orderId` を持つと **Id だけ残って辿れなくなる。**

保存期間の軸は、置き場所だけでなく**参照の向きまで縛る。**

### 導出できる値をあえて持つことがある

`UserCouponStamp.userId` は親の `UserCoupon.userId` から辿れるので、正規化の理屈では不要。それでも持たせた。障害調査で「この会員に何が起きたか」を横断的に引くとき、JOIN が必須だと初動が遅れるため。

**正規化の理屈と、運用上の引きやすさは別の軸で判断する。** ただし非正規化する以上、ズレない保証（作成時にコピーし、以後どちらも変わらない）を明記する。

これは「引きやすさ」の理由で持たせた例。**別の理由で持たせる列もある** → [冗長に見える列が、アクセス境界の鍵になっていることがある](#冗長に見える列がアクセス境界の鍵になっていることがある)

### 更新されない重複は、二重管理にならない

判定は「**その値、後から更新されるか**」の 1 問だけ。

- `CustomerStampCardItem.customerId` … カードの持ち主は変わらない → コピーしてよい
- `Coupon` を経路ごとに複製した場合の `name` / `discount` … 変わりうる → ダメ

重複そのものが害なのではなく、**同期を取り続けなければいけないこと**が害。

### 一番危ない重複は「同じものである」情報が消えること

`Coupon` を春用・秋用に 2 行作ると、DB 上は**完全に無関係な 2 件**になる。名前が同じなのは偶然にすぎない。

集計のたびに `WHERE coupon_id IN (1, 2)` と手で列挙することになり、**3 件目が増えたとき誰も気づけない。** エラーも出ない。

## 状態と区分値

### 区分値と状態は別物（包含関係）

```
区分値（決まった値の集合から選ぶ列）
 ├─ 状態    … 時間とともに変わる。遷移のルールがある
 └─ それ以外 … 分類するだけ。基本変わらない（性別、支払方法など）
```

状態には遷移・終端・同時実行・キャッシュのズレという論点が付いてくる。ただの分類には付いてこない。**新しい列を足すとき、どちらかを最初に判定すると必要な作業量が変わる。**

### 状態が長くなったら、2 つの役目が混ざっている

自分の `UserCoupon` は 5 状態（`IS_COLLECTING` → `IS_AVAILABLE` → `IS_USED` / `IS_EXPIRED` / `IS_INVALIDATED`）。雛形は貯める役と使う役を分けたので **2 状態＋3 状態**で済んでいる。

さらに `IS_EXPIRED` は日付判定に置き換えて消えている。**状態の数は、モデルの分け方の結果として出てくる。**

### 状態が 2 箇所にあっても、両方見る規則なら矛盾しない

`Coupon.state`（券の廃止）と `CouponOffer.state`（経路の停止）は別のものを止めている。`IS_ARCHIVE` × `IS_OPEN` は矛盾ではなく「券が死んでいるので配らない」という有効な状態。

**上位が死んでいたら下位が何でも無効**、という規則があれば、後始末が漏れても安全側に倒れる。ただし復活させるときは下位を個別に開き直す（**止めるのは 1 操作でよいが、戻すのは 1 操作にしてはいけない**）。


### 「作る操作」と「消費する操作」でタイミングが逆になる

これが一番手こずった。

| | スタンプ付与 | クーポン使用 |
|---|---|---|
| 操作の性質 | 行を 1 本足すだけ | 1 枚しかない権利を消費する |
| 早く確定させると | 困る（キャンセルで取り消しが要る） | **助かる**（二重使用を防げる） |
| 遅く確定させると | 助かる | **困る**（二重使用が起きる） |

同じ業務フローの中でも、**揃えたくなるが揃えてはいけない**。付与は受け渡し完了、使用は注文確定と、逆の時点になった。

### キャッシュを持つなら「正」を決め、全経路に適用する

`state` と `expiresAt` の二重管理で「正は `expiresAt`」と決めたのは正しかった。しかし**その原則を使用時にしか適用していなかった**。付与処理は `state` だけを見ていたため、バッチ実行前に期限切れカードへスタンプが載る穴が残った。

**原則を決めることと、原則を全経路に適用することは別作業。** 前者だけで満足しやすい。

### 定期処理と単発処理を混ぜると、単発側に穴が開く

期限切れは日次バッチが毎日拾い直すので自己修復する。対象メニューの販売終了は一度きりの処理なので、そのとき対象外だった行は**永久に取り残される**。

この非対称に気づかず、「使用済みのクーポンがキャンセルで復活すると、販売終了した商品のクーポンが使える状態に戻る」という穴を作った。

### `enum` にするかテーブルにするか

> **その値が増えたとき、コードを書く必要があるか。**

- **ある** → `enum`。`DiscountType` に `IS_PERCENT` を足せば計算式を書く
- **ない** → テーブル。`SalesTemplate` が 1 つ増えてもコードは 1 行も変わらない

言い換えると **`enum` はエンジニアが増やすもの、テーブルは運用担当が増やすもの。** `enum` にすると廃止もできない（値を消すと既存レコードが読めなくなる）。

### 区分値が、隣のフィールドの読み方を決める

雛形で 3 回出てきた形。

```
discountType → discountValue の単位が変わる
IssueType    → promoLimit が「配布上限」か「利用上限」かが変わる
rule         → 対になる値（何円で 1 個か）が必要になる
```

**型では守れないので、必ず文章で書く。** 書かないと実装者ごとに解釈が変わる。

### 変更が稀な値は、フィールドではなく定数に置く

`StampCard.rule` に「何円で 1 個か」のフィールドが無い点を穴だと思ったが、ボスの判断は「**関数か定数で計算すればいい。そこまで変わる情報ではない**」だった。

置き場所は **`enum` の中ではなく、コンパニオンオブジェクトの定数か、API 側の設定**。

```scala
object StampCard:

  // --[ Constants ]---------------------------------------------------
  /** 会計金額ルールで、スタンプ 1 個あたりの金額 */
  val PaymentAmountUnit: Int = 500

  enum Rule(val code: Short, val name: String) extends EnumStatus[Short]:
    case IS_PAYMENT_COUNT  extends Rule(code = 1, name = "会計回数")
    case IS_PAYMENT_AMOUNT extends Rule(code = 2, name = "会計金額")
```

**`enum` が持っていいのは区分値そのものの属性まで。** `code` は DB に入る値、`name` はその表示名で、どちらも「その区分が何か」を説明している。`unit`（何円で 1 個か）は**業務の設定値**であって区分の説明ではない。

混ぜると **金額を変えるたびに区分値の定義行を書き換える**ことになる。区分値の定義は本来安定しているべき場所なので、変更の理由が違うものを同居させない。

代償は 2 つ。**台帳ごとに単位を変えられない**ことと、**変更後に過去がどの基準で押されたか再現できない**こと。どちらも「今はそうならない」前提の上に成立しているので、**判断が変わる条件として書いておく。**

## 制約の担保

### 宣言しただけでは守られない

同じ文書の中に、こう混在していた。

| 制約 | 記述 |
|---|---|
| `usedOrderId` は一意 | 「一意」と明記 |
| 配布中マスタは 1 つ | 「運用で担保する」と明記 |
| **貯め中は会員あたり 1 枚** | **記述なし** |

最も壊れやすいものが空欄だった。制約を書くときは、**何で守るか（型 / DB制約 / 運用）をセットで決める。**

判断基準は更新頻度と操作主体。本部が年に数回触るものは運用で足りるが、会員の操作で毎日大量に発生するものは機械的な担保が要る。

### 一意制約が何を守るのか、言葉で言えるか

`usedOrderId` の一意制約は「**1 つの注文が 2 枚のクーポンを使う**」ことを防ぐ。「1 枚のクーポンが 2 つの注文に使われる」ことは防がない（同じ行を上書きするだけで値が衝突しない）。

これを取り違えて「一意制約が守ってくれる」と書いていた。**制約の向きを説明できないうちは、それに頼ってはいけない。**


### 冗長に見える列が、アクセス境界の鍵になっていることがある

`shopId` が `Shop` 以外の全 10 モデルにある。`paymentId` を辿れば店舗は分かるので、正規化の理屈では重複。**自分は「店舗別集計のため」と読んでいたが、本命は別だった。**

> **アクセス境界の条件は 1 行ごとに評価される。だから「その表の列」だけで書けなければならない。**

```sql
-- 書ける：その行だけを見て判定できる
shop_id = 42

-- 書けない：他の表をたどらないと判定できない
（payment_id から shop_payment を引いて、その shop_id と比べる）
```

行レベルセキュリティも、ORM の既定スコープも、スコープ付きリポジトリも、全部この前提の上に成り立っている。**境界の鍵が行に載っていなければ、どの仕組みにも載せられない。**

`WHERE shop_id = 42` を書き忘れたクエリはエラーにならず、**全店舗の行を返す。** 99 本正しくても 1 本漏れれば漏洩する。だから「気をつける」ではなく「基盤が必ず足す」に移す。

そして **後から足せない。** MySQL のパーティションキーは主キーとすべての一意キーに含まれている必要があるので、後付けは主キーの張り替えになる。

判断の順序はこうなる。上から見て、最初に当たったところで決める。

| | 判定 | 結論 |
|---|---|---|
| ① | **アクセス境界の鍵か**（この行を見てよい人を決める列） | **全行に持つ。例外を作らない** |
| ② | **物理分割の鍵になりうるか** | **全行に持つ。**使わずに終わってもよい |
| ③ | 障害対応や集計で、その表を単独で引くか | 持ってよい。理由をコメントに残す |
| ④ | 上のどれでもない | **持たない** |

**自分は ③ だと思っていたが、実際は ① だった。③ は後から足せるが、① は足せない。** 同じ「冗長な列」でも、境界の鍵と便利のための近道では重みが違う。

実際 `customerId` は `Payment` までで止まっていて、`PaymentItem` / `PaymentDiscount` には無い。**全部に付けているわけではない。**

## 処理の置き場所

### モデルに連鎖は書かれない。書かれなくて正しい

「10 個貯まったらクーポンを発行する」という動きは、モデルのどこにも無い。`case class` はデータの形しか表さない。**モデルをいくら読んでも連鎖は見えない。**

実際に動くのは、支払い完了をきっかけに 3 つのテーブルへ書き込む処理（`CustomerStampCardItem` を INSERT → 件数を数える → `CustomerCoupon` を INSERT ＋ `CustomerStampCard` を UPDATE）。**設計文書に決めごとを書いておけば、その処理を書ける**という関係になっている。

### `extension` に置けるのは、渡された値と `self` だけで終わるもの

```scala
def isCollectingOn(date: LocalDate, ledger: StampCard): Boolean
```

`ledger` を**引数で受け取っている**のがポイント。DB を引く・外部サービスを呼ぶ処理は置けない。

### 作るときの計算はファクトリメソッド

`UserPassword.hashed(uid, password)` が実例。**呼ぶ側は計算式を知らない。** `expiredAt = 発行日 + validDays` や `Payment` の税計算も同じ形になる。

`object` の中に `// --[ Factory Methods ]---` のセクションを作る。

### このリポジトリにはサービス層が無い

`app-api/app/controllers/` が `repos` を直接呼ぶ構成（`SignupController` 参照）。**流れはコントローラ、計算はモデル。**

```
コントローラ  引いて・呼んで・保存する流れ
モデル        渡された値だけで完結する計算
リポジトリ    DB アクセス
```

「API に計算を書く」のではなく、**API には流れを書き、計算はモデルに置いて呼ぶ。**

### モデル上できることと、運用上やっていいことは別

表示時間を分けたいとき `SalesTemplateMenu` を 1 行足せば解決する。だが **1 行が画面のタブ 1 枚に直結している**ので、会員から見ればタブが増える。

**データ整理の都合で、表示単位を増やしてはいけない。** こういうのは型で守れないので設計文書に書く。

## 要件を聞くとき

### 質問が片側に偏る

前述の通り、5 つの質問のうち 4 つが会員側だった。本部側のライフサイクル（いつ配る、いつ止める、後から変更できるか）を問う質問が無く、設計が固まった後の手戻りになった。

### 「判断が変わる条件」を書いておくと後で効く

論点に「こういう要件が来たらここを変える」と先回りして書いておいたおかげで、「サマースタンプを実装するとしたら何を変えるか」という質問に即答できた。

書いた時点では何の役にも立たない情報だが、後から効く。

## 文書を直すとき

### 修正は新たな矛盾を生む

相互参照が密な文書では、1 箇所直すと別の箇所と噛み合わなくなる。実際、**修正 → 確認を 6 ラウンド繰り返した**。

- 1 回目: 設計の穴（トランザクション範囲、二重使用の機構）
- 2 回目: 波及漏れ（同じ決定を書いている箇所の取り残し）
- 3 回目: さらに波及
- 6 回目: 0 件

**直したら必ず確認する。** 特に自分が直した箇所ほど確認する。

### 例外を積み上げる直し方は波及を生む

「A は変更不可。ただし B は例外。さらに C の場合は A も例外」と例外を足していったら、4 ラウンド目・5 ラウンド目にも新しい矛盾が出た。

ルールの立て方を `state` 基準の表に組み替えたところで収束した。

| `state` | 変更できるもの | 理由 |
|---|---|---|
| 準備中 | すべての条件 | まだ 1 枚も配られていない |
| 配布中 | `distEndAt` のみ | 配られた分が確定済み |
| 配布終了 | なし | 変えても何も起きない |

**矛盾が繰り返し出るのは、ルールの切り分け方が間違っているサイン。**

### 件数を明記すると、新しい矛盾源になる

「削除の経路は 3 つある」と書いた瞬間、4 つ目を見落とした矛盾になった。「〜など」と曖昧に書いてあれば矛盾しなかった。

**正確さを上げると、正確さを保つコストも上がる。**

### 図の中の参照も一緒に直す

章構成を再編したとき、マークダウンの相互参照は全部直したが、**SVG の中に埋め込んだ章番号を忘れた**。図は別ファイルなので、grep の対象から外れやすい。

### レビューは「指摘」と「検証」を分ける

指摘をそのまま受け入れず、反証を試みる工程を挟む。実際、挙がった指摘のうち**修正が必要だったのは 1 割強**だった。残りは誤読か、既に別の箇所で解決済みか、過剰な要求だった。

一方で、複数のデータ例を時系列で突き合わせて初めて見える矛盾（作成日を逆算すると不変条件に反する）は、検証工程がないと見つからなかった。
