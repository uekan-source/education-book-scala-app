# 成果物の書き方

**`01` / `02` / `03` に、それぞれ何を書くか。** 手順（何をどの順でやるか）は [`design_procedure.md`](./design_procedure.md)。

| ファイル | 何が書いてあるか |
|---|---|
| [`design_procedure.md`](./design_procedure.md) | **手順**（何を、どの順で） |
| **この文書** | **成果物の書き方**（`01`/`02`/`03` に何を書くか） |
| [`design_lessons.md`](./design_lessons.md) | **原則**（なぜそうするか） |
| [`../reference/`](../reference/README.md) | **原典**（教材の写し） |

```
01_requirements.md   何を作るか。どう作るかは書かない
02_analysis.md       思考過程。提出しない
03_design.md         最終的な設計。これを見せる
```

**`02` は書き換えない。** その時点でどう考えたかの記録なので、後の変更を反映すると価値が失われる。

## 分量の目安

| | 記入例 | 目安 |
|---|---|---|
| **新しいエンティティ** | 2 個 | **0〜3 個** |
| **新しいコンテキスト** | 0 個 | **原則 0** |
| **判断の記録** | 5 件 | **3〜5 件**（1 件 ＝ 判断 1 行 ＋ 理由 3〜6 行） |
| **業務フローの例外** | 4 行 | **3 行以上** |

全体で **3 ファイル合わせて A4 2〜3 ページ。**

書き忘れやすいのは 3 つ。**「対象外」にした名詞**（0 件なら仕分けをしていない）、**「既存で足りるもの」**、**「今回やらないこと」**。

## いくつ作るかで迷ったとき

**判断の問いは [`design_procedure.md`](./design_procedure.md) 段階 5。** ここには分量の目安だけ置く。

> **足りないより、増やしすぎのほうが直しにくい。迷ったら少ないほうに倒す。**

## この研修の中心にある考え方

**エンティティモデルがやり直しの効かない要である。**

コードは書き直せるが、データは書き直せない。正確には、構造の移行はできても、**存在しなかった情報は復元できない**。スタンプカードの設計では次の実例が出た。

- スタンプを独立したエンティティにしていたら、「このスタンプはどのカードに属すべきだったか」は最初から存在しないので、後から親子関係にしても復元できない
- 付与日時を持たずに `createdAt` で兼ねると、過去データを一括登録したときに配られた日時が失われる

処理（バッチ、手順、計算）は間違えてもコードを直せば済む。**この非対称性があるので、モデルに時間を使う。**

裏を返すと、モデルと「型では守れない決めごと」が正確に書かれていれば、その先はかなり機械的に導ける。

## 01_requirements.md — 要件定義

### 書くもの

| 節 | 内容 |
|---|---|
| 受け取った要求 | 依頼文をそのまま引用する。書き換えない |
| **前提** | **要求文に無いが、聞かないと設計が決まらないもの**（次節） |
| 確認したいこと（質問リスト） | 曖昧な点を質問と回答の対で残す |
| 業務フロー | **アクターを先に立ててから**、業務のまとまりごとに番号を振って並べる |
| 例外・ルール | フローに書けない業務ルール |

**業務フローはアクターより後。** 先にフローを書くと、書いたフローの主語しか登場しない。

02 章のフロー例は会員 1 人分だけで、**本部が主語の行が 1 行も無かった。** その結果、販売テンプレートもクーポンの配り方も概念として出てこなかった。

```
[本部]
1. 商品を登録する
2. メニュー構成を組む          ← SalesTemplate
3. 店舗に配る                  ← Shop.templateId
```

**「店舗に配る」と書けば、配られる何かが要る。** 書かなかったから拾えなかった。

本数は業務のまとまりで決まる（1 本に 2 人以上登場してよい）。チェックはこれ。

> **すべてのアクターが、どこかのフローで「主語」になっているか。**

所持物が 0 のアクターも書く。決済サービスのフローを書かないと `IS_PENDING` / `IS_FAILED` が出ないし、分析のフローを書かないと**どのデータを消してよいかが決まらない。**

### 質問の書き方

**中立に聞かない。設計案を提示して合意を取る。**

```
悪い： 有効期限はどう数えますか
良い： 有効期限は「スタンプ 1 個ごと」ではなく「貯めているカード 1 枚ごと」に
      持たせたい。1 個目のスタンプが押された日から数えて 1 年、という理解でよいか
```

こう書くと、相手は「はい／いいえ」で答えられる。判断を相手に丸投げせず、こちらが考えた上で確認する形にする。

### 質問が漏れやすいところ

スタンプカードの設計では、5 つの質問のうち 4 つが会員側（スタンプの数え方、期限、枚数）に寄っていた。**本部側の質問が「登録できるようにするか」の 1 つだけ**だったため、次が漏れた。

- いつからいつまで配るのか（配布期間）
- 登録した後に条件を変更できるのか
- 配った後に期限を切らない運用はあるか

この 3 つは設計が固まった後に指摘され、大きな手戻りになった。

**対策：** 「誰が触るか」を軸に質問を並べて、片側に偏っていないか確認する。設計の最後にやる「触る人と頻度」の表を、**質問リストを作る段階で先にやる**とよい。

これは**アクターを先に立てろ**ということ。**質問リストを作る前に 1 周しておく。** → [`design_procedure.md`](./design_procedure.md) 段階 1

### 「前提」は質問リストの外に出す

> ⚠️ **「前提」節はカリキュラムに無い。** 教材の `01` は「受け取った要求 / 確認したいこと / 業務フロー」の 3 節だけ。**これは自分で足したもの。**

質問リストに混ぜない。**回答が返ってきた後の性質が違う。**

| | 回答後 |
|---|---|
| **前提** | **設計の前提条件**として、ずっと参照される |
| 個別の質問 | 解消したら役目が終わる |

混ぜると、20 個の質問の中に「規模：300 店舗」が埋もれる。**設計全体を規定する値なので独立させる。**

**空欄にしない。** 聞いていないのか、該当しないのかが分からなくなる。6 類型で「いない」と明記するのと同じ。

```
- 想定規模：**未確認**（次回 MTG で聞く）
- 法規制・監査：該当なし（個人情報を扱わないため）
```

**「未確認」と書いてあれば MTG の持ち物になる。** 空欄だと誰も気づかない。

何を書くかは [`design_procedure.md`](./design_procedure.md) 段階 2。

## 02_analysis.md — 思考過程

提出しない。当時どう考えたかの記録なので、後から変更を反映しない。

| 節 | 内容 | 段階 |
|---|---|---|
| **アクター洗い出し** | **7 つの問い / 6 類型 / 所持物 / はみ出し** | 1 |
| 名詞と動詞 | 要求文から機械的に拾う | 4 |
| 動詞の仕分け | 「状態を変える（書き込む）」と「値を返す（読むだけ）」に分ける | 4 |
| 名詞のふるい分け | エンティティ / 値オブジェクト / 属性 / 対象外に分ける | 5 |
| ユビキタス言語 | エンティティの日本語名と英語名 | 6 |
| 命名の評価 | 候補を軸ごとに採点する。**採用しない案と却下理由も残す** | 6 |
| **概念を配る** | どのコンテキストか ＋ **追加する / 既存で足りる / 既存から動かす** | 7 |

**段階の中身は [`design_procedure.md`](./design_procedure.md)。** ここは「何を `02` に残すか」だけ。

**アクター洗い出しは `02` に残す。** 前提（規模・保存期間など）は `01`、**思考過程はこちら**。

### ふるい分けのコツ

**業務に言葉があっても、モデルにするとは限らない。**

- 「カード」と「クーポン」は業務では呼び分けるが、同じモデルの状態違いだった
- 「あと何個か」は計算できるので保存しない
- 「本部」は操作する人だが、誰が登録したかを記録しないのでモデルに現れない

## 03_design.md — 設計

### 構成

```
リード文（対象・前提・追加するエンティティの表）
1. 用語 — 全体の用語集に追加する呼称
2. ER 図
3. EntityModel（エンティティごと）
4. 区分値の考え方
5. エンティティをまたぐルール（あれば。無ければ節ごと省く）
6. 置き場所（コンテキスト）— 判断 / 理由
---
付録A 今回やらないこと
付録B 判断の記録
```

### 用語の表

「何と呼ぶか」だけでなく**「何と呼ばないか」**を決める。これを書かないと次の会議で言い換えが起きる。

| 呼称 | 何を指すか | 言い換えない |
|---|---|---|
| クーポン | 本部が登録するクーポンの種類 | クーポンマスタ、テンプレート |

### EntityModel

`case class` とコンパニオンオブジェクト（Id・区分値）まで書く。**形だけを書き、メソッドや検証は書かない。**

そのうえで 3 つを添える。

1. **ここで型が語っていること** — 必須か任意かを型がどう表しているか
2. **型では守れない決めごと** — 一意制約、属性どうしの連動、運用ルール
3. **保存されるデータの例** — パターンごとに 1 行、実際に入る値で

### 付録B 判断の記録

論点ごとに「判断 / 理由 3〜6 行 / 代償 / 判断が変わる条件」。

**迷わなかったことは書かない。** 本文に結論も理由も書いてあるものは、論点にしない。論点の固有価値は**採らなかった案とその理由**にある。

「判断が変わる条件」は書いた時点では役に立たないが、後から要件が増えたときに「どこを変えればいいか」が即座に分かる。
