# 問題1：スタンプカード（ポイント） — 思考過程（メモ・提出しない）

## 名詞と動詞

**名詞**：
会員、店舗、注文、注文明細、支払い、スタンプ、付与日、スタンプ数（保有数）、有効なスタンプ、失効したスタンプ、有効期限、クーポン、無料特典（ハンバーガー1つ無料）、キャンセル、専用画面

**動詞**：
ログインする、確認する、支払う、キャンセルする、選ぶ、
スタンプを付与する、スタンプを取り消す、クーポンを発行する、クーポンを使用する、
数え上げる、除外する、失効する、判定する

動詞を 2 つに分けます。

| 種類 | 動詞 | 行き先 |
|---|---|---|
| **状態を変える** | スタンプを付与する | スタンプを **1 行足す**（新しい状態遷移は増えない） |
| **状態を変える** | クーポンを発行する | クーポンを **1 行足す**（新しい状態遷移は増えない） |
| **状態を変える** | スタンプにクーポンを紐付ける | 消費の事実として、スタンプに **クーポンへの参照を書く**（一度書いたら戻さない） |
| **状態を変える** | クーポンを使用する | **未使用 → 使用済み の状態遷移**（今回唯一の遷移） |
| **状態を変える** | スタンプを取り消す | キャンセル時。付与済みスタンプを無効化する |
| **値を返す** | 有効なスタンプ数を数え上げる | モデルのメソッド。保存しない |
| **値を返す** | そのスタンプが失効しているか判定する | モデルのメソッド。付与日と現在日時から算出 |
| **値を返す** | 使えるクーポンがあるか判定する | モデルのメソッド |

## ここで気づいたこと（③に持っていく）

**1. 「消費済み」という名詞が消えた**

紐付け方式にしたことで、「消費済みフラグ」という独立した概念は不要になりました。**クーポンへの参照が入っていれば消費済み、空なら未消費**と読めるためです。フラグと参照の二重管理が起きません。

**2. 状態遷移が 1 つだけ現れた**

参考例（営業時間）では状態遷移がゼロでしたが、今回は「**クーポンを使用する**」だけが未使用 → 使用済みの遷移になります。スタンプ側は行を足すだけなので遷移を持ちません。**スタンプとクーポンで性質が違う**、というのが今回の発見です。

**3. 「失効する」は誰も操作していない**

動詞の形をしていますが、時間が経つだけで勝手にそうなります。「状態を変える」列に入れられず、判定（値を返す）側に落ちました。**これが次のふるい分けで「有効期限は対象外＝計算結果」になる根拠**です。

## ふるい分け

| 名詞 | 仕分け | 理由 |
|---|---|---|
| 会員 | **既存エンティティ**（`User`） | 雛形をそのまま使う。新しく作らない |
| 店舗 | **既存エンティティ**（`Shop`） | 新しく作らない |
| 注文 | **既存エンティティ**（`Order`） | スタンプを押すきっかけ。参照するだけ |
| 注文明細（`OrderItem`） | **既存エンティティ** | 無料対象の商品を特定するのに使う。持ち方は変わらない |
| 支払い | **既存エンティティ** | 付与のタイミング（支払い確定）を知るのに使う |
| スタンプ | **エンティティ（新規）** | 1 個ずつ識別する。どの注文で押されたか、どのクーポンに消費されたかを追跡し、古い順に 10 個選ぶ（FIFO）必要がある |
| クーポン | **エンティティ（新規）** | 発行される・未使用/使用済みの遷移を持つ・未使用のまま複数枚持てる |
| 付与日 | 属性 | スタンプの列。**唯一保存する事実**で、失効判定の根拠になる |
| スタンプ数（保有数） | **対象外（＝計算結果）** | 保存しない。有効なスタンプの行を都度数え上げる |
| 有効なスタンプ / 失効したスタンプ | **対象外（＝計算結果）** | 保存しない。付与日と現在日時から判定する |
| 有効期限 | **対象外（＝計算結果）** | 保存しない。付与日 + 1 年で算出する。列を作らない |
| 無料特典 | **対象外** | クーポン 1 枚 = ハンバーガー 1 つ無料と固定。特典の種類を管理しない |
| キャンセル | **既存**（`Order` のステータス） | 注文のキャンセル自体は `sales` に既にある概念。新設しない |
| 専用画面 | **対象外** | 画面の話であり、業務の概念ではない |

### ふるい分けで確認したこと

- **新規に作るのは `スタンプ` と `クーポン` の 2 つだけ**に収まった
- **値オブジェクトは 0 件。** 有効期限は保存しないため対象外に落ち、時刻や日付は属性で足りる
- **対象外が 5 件**（うち 3 件は計算結果）。拾った名詞を全部エンティティに昇格させていない
- **有効期限を対象外にしたのが今回の要点。** ここを値オブジェクトにすると `expires_at` 列を作りたくなり、付与日との二重管理が生まれる

## 多重度の整理

**名前を決める前に、構造（多重度）を固める。**

| 関係 | 多重度 | 補足 |
|---|---|---|
| 会員 ↔ スタンプ | `1:*` | 1 人が何個も持つ |
| 注文 ↔ スタンプ | `1:1` | 注文 1 回につき 1 個 |
| 会員 ↔ クーポン | `1:*` | 未使用のまま複数枚持てる（発行上限なし） |
| クーポン ↔ スタンプ | `1:10` | 消費された 10 個が紐づく。スタンプ側がクーポンへの参照を持つ |
| 注文 ↔ クーポン | `1:0..1` | 1 注文でクーポン 1 枚使用。使わないこともある |

スタンプもクーポンも会員に対して `1:*`。どちらも集合として扱うため、単数形の 1 レコード = 会員の全体像、という名前にはできない。

## ユビキタス言語（候補）

| 日本語 | 英語名 | 意味 | 多重度・備考 |
|---|---|---|---|
| スタンプ | `Stamp` | 注文 1 回につき 1 個押される、貯める単位の 1 個分 | `User` と `1:*`、`Order` と `1:1`。**行を足すだけ**で、数は保存しない |
| 付与日 | `grantedAt` | そのスタンプが押された日付 | `Stamp` の属性。**唯一保存する事実**。失効判定の根拠 |
| スタンプの取り消し | `canceledAt` | 注文キャンセルによりスタンプが無効になった記録 | `Stamp` の属性。行は消さず履歴として残す。真偽値ではなく日時にして、いつ取り消されたかも残す |
| 無料クーポン | `StampCoupon` | スタンプ 10 個と引き換えに発行される、ハンバーガー 1 つ無料の権利 | `User` と `1:*`、`Stamp` と `1:10`、`Order` と `1:0..1` |
| クーポンの利用状態 | `StampCoupon.Status`<br>（`UNUSED` / `USED`） | 未使用か使用済みか | **今回唯一の状態遷移**。enum で持つ |
| （有効期限） | — | — | **名前を付けない。** 保存しないため。`grantedAt` + 1 年で都度計算 |
| （スタンプ数） | — | — | **名前を付けない。** 有効な `Stamp` の行を数え上げた結果 |

> 既存の `User` / `Order` / `Payment` は再掲しない。

## 名前を並べて確認する

`sales` コンテキストの既存の名前に混ぜて、名前順に並べる。

```
Cart                 ← 既存
CartItem             ← 既存
CartItemOption       ← 既存
Order                ← 既存
OrderItem            ← 既存
OrderItemOption      ← 既存
Payment              ← 既存
Stamp                ← 今回追加
StampCoupon          ← 今回追加
```

```
sales_cart                ← 既存
sales_cart_item           ← 既存
sales_cart_item_option    ← 既存
sales_order               ← 既存
sales_order_item          ← 既存
sales_order_item_option   ← 既存
sales_payment             ← 既存
sales_stamp               ← 今回追加
sales_stamp_coupon        ← 今回追加
```

見るポイント：

- **`Stamp*` の 2 つが隣り合っている。** スタンプまわりを直したい人が、名前順の一覧から 2 つを同時に見つけられる
- **既存の `cart_*` / `order_*` 一族と喧嘩せず、末尾に固まっている**
- テーブル名は **コンテキストのパスを頭に付けて `sales_stamp`**。マージするのは `Shop` / `shop` のようにエンティティ名がコンテキスト名で始まる場合だけで、`Stamp` は該当しない

### 却下した案

| 案 | 却下理由 |
|---|---|
| `UserStamp` / `UserStampCoupon` | `User*` 一族に加わり「会員に属するもの」と読めるのは利点。ただし 3 語は冗長。**判断が変わる条件**：店舗独自スタンプなど会員以外に紐づくスタンプが将来登場するなら、この案が勝つ |
| `LoyaltyStamp` / `LoyaltyCoupon` | `Loyalty` は**業務の人が使わない言葉**。発注者は「スタンプ」と言っている。ユビキタス言語として失格 |
| `Coupon`（接頭辞なし） | 将来キャンペーン等で別種のクーポンが来たときに衝突する。`Stamp` 由来であることを名前に残す |

### 対比の軸について

`Stamp` と `StampCoupon` の実際の対比は「**貯めるもの**」と「**引き換えて使うもの**」。前者は行が増えるだけ、後者は未使用 → 使用済みの状態遷移を持つ、という性質の違いがある。`StampCoupon` という名前には「スタンプから生まれた」という**由来**が入っており、これは保持したい情報。

## コンテキストの判断

| 日常的に書き換える人 | 何を書き換えるか | 更新の頻度 | 見る画面 |
|---|---|---|---|
| **会員**（注文することで、システムが） | スタンプの行が 1 本増える | 注文のたび（毎日・大量） | 会員アプリのスタンプ専用画面 |
| **会員** | クーポンを未使用 → 使用済みにする | 10 注文ごと | 注文画面 |

**判断：既存の `sales` コンテキストに入れる。**

**理由：** 日常的に書き換えるのは**会員の注文行為**であり、`Order` と**触る人・更新頻度・書き換わるトリガー（支払い確定）が一致する**。スタンプを押すきっかけが注文だから、ではなく、**日々書き換える主体が `Order` と同じだから** `sales` に置く。

### `common` に置けないか

| 条件 | 判定 | 理由 |
|---|---|---|
| 1. 業務の操作では変わらない | ✗ | **注文（業務操作）のたびに行が増える。** マスタではない |
| 2. 管理者が別にいる | ✗ | 店長や管理者が編集しない。会員の行為で自動的に変わる |
| 3. 他のコンテキストから参照されるだけ | ✗ | `User.Id` と `Order.Id` を**参照する側**。逆流が生まれる |

**3 条件すべてで落ちる。** 「ポイントはマスタっぽい」という直感はここで否定される。営業時間が条件 3 だけで落ちたのに対し、スタンプは 1 つも満たさない。

### 新しいコンテキストを作らないか

`loyalty` のような新コンテキストも考えられるが、作らない。

- **新設の根拠**：専用画面で見る／店舗をまたいで共通／`Order` より寿命が長い（1 年）
- **払うコスト**：パッケージ・`Module`・`RepositoryFacade`・`app-api` の配線が 1 セット増える。スタンプ画面を 1 つ描くのに `sales` と新コンテキストの 2 つのリポジトリを呼んで自分で組み立てることになる
- **決め手**：触る人が会員で、`Order` と同じ。**分ける理由がない**

**コンテキストは 4 つのまま、増えない。**
