# 店舗スタッフ向けの調理管理 — 詳細要件定義

対象：店舗タブレットでの調理管理 ／ 前提：[要件定義](./p2_01_REQUIREMENTS.md)で合意済み

## 1. 概要

店舗のタブレットで、その店舗に入った注文を一覧し、状態を進めていけるようにする。受け取りに来なかった注文を「未受け取り」として片付けられるようにし、材料が切れた商品をその場で売り切れにできるようにする。

新しいエンティティは作らない。既存エンティティに列も足さない。変更は `Order.Status` に値を 1 つ追加するだけ。

## 2. 用語

全体の用語集への追加を申請する。

| 呼称 | 何を指すか | 言い換えない |
|---|---|---|
| 未受け取り | 受取準備完了のまま閉店を迎え、会員が受け取りに来なかった注文 | キャンセル、破棄、放置、無効 |

要求文と既存の呼称が食い違っていたため、既存側にそろえる。

| 業務で使われている言葉 | 統一後の呼称 |
|---|---|
| できあがり | **受取準備完了** |
| 調理中ボタンを押す | **調理を開始する** |

タブレットのボタンのラベルは「できあがり」でよい。仕様書・コード・会話では「受取準備完了」に統一する。

「未受け取り」と「キャンセル」は別物として区別する。

| 呼称 | 商品 | 支払い |
|---|---|---|
| キャンセル | 作っていない | 返金する |
| 未受け取り | 作った | 返金しない。売上は立ったまま |

## 3. データ構成

ER 図は省略する。エンティティ間の繋がりは 1 本も変わらない。新しいエンティティを作らず、既存エンティティに列も足さないため、既存の参照関係（`Order → Shop`、`ShopMenuStock → MenuItem` など）はそのままである。

変わるのは `Order.Status` が取りうる値の数だけ。

## 4. モデル定義

### 4.1 `Order.Status`

値を 1 つ追加する。`Order` の `case class` は変更しない。

```scala
object Order:

  /** 注文の状態 */
  enum Status(val code: Int) extends EnumStatus[Int]:
    case IS_ACCEPTED  extends Status(code = 0) // 受付
    case IS_COOKING   extends Status(code = 1) // 調理中
    case IS_READY     extends Status(code = 2) // 受取準備完了
    case IS_DELIVERED extends Status(code = 3) // 受渡し完了
    case IS_CANCELED  extends Status(code = 4) // キャンセル
    case IS_UNCLAIMED extends Status(code = 5) // 未受け取り（今回追加）
```

型では守れない決めごと。

- `code = 5` を新しく振る。既存の 0〜4 は変えない。DB には `code` の数値が保存されているため、番号を振り直すと過去のデータの意味が変わる。
- 値の並びは名前順ではなく遷移の順序にそろえる。終端状態（キャンセル・未受け取り）を末尾に置く。

### 4.2 `ShopMenuStock`

変更しない。売り切れにする操作は、既存の `ShopMenuStock.Status`（提供可 / 売り切れ）を書き換えるだけ。

## 5. 状態遷移

| 遷移元 | 遷移先 | きっかけ |
|---|---|---|
| （なし） | 受付 | 会員が注文を確定し、支払う |
| 受付 | 調理中 | スタッフが調理を開始する |
| 受付 | キャンセル | 会員がキャンセルする |
| 調理中 | 受取準備完了 | スタッフが「できあがり」を押す |
| 受取準備完了 | 受渡し完了 | 会員に商品を渡す |
| 受取準備完了 | **未受け取り** | 閉店時、スタッフが一括処理する（今回追加） |

型では守れない決めごと。

- 未受け取りに入れるのは受取準備完了からだけ。商品ができている注文のみが対象。
- 状態は飛ばせない。受付から直接受取準備完了にはできない。
- 一度進めた状態は前に戻せない。押し間違えは運用でカバーする。
- 終端は 3 つ（受渡し完了 / キャンセル / 未受け取り）。ここから先へは進まない。
- 調理中からキャンセルはできない。既存ルール（調理開始後は会員がキャンセルできない）のまま。

未受け取りは 3 つ目の終わり方として追加される。既存の遷移を書き換えるのではなく、受取準備完了からの分岐を 1 本増やすだけ。

## 6. 受け取り時間順に並べる

モデルに何も持たせない。`Order` はすでに受け取り時間を属性として持っている。並び替えは、その店舗の注文を受け取り時間の昇順で取得するだけ。

混雑の自動判定はしない。スタッフが必要に応じて並び替える。

## 7. 売り切れにする操作

既存の `ShopMenuStock.Status` を「提供可 → 売り切れ」に書き換えるだけ。

型では守れない決めごと。

- 売り切れは店舗ごと。他店舗の同じ商品には影響しない（`ShopMenuStock` が店舗 × 商品であることで成立する）。
- すでに確定した注文には影響しない。調理は続行する。
- 提供可に戻す操作もスタッフが行う。自動では戻らない。

## 8. エンティティ一覧

### 追加するもの

なし。

### 既存で足りるもの

| エンティティ | 今回の関わり | 変更 |
|---|---|---|
| `Order` | 状態を進める対象。受け取り時間で並べ替える | `Status` に値を 1 つ追加 |
| `ShopMenuStock` | 売り切れにする対象 | なし（状態を書き換えるだけ） |
| `Shop` | どの店舗の注文かを絞り込むのに使う | なし |
| `MenuItem` | 売り切れにする商品 | なし |
| `User` | 注文した会員。一覧に表示する | なし |
| `Payment` | 支払い済みの注文だけが対象になる | なし |

### 既存から動かすもの

なし。列も 1 つも足さない。

## 9. 置き場所

新しいコンテキストは作らない。変更は既存の 2 つに収まる。

- `Order.Status` への値追加 → `sales`
- `ShopMenuStock` の状態を変える操作 → `shop`

| 日常的に書き換える人 | 何を書き換えるか | 更新の頻度 | 見る画面 |
|---|---|---|---|
| 店舗スタッフ | `Order.Status` の状態 | 注文が入るたび（毎日・大量） | 店舗タブレットの注文管理画面 |
| 店舗スタッフ | `ShopMenuStock` の状態 | 材料が切れたとき（不定期） | 店舗タブレットの注文管理画面 |

02_BURGER_DOMAIN のコンテキスト表で、`sales` の管理者はすでに「会員と店舗スタッフ」、`shop` の管理者は「本部／店長」と定義されている。今回の要求で新しいアクターは登場していない。

画面が 2 つのコンテキストをまたぐのは正常であり、分割の理由にならない。「調理管理」は画面の名前であって、データの持ち主ではない。持ち主は `Order` が `sales`、`ShopMenuStock` が `shop` のまま変わらない。

店舗スタッフはモデルに現れない。「誰がその操作をしたか」を記録しないため、識別する必要がない。`User`（会員）が必要なのは `Order.userId` として記録されるからで、記録しないものは操作する人であってもモデルに現れない。

`common` については該当なし。今回 `common` に置く候補となる新しいデータが無い。

# 付録A 今回やらないこと

- スタッフのログイン・アカウント管理。
- 操作権限の区別（店長のみ、アルバイトは不可、といった制御）。
- シフト管理・勤怠。
- 「誰がその操作をしたか」の記録。
- 混雑の自動判定。
- 状態の差し戻し（押し間違えたときに前の状態へ戻す）。
- 調理を開始しないまま閉店を迎えた注文の扱い。「お客さんが来なかった」注文とは別のケースなので対象外とする。
- 未受け取り発生時の会員への通知・返金処理。
- 売り切れの自動復帰（翌日リセットなど）。
- 材料・在庫数の管理。

# 付録B 判断の記録

## 論点1：「未受け取り」を新しい状態にするか、キャンセルで代用するか

判断：新しい状態を追加する。キャンセルでは代用しない。

`Order.Status` にはすでにキャンセルがある。「渡さずに終わった注文」という点では同じなので代用もできる。しかし会計上の扱いが逆になる。キャンセルは商品を作っておらず返金するが、未受け取りは商品を作っており返金しない。

代用すると、売上の集計で返金した注文と混ざる。また「作ったのに渡せなかった件数」が数えられなくなり、廃棄ロスの把握もできない。

代償：状態が 6 つに増える。ただし遷移は受取準備完了から 1 本だけなので、判定の分岐はほとんど増えない。

## 論点2：`code` の番号をどう振るか

判断：`code = 5` を新しく振る。既存の 0〜4 は変えない。

遷移の順序で並べるなら、未受け取りは受渡し完了（3）の隣が読みやすい。しかし番号を挿入すると既存のキャンセル（4）が 5 にずれる。

DB には `code` の数値が保存されている。番号を振り直すと、すでに保存された「4」の意味がキャンセルから未受け取りに変わり、過去のデータが壊れる。

番号は追加順、並びは遷移順とする。定義の並び順と `code` の順序が一致しなくても構わない。

## 論点3：受け取り時間の近い順に並べるために、何か持たせるか

判断：何も持たせない。`Order` がすでに受け取り時間を持っている。

要求文の「混んでいるときは、受け取り時間の近いものから作りたい」は並び替えの要求であり、優先度やソート順を保存する要求ではない。`priority` のような列を持つと受け取り時間との二重管理になり、受け取り時間が変わったら優先度も直す必要が出る。比べれば分かるものは保存しない。

混雑の自動判定もしない。「混んでいるとき」はスタッフが並び替えを使う場面の説明であり、システムが混雑を検知する要求ではない。

判断が変わる条件：「大口注文を優先する」「VIP 会員を優先する」など、受け取り時間以外の要素で順序を決めるなら優先度を持つ必要が出る。

## 論点4：新しいコンテキストを作るか

判断：作らない。

「調理管理」という新しい機能なので `kitchen` のようなコンテキストも考えられる。触る人が会員からスタッフに変わるため、判断軸（誰が日常的に触るか）からすると分ける余地はある。

しかし `sales` の管理者はすでに「会員と店舗スタッフ」、`shop` の管理者は「本部／店長」と定義されており、新しいアクターが登場していない。そして新規エンティティが 0 件なので、コンテキストを作っても中身が無く、配線（パッケージ・`Module`・`RepositoryFacade`・`app-api`）が 1 セット増えるだけになる。

画面が複数のコンテキストをまたぐのは正常であり、分割の理由にならない。

## 論点5：店舗スタッフをエンティティにするか

判断：しない。モデルに現れない。

操作する人ではあるが、「誰がその操作をしたか」を記録しないと決めた。記録しないものはモデルに現れない。会員が必要なのは `Order.userId` として注文に紐づくからで、スタッフはどこにも紐づかない。

判断が変わる条件：操作ログ（誰が売り切れにしたか）やシフト連携が要求されたら、スタッフを識別するエンティティが必要になる。そのときは `shop` に `ShopStaff` として置く。店長が管理し `Shop` にぶら下がるため、`common` には置けない。

## 論点6：状態の差し戻しを認めるか

判断：認めない。一度進めた状態は前に戻せない。

実務では押し間違いが起きるため、調理中から受付に戻したくなる場面はある。しかし戻せるようにすると遷移が双方向になり組み合わせが増える。「受渡し完了から調理中に戻せるのか」「キャンセルから復活できるのか」まで決める必要が出る。

判断が変わる条件：押し間違いが頻発して運用でカバーできないなら、特定の 1 本だけ（例：受取準備完了 → 調理中）を戻せるようにする。全遷移を双方向にはしない。
