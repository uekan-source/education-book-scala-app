# 店舗スタッフ向けの調理管理 — 詳細要件定義

対象：店舗タブレットでの調理管理 ／ 前提：[要件定義](./p2_01_REQUIREMENTS.md)で合意済み

## 1. 概要

店舗のタブレットで、その店舗に入った注文を一覧し、状態を進めていけるようにする。受け取りに来なかった注文を「未受け取り」として片付けられるようにし、材料が切れた商品をその場で売り切れにできるようにする。あわせて、材料切れで作れなくなった注文を店舗都合のキャンセルとして扱えるようにする。

新しいエンティティは作らない。変更は既存の `Order` に対する 2 点だけ。

- `Order.Status` に値を 3 つ追加する（未受け取り、会員キャンセル、店舗キャンセル）
- `Order` に備考欄の列を 2 つ追加する（会員向け・店舗向け）

## 2. 用語

全体の用語集への追加を申請する。

| 呼称 | 何を指すか | 言い換えない |
|---|---|---|
| 未受け取り | 受取準備完了のまま閉店を迎え、会員が受け取りに来なかった注文 | キャンセル、破棄、放置、無効 |
| 会員キャンセル | 会員の都合で取り消された注文 | キャンセル（どちらか分からない） |
| 店舗キャンセル | 材料切れなど店舗の都合で取り消された注文 | キャンセル、欠品、中止 |

要求文と既存の呼称が食い違っていたため、既存側にそろえる。

| 業務で使われている言葉 | 統一後の呼称 |
|---|---|
| できあがり | **受取準備完了** |
| 調理中ボタンを押す | **調理を開始する** |

タブレットのボタンのラベルは「できあがり」でよい。仕様書・コード・会話では「受取準備完了」に統一する。

「渡さずに終わった注文」は 3 種類あり、原因と会計上の扱いが違う。

| 呼称 | 商品 | 支払い | 誰の都合 |
|---|---|---|---|
| 会員キャンセル | 作っていない | 返金する | 会員 |
| 店舗キャンセル | 作っていない | 返金する | 店舗 |
| 未受け取り | 作った | 返金しない。売上は立ったまま | 会員 |

「キャンセルにする」と言われたら、必ずどれか聞き返す。とくにキャンセルを 1 つにまとめてはいけない。店舗都合のキャンセル率は改善指標になるため、会員都合と混ぜると測れなくなる。

## 3. データ構成

ER 図は省略する。エンティティ間の繋がりは 1 本も変わらない。新しいエンティティを作らず、他のエンティティへの参照も 1 本も増やさないため、既存の参照関係（`Order → Shop`、`ShopMenuStock → MenuItem` など）はそのままである。

変わるのは `Order` の中身だけ。`Status` の値が 3 つ増え、備考欄の列が 2 つ増える。

## 4. モデル定義

### 4.1 `Order.Status`

値を 3 つ追加する。

```scala
object Order:

  /** 注文の状態 */
  enum Status(val code: Int) extends EnumStatus[Int]:
    case IS_ACCEPTED         extends Status(code =  100) // 受付
    case IS_COOKING          extends Status(code =  200) // 調理中
    case IS_READY            extends Status(code =  300) // 受取準備完了
    case IS_DELIVERED        extends Status(code =  400) // 受渡し完了
    case IS_CANCELED_BY_USER extends Status(code =   -1) // 会員によるキャンセル
    case IS_CANCELED_BY_SHOP extends Status(code =   -2) // 店舗によるキャンセル
    case IS_UNCLAIMED        extends Status(code =   -3) // 未受け取り
```

`code` の符号が意味を持つ。正は受け渡しまで正常に進む流れ、負は商品が渡らずに終わったことを表す。`code > 0` で「正常に完了したか」を判定できる。

正の値は 100 刻みにする。「調理中」と「受取準備完了」の間に状態が増えても `250` で挿入でき、番号を振り直さずに済む。

0 は使わない。0 は「何も設定されていない」を意味してしまい、未初期化の値と区別できなくなる。

型では守れない決めごと。

- 値の並びは名前順ではなく遷移の順序にそろえる。負の終端状態を末尾に置く。
- `IS_UNCLAIMED` は負の値だが売上は立つ。符号が表しているのは「商品が渡ったか」であって「売上が立ったか」ではない。
- DB に保存済みのデータがある場合、番号の振り直しは過去データを壊す。今回は `Order` が未実装の段階なので振り直せるが、運用に乗った後は番号を変えずに追加するしかない。

### 4.2 `Order` の備考欄

列を 2 つ追加する。

```scala
case class Order(
  // ... 既存のフィールド
  noteForUser: Option[String],  // 会員に見せる備考。キャンセル・未受け取りの理由など
  noteForShop: Option[String],  // 店舗内部のメモ。会員には見せない
  // ...
) extends EntityModel[Id]
```

どちらも `Option` で、通常の注文では空になる。負の状態にするときに理由を書く。

`reason` ではなく `note` にする。判定には使わない自由記述であることを名前で示すためであり、`reason` にすると「理由コード」と読まれて集計に使えると誤解される。

会員向けと店舗向けを分ける。会員には「材料が不足したため」と伝え、店舗内部には「バンズ発注ミス」と残す、といった書き分けができる。

型では守れない決めごと。

- 判定には使わない。状態の遷移や集計に使わず、表示と記録のためだけに持つ。
- `noteForShop` は会員に見せない。API のレスポンスに含めない。
- 負の状態にするときに書くことを想定しているが、必須にはしない。理由を書かずにキャンセルすることもできる。

### 4.3 `ShopMenuStock`

変更しない。売り切れにする操作は、既存の `ShopMenuStock.Status`（提供可 / 売り切れ）を書き換えるだけ。

## 5. 状態遷移

| 遷移元 | 遷移先 | きっかけ | code |
|---|---|---|---|
| （なし） | 受付 | 会員が注文を確定し、支払う | 100 |
| 受付 | 調理中 | スタッフが調理を開始する | 200 |
| 調理中 | 受取準備完了 | スタッフが「できあがり」を押す | 300 |
| 受取準備完了 | 受渡し完了 | 会員に商品を渡す | 400 |
| 受付 | 会員キャンセル | 会員がキャンセルする | -1 |
| 受付 / 調理中 | **店舗キャンセル** | 材料切れなどでスタッフが取り消す | -2 |
| 受取準備完了 | **未受け取り** | 閉店時、スタッフが一括処理する | -3 |

正の状態は 1 本道、負の状態は分岐である。`受付 → 調理中 → 受取準備完了 → 受渡し完了` が唯一の正常な流れで、そこから外れる 3 通りが負の値になっている。

型では守れない決めごと。

- 未受け取りに入れるのは受取準備完了からだけ。商品ができている注文のみが対象。
- 店舗キャンセルは受付と調理中の両方から入れる。調理中に材料が足りないと気づくこともある。
- 会員キャンセルは受付からだけ。調理開始後は会員がキャンセルできない（既存ルール）。
- 状態は飛ばせない。受付から直接受取準備完了にはできない。
- 一度進めた状態は前に戻せない。押し間違えは運用でカバーする。
- 終端は 4 つ（受渡し完了 / 会員キャンセル / 店舗キャンセル / 未受け取り）。ここから先へは進まない。
- 負の状態にするときは、備考欄に理由を書ける（必須ではない）。

## 6. 受け取り時間順に並べる

モデルに何も持たせない。`Order` はすでに受け取り時間を属性として持っている。並び替えは、その店舗の注文を受け取り時間の昇順で取得するだけ。

混雑の自動判定はしない。スタッフが必要に応じて並び替える。

## 7. 売り切れにする操作

既存の `ShopMenuStock.Status` を「提供可 → 売り切れ」に書き換えるだけ。

型では守れない決めごと。

- 売り切れは店舗ごと。他店舗の同じ商品には影響しない（`ShopMenuStock` が店舗 × 商品であることで成立する）。
- すでに確定した注文には自動で影響しない。作れる注文は調理を続行する。
- 作れなくなった注文は、スタッフが個別に店舗キャンセルにする。
- 提供可に戻す操作もスタッフが行う。自動では戻らない。

## 9. 置き場所

新しいコンテキストは作らない。変更は既存の 2 つに収まる。

- `Order.Status` への値追加と備考欄の列追加 → `sales`
- `ShopMenuStock` の状態を変える操作 → `shop`

| 日常的に書き換える人 | 何を書き換えるか | 更新の頻度 | 見る画面 |
|---|---|---|---|
| 店舗スタッフ | `Order.Status` の状態と備考欄 | 注文が入るたび（毎日・大量） | 店舗タブレットの注文管理画面 |
| 店舗スタッフ | `ShopMenuStock` の状態 | 材料が切れたとき（不定期） | 店舗タブレットの注文管理画面 |

02_BURGER_DOMAIN のコンテキスト表で、`sales` の管理者はすでに「会員と店舗スタッフ」、`shop` の管理者は「本部／店長」と定義されている。今回の要求で新しいアクターは登場していない。

画面が 2 つのコンテキストをまたぐのは正常であり、分割の理由にならない。「調理管理」は画面の名前であって、データの持ち主ではない。持ち主は `Order` が `sales`、`ShopMenuStock` が `shop` のまま変わらない。

店舗スタッフはモデルに現れない。「誰がその操作をしたか」を記録しないため、識別する必要がない。`User`（会員）が必要なのは `Order.userId` として記録されるからで、記録しないものは操作する人であってもモデルに現れない。

`common` については該当なし。今回 `common` に置く候補となる新しいデータが無い。

# 付録A 今回やらないこと

- スタッフのログイン・アカウント管理。タブレットは店舗に設置され、開いた人が誰でも操作できる前提とする。
- 操作権限の区別（店長のみ、アルバイトは不可、といった制御）。
- シフト管理・勤怠。
- 「誰がその操作をしたか」の記録。
- 混雑の自動判定。
- 状態の差し戻し（押し間違えたときに前の状態へ戻す）。
- 調理を開始しないまま閉店を迎えた注文の扱い。「お客さんが来なかった」注文とは別のケースなので対象外とする。
- 未受け取り発生時の会員への通知。
- 会員キャンセル・店舗キャンセル時の返金処理そのもの。
- 売り切れになった商品を含む注文の自動キャンセル。スタッフが個別に判断する。
- 売り切れの自動復帰（翌日リセットなど）。
- 材料・在庫数の管理。
- 備考欄の定型文（テンプレート）の管理。スタッフが毎回手で書く。

# 付録B 判断の記録

## 論点1：「未受け取り」を新しい状態にするか、キャンセルで代用するか

判断：新しい状態を追加する。キャンセルでは代用しない。

「渡さずに終わった注文」という点ではキャンセルと同じなので、キャンセルで済ませることもできる。しかし会計上の扱いが逆になる。キャンセルは商品を作っておらず返金するが、未受け取りは商品を作っており返金しない。

代用すると、売上の集計で返金した注文と混ざる。また「作ったのに渡せなかった件数」が数えられなくなり、廃棄ロスの把握もできない。

代償：状態が増える。ただし遷移は受取準備完了から 1 本だけなので、判定の分岐はほとんど増えない。

## 論点2：キャンセルを 1 つにまとめるか、2 つに分けるか

判断：`IS_CANCELED_BY_USER` と `IS_CANCELED_BY_SHOP` に分ける。

初回の設計では `IS_CANCELED` の 1 つだった。しかしキャンセルには 2 種類ある。会員が気を変えた場合と、材料切れなど店舗の都合による場合である。

1 つにまとめると「店舗の都合で取り消した率」が測れない。これは改善すべき指標なので、会員都合と混ぜてはいけない。会員都合のキャンセルは減らせないが、店舗都合は発注や仕込みの改善で減らせる。

代償：状態が 1 つ増える。ただし遷移元が違う（会員キャンセルは受付からだけ、店舗キャンセルは受付と調理中から）ので、判定の分岐は自然に分かれる。

判断が変わる条件：本部の都合によるキャンセル（店舗の一時閉鎖など）が出たら `IS_CANCELED_BY_HQ` を足す。`BY_` を接頭辞にしたので拡張できる。

## 論点3：備考欄を会員向けと店舗向けに分けるか

判断：分ける。`noteForUser` と `noteForShop` の 2 つを持つ。

キャンセルや未受け取りの理由を記録する必要がある。しかし会員に見せる文面と、店舗内部のメモは別物である。会員には「材料が不足したため、ご注文をキャンセルさせていただきました」と伝え、店舗内部には「バンズの発注ミス。前日確認漏れ」と残す。

1 つの列にまとめると、内部のメモを会員に見せてしまうか、会員向けの丁寧な文面しか残せないかのどちらかになる。

`reason` ではなく `note` にした理由は、判定に使わない自由記述であることを名前で示すため。`reason` にすると「理由コード」と読まれ、集計に使えると誤解される。

代償：列が 2 つ増える。「新しいエンティティは作らない」という当初の見込みは変わらないが、「既存に列を足さない」ではなくなった。

## 論点4：`code` の番号をどう振るか

判断：正の状態は 100 刻み、負の状態は −1 から連番。0 は使わない。

符号に意味を持たせる。正は受け渡しまで正常に進む流れ、負は商品が渡らずに終わったことを表す。`code > 0` で「正常に完了したか」を判定できる。

100 刻みにする理由は、「調理中」と「受取準備完了」の間に状態が増えても `250` で挿入できるため。連番だと、間に入れたい状態が出た瞬間に全部を振り直すか、順序と番号がずれるかの二択になる。

0 を使わない理由は、0 が「何も設定されていない」を意味してしまうため。未初期化の値と区別できなくなるので、区分値には割り当てない。

`IS_UNCLAIMED` を負にした理由は、商品を渡していないため。売上は立つが、符号が表しているのは「商品が渡ったか」であって「売上が立ったか」ではない。

DB に保存済みのデータがある場合、番号の振り直しは過去データを壊す。今回は `Order` がまだ実装されていない段階なので振り直せるが、運用に乗った後は番号を変えずに追加するしかない。

## 論点5：受け取り時間の近い順に並べるために、何か持たせるか

判断：何も持たせない。`Order` がすでに受け取り時間を持っている。

要求文の「混んでいるときは、受け取り時間の近いものから作りたい」は並び替えの要求であり、優先度やソート順を保存する要求ではない。`priority` のような列を持つと受け取り時間との二重管理になり、受け取り時間が変わったら優先度も直す必要が出る。比べれば分かるものは保存しない。

混雑の自動判定もしない。「混んでいるとき」はスタッフが並び替えを使う場面の説明であり、システムが混雑を検知する要求ではない。

判断が変わる条件：「大口注文を優先する」「VIP 会員を優先する」など、受け取り時間以外の要素で順序を決めるなら優先度を持つ必要が出る。

## 論点6：新しいコンテキストを作るか

判断：作らない。

「調理管理」という新しい機能なので `kitchen` のようなコンテキストも考えられる。触る人が会員からスタッフに変わるため、判断軸（誰が日常的に触るか）からすると分ける余地はある。

しかし `sales` の管理者はすでに「会員と店舗スタッフ」、`shop` の管理者は「本部／店長」と定義されており、新しいアクターが登場していない。そして新規エンティティが 0 件なので、コンテキストを作っても中身が無く、配線（パッケージ・`Module`・`RepositoryFacade`・`app-api`）が 1 セット増えるだけになる。

画面が複数のコンテキストをまたぐのは正常であり、分割の理由にならない。

## 論点7：店舗スタッフをエンティティにするか

判断：しない。モデルに現れない。

操作する人ではあるが、「誰がその操作をしたか」を記録しないと決めた。記録しないものはモデルに現れない。会員が必要なのは `Order.userId` として注文に紐づくからで、スタッフはどこにも紐づかない。

判断が変わる条件：操作ログ（誰が売り切れにしたか、誰が店舗キャンセルにしたか）やシフト連携が要求されたら、スタッフを識別するエンティティが必要になる。そのときは `shop` に `ShopStaff` として置く。店長が管理し `Shop` にぶら下がるため、`common` には置けない。

## 論点8：状態の差し戻しを認めるか

判断：認めない。一度進めた状態は前に戻せない。

実務では押し間違いが起きるため、調理中から受付に戻したくなる場面はある。しかし戻せるようにすると遷移が双方向になり組み合わせが増える。「受渡し完了から調理中に戻せるのか」「キャンセルから復活できるのか」まで決める必要が出る。

判断が変わる条件：押し間違いが頻発して運用でカバーできないなら、特定の 1 本だけ（例：受取準備完了 → 調理中）を戻せるようにする。全遷移を双方向にはしない。
