# 問題2：店舗スタッフ向けの調理管理 — 詳細要件定義

対象：店舗スタッフの調理管理 ／ 前提：[要件定義](./p2_01_REQUIREMENTS.md)で合意済み

---

# 本体：確定したエンティティ要件

## 1. 概要

店舗のタブレットで、その店舗に入った注文を一覧し、状態を進めていけるようにする。
受け取りに来なかった注文を「未受け取り」として片付けられるようにする。
材料が切れた商品を、その場で売り切れにできるようにする。

**新しいエンティティは作らない。** 変更は既存の `Order` に対する 2 点だけ。

- `Order.Status` に値を **3 つ**追加する（未受け取り、および 2 種類のキャンセル）
- `Order` に備考欄の列を **2 つ**追加する（会員向け・店舗向け）

## 2. 用語

### 追加を申請する呼称

| 呼称（これで統一する） | 何を指すか | 言い換えない |
|---|---|---|
| 未受け取り | 受取準備完了のまま閉店を迎え、会員が受け取りに来なかった注文 | 「キャンセル」「破棄」「放置」「無効」 |
| 会員キャンセル | 会員の都合で取り消された注文 | 「キャンセル」（どちらか分からない） |
| 店舗キャンセル | 材料切れなど店舗の都合で取り消された注文 | 「キャンセル」「欠品」「中止」 |

### 呼び方の衝突を統一する

要求文と既存の呼称が食い違っていたので、既存側にそろえる。

| 業務で使われている言葉 | 統一後の呼称 | なぜ |
|---|---|---|
| できあがり | **受取準備完了** | 同じ状態を指す。既存の `Order.Status` の呼称に合わせる |
| 調理中ボタンを押す | **調理を開始する** | 「ボタン」は画面の話。業務の操作名にそろえる |

タブレットのボタンのラベルは「できあがり」でよい。**仕様書・コード・会話では「受取準備完了」に統一する。**

### 「未受け取り」と「キャンセル」は別物

| 呼称 | 何が起きたか | 商品 | 支払い | 誰の都合 |
|---|---|---|---|---|
| 会員キャンセル | 調理開始前に会員が取り消した | 作っていない | 返金する | 会員 |
| 店舗キャンセル | 材料切れなどで店舗が取り消した | 作っていない | 返金する | **店舗** |
| **未受け取り** | 調理済みだが、会員が取りに来なかった | **作った** | **返金しない。売上は立ったまま** | 会員 |

3 つとも「渡さずに終わった注文」だが、原因と会計上の扱いが違う。
**「キャンセルにする」と言われたら、必ずどれか聞き返す。**

> ⚠️ **キャンセルを 1 つにまとめない。** 「店舗の都合で取り消した率」は改善指標になるので、
> 会員都合と混ぜると測れなくなる。

## 3. データ構成

**ER 図は省略する。** 今回、エンティティ間の繋がりは 1 本も変わらない。

- 新しいエンティティを作らない
- 既存の参照関係（`Order → Shop` / `ShopMenuStock → MenuItem` など）はそのまま
- **他のエンティティへの参照を 1 本も増やさない**

変わるのは `Order` の中身だけ（`Status` の値が 3 つ増え、備考欄の列が 2 つ増える）。
参照関係が変わらないので、ER 図を描いても前と同じ図になる。

## 4. モデル定義

### 4.1 `Order.Status` — 値を 3 つに増やす

```scala
object Order:

  /** 注文の状態 */
  enum Status(val code: Int) extends EnumStatus[Int]:
    case IS_ACCEPTED         extends Status(code =  100) // 受付
    case IS_COOKING          extends Status(code =  200) // 調理中
    case IS_READY            extends Status(code =  300) // 受取準備完了
    case IS_DELIVERED        extends Status(code =  400) // 受渡し完了
    case IS_CANCELED_BY_USER extends Status(code =   -1) // 会員によるキャンセル  ← 今回追加
    case IS_CANCELED_BY_SHOP extends Status(code =   -2) // 店舗によるキャンセル  ← 今回追加
    case IS_UNCLAIMED        extends Status(code =   -3) // 未受け取り            ← 今回追加
```

**ここで `code` が語っていること**

- **符号が意味を持つ。** 正 ＝ 受け渡しまで正常に進む流れ、負 ＝ 商品が渡らずに終わった。
  `code > 0` で「正常に完了したか」を判定できる
- **正の値は 100 刻み。** 「調理中」と「受取準備完了」の間に状態が増えても `250` で挿入できる。
  番号を振り直さずに済む
- **0 は使わない。** 0 は「何も設定されていない」を意味してしまうため、区分値には割り当てない
- **キャンセルが 2 つに分かれている。** 会員都合と店舗都合で、会計上・分析上の扱いが違う（→ [論点2](#論点2キャンセルを-1-つにまとめるか-2-つに分けるか)）

型では守れない決めごと。

- 値の並びは名前順ではなく**遷移の順序**にそろえる。負の終端状態を末尾に置く
- **`IS_UNCLAIMED` は負の値だが、売上は立つ。** 商品を作っているため返金しない。
  符号は「商品が渡ったか」を表しており、「売上が立ったか」ではない

### 4.2 `Order` — 備考欄の列を 2 つ追加する

```scala
case class Order(
  // ... 既存のフィールド
  noteForUser: Option[String],  // 会員に見せる備考。キャンセル・未受け取りの理由など
  noteForShop: Option[String],  // 店舗内部のメモ。会員には見せない
  // ...
) extends EntityModel[Id]
```

**ここで型が語っていること**

- **どちらも `Option`。** 通常の注文では空。負の状態になったときに理由を書く
- **`note` であって `reason` ではない。** 判定には使わない自由記述であることを名前で示す。
  `reason` にすると「理由コード」と読まれかねない
- **会員向けと店舗向けを分ける。** 会員には「材料が不足したため」と伝え、
  店舗内部には「バンズ発注ミス」と残す、といった書き分けができる

型では守れない決めごと。

- **判定には使わない。** 状態の遷移や集計に使わず、表示と記録のためだけに持つ
- **`noteForShop` は会員に見せない。** API のレスポンスに含めない
- 状態が負のときに書くことを想定しているが、**必須にはしない。**
  理由を書かずにキャンセルすることもできる

### 4.3 `ShopMenuStock` — 変更しない

売り切れにする操作は、既存の `ShopMenuStock.Status`（提供可 / 売り切れ）を書き換えるだけ。
**モデルの形は変わらない。**

## 5. 状態遷移

どの状態からどの状態へ行けるか。

| 遷移元 | 遷移先 | きっかけ | code |
|---|---|---|---|
| （なし） | 受付 | 会員が注文を確定し、支払う | 100 |
| 受付 | 調理中 | スタッフが調理を開始する | 200 |
| 調理中 | 受取準備完了 | スタッフが「できあがり」を押す | 300 |
| 受取準備完了 | 受渡し完了 | 会員に商品を渡す | 400 |
| 受付 | **会員キャンセル** | 会員がキャンセルする | -1 |
| **受付 / 調理中** | **店舗キャンセル** | **材料切れなどでスタッフが取り消す（今回追加）** | -2 |
| **受取準備完了** | **未受け取り** | **閉店時、スタッフが一括処理する（今回追加）** | -3 |

型では守れない決めごと。

- **`未受け取り` に入れるのは `受取準備完了` からだけ。** 商品ができている注文だけが対象
- **`店舗キャンセル` は `受付` と `調理中` の両方から入れる。** 調理中に材料が足りないと気づくこともある
- **`会員キャンセル` は `受付` からだけ。** 調理開始後は会員がキャンセルできない（既存ルール）
- **飛ばせない。** `受付` から直接 `受取準備完了` にはできない
- **戻せない。** 一度進めた状態は前に戻らない。押し間違えは運用でカバーする
- **終端は 4 つ**（`受渡し完了` / `会員キャンセル` / `店舗キャンセル` / `未受け取り`）。ここから先へは進まない
- **負の状態に入れるときは、`noteForUser` / `noteForShop` に理由を書ける**（必須ではない）

> **正の状態は 1 本道、負の状態は分岐。** `受付 → 調理中 → 受取準備完了 → 受渡し完了` が
> 唯一の正常な流れで、そこから外れる 3 通りが負の値になっている。

> ⚠️ **`店舗キャンセル` は今回追加した状態だが、要求文には明示されていない。**
> 「急に材料が切れたら、その場で商品を売り切れにしたい」という要求から、
> **すでに受け付けた注文をどうするか**が問題になるため追加している。要件定義で合意を取る。

## 6. 受け取り時間順に並べる

**モデルに何も持たせない。** `Order` はすでに受け取り時間を属性として持っている。

- 並び替えは、その店舗の注文を受け取り時間の昇順で取得するだけ
- **混雑の自動判定はしない**（①で確認済み）。スタッフが必要に応じて並び替える

## 7. 売り切れにする操作

**既存の `ShopMenuStock` の状態を書き換えるだけ。**

| 変えるもの | 遷移 |
|---|---|
| `ShopMenuStock.Status` | 提供可 → 売り切れ |

型では守れない決めごと。

- **売り切れは店舗ごと。** 他店舗の同じ商品には影響しない（`ShopMenuStock` が店舗 × 商品だから成立する）
- **すでに確定した注文には影響しない。** 調理は続行する
- 提供可に戻す操作もスタッフが行う。自動では戻らない

## 9. 置き場所（コンテキスト）

**判断：新しいコンテキストは作らない。**

変更は既存の 2 つに収まる。

- `Order.Status` への値追加 → **`sales`**
- `ShopMenuStock` の状態を変える操作 → **`shop`**

| 日常的に書き換える人 | 何を書き換えるか | 更新の頻度 | 見る画面 |
|---|---|---|---|
| 店舗スタッフ | `Order.Status` の状態 | 注文が入るたび（毎日・大量） | 店舗タブレットの注文管理画面 |
| 店舗スタッフ | `ShopMenuStock` の状態 | 材料が切れたとき（不定期） | 店舗タブレットの注文管理画面 |

**理由：**

1. **触る人が既存の想定内。** 02_BURGER_DOMAIN のコンテキスト表で、`sales` の管理者は
   「会員と**店舗スタッフ**」、`shop` の管理者は「本部／**店長**」とすでに定義されている。
   今回の要求で新しいアクターは登場していない
2. **画面が 2 つのコンテキストをまたぐのは正常。** カリキュラムも「画面を 1 つ描くのに
   複数のリポジトリを呼んで自分で組み立てる」ことを前提にしている。
   **画面の単位とコンテキストの単位は一致しない**
3. **「調理管理」は画面の名前であって、データの持ち主ではない。**
   持ち主は `Order` が `sales`、`ShopMenuStock` が `shop` のまま変わらない

### 店舗スタッフを `User` と別のものとして扱うか

**扱わない。モデルに現れない。**

①で「誰がその操作をしたか」を記録しないと決めたため、スタッフを識別する必要がない。
タブレットは店舗に設置され、開いた人が誰でも操作できる。

**`User`（会員）が必要なのは、`Order.userId` として記録されるから。**
記録しないものは、操作する人であってもモデルに現れない。

### `common` に置けないか

**該当なし。** 今回 `common` に置く候補となる新しいデータが無い。
`Order.Status` の値は `Order` の一部であり、単独で `common` に置ける形をしていない。

# 付録

## 付録A：今回やらないこと

- スタッフのログイン・アカウント管理
- 操作権限の区別（店長のみ、アルバイトは不可、といった制御）
- シフト管理・勤怠
- 「誰がその操作をしたか」の記録
- 混雑の自動判定
- 状態の差し戻し（押し間違えたときに前の状態へ戻す）
- 調理を開始しないまま閉店を迎えた注文（受付のまま残った注文）の扱い。
  「お客さんが来なかった」注文とは別のケースなので今回は対象外
- 未受け取り発生時の会員への通知・返金処理
- 売り切れの自動復帰（翌日リセットなど）
- 材料・在庫数の管理
- 備考欄の定型文（テンプレート）の管理。スタッフが毎回手で書く
- 会員キャンセル・店舗キャンセル時の返金処理そのもの

## 付録B：判断の記録

### 論点1：「未受け取り」を新しい状態にするか、キャンセルで代用するか

**判断：新しい状態を追加する。キャンセルでは代用しない。**

「渡さずに終わった注文」という点ではキャンセルと同じなので、キャンセルで済ませることもできる。

しかし**会計上の扱いが逆**になる。

| | 商品 | 支払い |
|---|---|---|
| キャンセル | 作っていない | 返金する |
| 未受け取り | **作った** | **返金しない。売上は立ったまま** |

キャンセルで代用すると、**売上の集計で「返金した注文」と混ざる。**
また「作ったのに渡せなかった件数」が数えられなくなり、廃棄ロスの把握もできない。

**代償：** 状態が増える。ただし遷移は `受取準備完了 → 未受け取り` の 1 本だけなので、
判定の分岐はほとんど増えない。

### 論点2：キャンセルを 1 つにまとめるか、2 つに分けるか

**判断：`IS_CANCELED_BY_USER` と `IS_CANCELED_BY_SHOP` に分ける。**

初回の設計では `IS_CANCELED` の 1 つだった。しかしキャンセルには 2 種類ある。

| | 原因 | 誰の都合 |
|---|---|---|
| 会員キャンセル | 会員が気を変えた | 会員 |
| 店舗キャンセル | 材料切れ・在庫切れ | **店舗** |

**1 つにまとめると「店舗の都合で取り消した率」が測れない。** これは改善すべき指標なので、
会員都合と混ぜてはいけない。会員都合のキャンセルは減らせないが、店舗都合は発注や仕込みの
改善で減らせる。

**代償：** 状態が 1 つ増える。ただし遷移元が違う（会員キャンセルは `受付` からだけ、
店舗キャンセルは `受付` と `調理中` から）ので、判定の分岐は自然に分かれる。

**判断が変わる条件：** 本部の都合によるキャンセル（店舗の一時閉鎖など）が出たら
`IS_CANCELED_BY_HQ` を足す。`BY_` を接頭辞にしたので拡張できる。

### 論点3：備考欄を会員向けと店舗向けに分けるか

**判断：分ける。`noteForUser` と `noteForShop` の 2 つを持つ。**

キャンセルや未受け取りの理由を記録する必要がある。しかし**会員に見せる文面と、
店舗内部のメモは別物**である。

| | 例 |
|---|---|
| `noteForUser` | 「材料が不足したため、ご注文をキャンセルさせていただきました」 |
| `noteForShop` | 「バンズの発注ミス。前日確認漏れ」 |

1 つの列にまとめると、内部のメモを会員に見せてしまうか、会員向けの丁寧な文面しか
残せないかのどちらかになる。

**`reason` ではなく `note` にした理由：** 判定に使わない自由記述であることを名前で示すため。
`reason` にすると「理由コード」と読まれ、集計に使えると誤解される。

**代償：** 列が 2 つ増える。「新しいエンティティは作らない」という当初の見込みは変わらないが、
「既存に列を足さない」ではなくなった。

### 論点4：`code` の番号をどう振るか

**判断：正の状態は 100 刻み、負の状態は −1 から連番。0 は使わない。**

```
100 受付 / 200 調理中 / 300 受取準備完了 / 400 受渡し完了
 -1 会員キャンセル / -2 店舗キャンセル / -3 未受け取り
```

**符号に意味を持たせる。** 正 ＝ 受け渡しまで正常に進む流れ、負 ＝ 商品が渡らずに終わった。
`code > 0` で「正常に完了したか」を判定できる。

**100 刻みにする理由：** 「調理中」と「受取準備完了」の間に状態が増えても `250` で挿入できる。
連番だと、間に入れたい状態が出た瞬間に**全部を振り直すか、順序と番号がずれるかの二択**になる。

**0 を使わない理由：** 0 は「何も設定されていない」を意味してしまう。
未初期化の値と区別できなくなるため、区分値には割り当てない。

> ⚠️ **DB に保存済みのデータがある場合、番号の振り直しは過去データを壊す。**
> 今回は `Order` がまだ実装されていない段階なので振り直せる。
> **運用に乗った後は、番号を変えずに追加するしかない。**

**`IS_UNCLAIMED` を負にした理由：** 商品を渡していないため。売上は立つが、
符号が表しているのは「商品が渡ったか」であって「売上が立ったか」ではない。

### 論点5：受け取り時間の近い順に並べるために、何か持たせるか

**判断：何も持たせない。`Order` がすでに受け取り時間を持っている。**

要求文は「混んでいるときは、受け取り時間の近いものから作りたい」だが、これは
**並び替えの要求**であって、優先度やソート順を保存する要求ではない。

`priority` のような列を持つと、受け取り時間との二重管理になる。
受け取り時間が変わったら優先度も直す必要が出る。**比べれば分かるものは保存しない。**

**混雑の自動判定もしない**（①で確認済み）。「混んでいるとき」はスタッフが並び替えを使う
場面の説明であり、システムが混雑を検知する要求ではない。

**判断が変わる条件：** 「大口注文を優先する」「VIP 会員を優先する」など、
受け取り時間以外の要素で順序を決めるなら、優先度を持つ必要が出る。

### 論点6：新しいコンテキストを作るか

**判断：作らない。**

「調理管理」という新しい機能なので、`kitchen` のようなコンテキストも考えられる。
触る人が会員からスタッフに変わるため、⑤の判断軸（誰が日常的に触るか）からすると
分ける余地はある。

しかし 02_BURGER_DOMAIN のコンテキスト表で、**`sales` の管理者はすでに「会員と店舗スタッフ」**、
`shop` の管理者は「本部／店長」と定義されている。**新しいアクターが登場していない。**

そして新規エンティティが 0 件なので、コンテキストを作っても中身が無い。
配線（パッケージ・`Module`・`RepositoryFacade`・`app-api`）が 1 セット増えるだけになる。

**「調理管理」は画面の名前であって、データの持ち主ではない。**
画面が複数のコンテキストをまたぐのは正常。

### 論点7：店舗スタッフをエンティティにするか

**判断：しない。モデルに現れない。**

操作する人ではあるが、①で「誰がその操作をしたか」を記録しないと決めた。
記録しないものは、モデルに現れない。

**`User`（会員）との違いは、記録されるかどうか。** 会員は `Order.userId` として
注文に紐づくから必要になる。スタッフはどこにも紐づかない。

**判断が変わる条件：** 操作ログ（誰が売り切れにしたか）やシフト連携が要求されたら、
スタッフを識別するエンティティが必要になる。そのときは `shop` に `ShopStaff` として置く
（店長が管理し、`Shop` にぶら下がるため `common` には置けない）。

### 論点8：状態の差し戻しを認めるか

**判断：認めない。一度進めた状態は前に戻せない。**

実務では押し間違いが起きるので、「調理中 → 受付」に戻したくなる場面はある。

しかし戻せるようにすると、遷移が双方向になり組み合わせが増える。
「受渡し完了から調理中に戻せるのか」「キャンセルから復活できるのか」まで決める必要が出る。

①で「戻せなくてよい。押し間違えは運用でカバーする」と確認したため、**一方向のみ**とする。

**判断が変わる条件：** 押し間違いが頻発して運用でカバーできないなら、
**特定の 1 本だけ**（例：受取準備完了 → 調理中）を戻せるようにする。
全遷移を双方向にはしない。
