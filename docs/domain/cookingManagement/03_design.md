# 問題2：店舗スタッフ向けの調理管理 — 詳細要件定義

対象：店舗スタッフの調理管理 ／ 前提：[要件定義](./p2_01_REQUIREMENTS.md)で合意済み

---

# 本体：確定したエンティティ要件

## 1. 概要

店舗のタブレットで、その店舗に入った注文を一覧し、状態を進めていけるようにする。
受け取りに来なかった注文を「未受け取り」として片付けられるようにする。
材料が切れた商品を、その場で売り切れにできるようにする。

**新しいエンティティは作らない。** 変更は `Order.Status` に値を 1 つ追加するだけ。

## 2. 用語

### 追加を申請する呼称

| 呼称（これで統一する） | 何を指すか | 言い換えない |
|---|---|---|
| 未受け取り | 受取準備完了のまま閉店を迎え、会員が受け取りに来なかった注文 | 「キャンセル」「破棄」「放置」「無効」 |

### 呼び方の衝突を統一する

要求文と既存の呼称が食い違っていたので、既存側にそろえる。

| 業務で使われている言葉 | 統一後の呼称 | なぜ |
|---|---|---|
| できあがり | **受取準備完了** | 同じ状態を指す。既存の `Order.Status` の呼称に合わせる |
| 調理中ボタンを押す | **調理を開始する** | 「ボタン」は画面の話。業務の操作名にそろえる |

タブレットのボタンのラベルは「できあがり」でよい。**仕様書・コード・会話では「受取準備完了」に統一する。**

### 「未受け取り」と「キャンセル」は別物

| 呼称 | 何が起きたか | 商品 | 支払い |
|---|---|---|---|
| キャンセル | 調理開始前に注文が取り消された | 作っていない | 返金する |
| **未受け取り** | 調理済みだが、会員が取りに来なかった | **作った** | **返金しない。売上は立ったまま** |

どちらも「渡さずに終わった注文」だが、原因と会計上の扱いが違う。
**「来なかった注文をキャンセルにする」と言われたら、必ずどちらか聞き返す。**

## 3. データ構成

**ER 図は省略する。** 今回、エンティティ間の繋がりは 1 本も変わらない。

- 新しいエンティティを作らない
- 既存エンティティに列を足さない
- 既存の参照関係（`Order → Shop` / `ShopMenuStock → MenuItem` など）はそのまま

変わるのは `Order.Status` が取りうる**値の数**だけ。

## 4. モデル定義

### 4.1 `Order.Status` — 値を 1 つ追加する

```scala
object Order:

  /** 注文の状態 */
  enum Status(val code: Short) extends EnumStatus[Short]:
    case IS_ACCEPTED  extends Status(code = 0) // 受付
    case IS_COOKING   extends Status(code = 1) // 調理中
    case IS_READY     extends Status(code = 2) // 受取準備完了
    case IS_DELIVERED extends Status(code = 3) // 受渡し完了
    case IS_CANCELED  extends Status(code = 4) // キャンセル
    case IS_UNCLAIMED extends Status(code = 5) // 未受け取り  ← 今回追加
```

**`Order` の `case class` は変更しない。** `status` フィールドはすでに存在する。

型では守れない決めごと。

- **`code = 5` を新しく振る。既存の 0〜4 は変えない。**
  DB には `code` の数値が保存されているので、番号を振り直すと過去のデータの意味が変わる
- 値の並びは名前順ではなく**遷移の順序**にそろえる。終端状態（キャンセル・未受け取り）を末尾に置く

### 4.2 `ShopMenuStock` — 変更しない

売り切れにする操作は、既存の `ShopMenuStock.Status`（提供可 / 売り切れ）を書き換えるだけ。
**モデルの形は変わらない。**

## 5. 状態遷移

どの状態からどの状態へ行けるか。

| 遷移元 | 遷移先 | きっかけ |
|---|---|---|
| （なし） | 受付 | 会員が注文を確定し、支払う |
| 受付 | 調理中 | スタッフが調理を開始する |
| 受付 | キャンセル | 会員がキャンセルする |
| 調理中 | 受取準備完了 | スタッフが「できあがり」を押す |
| 受取準備完了 | 受渡し完了 | 会員に商品を渡す |
| **受取準備完了** | **未受け取り** | **閉店時、スタッフが一括処理する（今回追加）** |

型では守れない決めごと。

- **`未受け取り` に入れるのは `受取準備完了` からだけ。** 商品ができている注文だけが対象
- **飛ばせない。** `受付` から直接 `受取準備完了` にはできない
- **戻せない。** 一度進めた状態は前に戻らない。押し間違えは運用でカバーする
- **終端は 3 つ**（`受渡し完了` / `キャンセル` / `未受け取り`）。ここから先へは進まない
- **`調理中` からキャンセルできない。** 既存ルール（調理開始後は会員がキャンセルできない）のまま

> **`未受け取り` は 3 つ目の終わり方として追加された。**
> 既存の遷移を書き換えるのではなく、`受取準備完了` からの分岐を 1 本増やしただけ。

## 6. 受け取り時間順に並べる

**モデルに何も持たせない。** `Order` はすでに受け取り時間を属性として持っている。

- 並び替えは、その店舗の注文を受け取り時間の昇順で取得するだけ
- **混雑の自動判定はしない**（①で確認済み）。スタッフが必要に応じて並び替える

## 7. 売り切れにする操作

**既存の `ShopMenuStock` の状態を書き換えるだけ。**

| 変えるもの | 遷移 |
|---|---|
| `ShopMenuStock.Status` | 提供可 → 売り切れ |

型では守れない決めごと。

- **売り切れは店舗ごと。** 他店舗の同じ商品には影響しない（`ShopMenuStock` が店舗 × 商品だから成立する）
- **すでに確定した注文には影響しない。** 調理は続行する
- 提供可に戻す操作もスタッフが行う。自動では戻らない

## 8. エンティティ一覧

### 追加するもの

**ありません。**

### 既存で足りるもの

| エンティティ | 今回の関わり | 変更 |
|---|---|---|
| `Order` | 状態を進める対象。受け取り時間で並べ替える | **`Status` に値を 1 つ追加** |
| `ShopMenuStock` | 売り切れにする対象 | なし（状態を書き換えるだけ） |
| `Shop` | どの店舗の注文かを絞り込むのに使う | なし |
| `MenuItem` | 売り切れにする商品 | なし |
| `User` | 注文した会員。一覧に表示する | なし |
| `Payment` | 支払い済みの注文だけが対象になる | なし |

### 既存から動かすもの

**ありません。**

### 新しく持つ参照

**ありません。** 列を 1 つも足しません。

## 9. 置き場所（コンテキスト）

**判断：新しいコンテキストは作らない。**

変更は既存の 2 つに収まる。

- `Order.Status` への値追加 → **`sales`**
- `ShopMenuStock` の状態を変える操作 → **`shop`**

| 日常的に書き換える人 | 何を書き換えるか | 更新の頻度 | 見る画面 |
|---|---|---|---|
| 店舗スタッフ | `Order.Status` の状態 | 注文が入るたび（毎日・大量） | 店舗タブレットの注文管理画面 |
| 店舗スタッフ | `ShopMenuStock` の状態 | 材料が切れたとき（不定期） | 店舗タブレットの注文管理画面 |

**理由：**

1. **触る人が既存の想定内。** 02_BURGER_DOMAIN のコンテキスト表で、`sales` の管理者は
   「会員と**店舗スタッフ**」、`shop` の管理者は「本部／**店長**」とすでに定義されている。
   今回の要求で新しいアクターは登場していない
2. **画面が 2 つのコンテキストをまたぐのは正常。** カリキュラムも「画面を 1 つ描くのに
   複数のリポジトリを呼んで自分で組み立てる」ことを前提にしている。
   **画面の単位とコンテキストの単位は一致しない**
3. **「調理管理」は画面の名前であって、データの持ち主ではない。**
   持ち主は `Order` が `sales`、`ShopMenuStock` が `shop` のまま変わらない

### 店舗スタッフを `User` と別のものとして扱うか

**扱わない。モデルに現れない。**

①で「誰がその操作をしたか」を記録しないと決めたため、スタッフを識別する必要がない。
タブレットは店舗に設置され、開いた人が誰でも操作できる。

**`User`（会員）が必要なのは、`Order.userId` として記録されるから。**
記録しないものは、操作する人であってもモデルに現れない。

### `common` に置けないか

**該当なし。** 今回 `common` に置く候補となる新しいデータが無い。
`Order.Status` の値は `Order` の一部であり、単独で `common` に置ける形をしていない。

# 付録

## 付録A：今回やらないこと

- スタッフのログイン・アカウント管理
- 操作権限の区別（店長のみ、アルバイトは不可、といった制御）
- シフト管理・勤怠
- 「誰がその操作をしたか」の記録
- 混雑の自動判定
- 状態の差し戻し（押し間違えたときに前の状態へ戻す）
- 調理を開始しないまま閉店を迎えた注文（受付のまま残った注文）の扱い。
  「お客さんが来なかった」注文とは別のケースなので今回は対象外
- 未受け取り発生時の会員への通知・返金処理
- 売り切れの自動復帰（翌日リセットなど）
- 材料・在庫数の管理

## 付録B：判断の記録

### 論点1：「未受け取り」を新しい状態にするか、キャンセルで代用するか

**判断：新しい状態を追加する。キャンセルでは代用しない。**

`Order.Status` にはすでに `キャンセル` がある。「渡さずに終わった注文」という点では同じなので、
キャンセルで済ませることもできる。

しかし**会計上の扱いが逆**になる。

| | 商品 | 支払い |
|---|---|---|
| キャンセル | 作っていない | 返金する |
| 未受け取り | **作った** | **返金しない。売上は立ったまま** |

キャンセルで代用すると、**売上の集計で「返金した注文」と混ざる。**
また「作ったのに渡せなかった件数」が数えられなくなり、廃棄ロスの把握もできない。

**代償：** 状態が 6 つに増える。ただし遷移は `受取準備完了 → 未受け取り` の 1 本だけなので、
判定の分岐はほとんど増えない。

### 論点2：`code` の番号をどう振るか

**判断：`code = 5` を新しく振る。既存の 0〜4 は変えない。**

遷移の順序で並べるなら、`未受け取り` は `受渡し完了`（3）の隣が読みやすい。
しかし番号を挿入すると、既存の `キャンセル`（4）が 5 にずれる。

**DB には `code` の数値が保存されている。** 番号を振り直すと、すでに保存された
「4」の意味がキャンセルから未受け取りに変わり、**過去のデータが壊れる。**

**番号は追加順、並びは遷移順**とする。定義の並び順と `code` の順序が一致しなくても構わない。

### 論点3：受け取り時間の近い順に並べるために、何か持たせるか

**判断：何も持たせない。`Order` がすでに受け取り時間を持っている。**

要求文は「混んでいるときは、受け取り時間の近いものから作りたい」だが、これは
**並び替えの要求**であって、優先度やソート順を保存する要求ではない。

`priority` のような列を持つと、受け取り時間との二重管理になる。
受け取り時間が変わったら優先度も直す必要が出る。**比べれば分かるものは保存しない。**

**混雑の自動判定もしない**（①で確認済み）。「混んでいるとき」はスタッフが並び替えを使う
場面の説明であり、システムが混雑を検知する要求ではない。

**判断が変わる条件：** 「大口注文を優先する」「VIP 会員を優先する」など、
受け取り時間以外の要素で順序を決めるなら、優先度を持つ必要が出る。

### 論点4：新しいコンテキストを作るか

**判断：作らない。**

「調理管理」という新しい機能なので、`kitchen` のようなコンテキストも考えられる。
触る人が会員からスタッフに変わるため、⑤の判断軸（誰が日常的に触るか）からすると
分ける余地はある。

しかし 02_BURGER_DOMAIN のコンテキスト表で、**`sales` の管理者はすでに「会員と店舗スタッフ」**、
`shop` の管理者は「本部／店長」と定義されている。**新しいアクターが登場していない。**

そして新規エンティティが 0 件なので、コンテキストを作っても中身が無い。
配線（パッケージ・`Module`・`RepositoryFacade`・`app-api`）が 1 セット増えるだけになる。

**「調理管理」は画面の名前であって、データの持ち主ではない。**
画面が複数のコンテキストをまたぐのは正常。

### 論点5：店舗スタッフをエンティティにするか

**判断：しない。モデルに現れない。**

操作する人ではあるが、①で「誰がその操作をしたか」を記録しないと決めた。
記録しないものは、モデルに現れない。

**`User`（会員）との違いは、記録されるかどうか。** 会員は `Order.userId` として
注文に紐づくから必要になる。スタッフはどこにも紐づかない。

**判断が変わる条件：** 操作ログ（誰が売り切れにしたか）やシフト連携が要求されたら、
スタッフを識別するエンティティが必要になる。そのときは `shop` に `ShopStaff` として置く
（店長が管理し、`Shop` にぶら下がるため `common` には置けない）。

### 論点6：状態の差し戻しを認めるか

**判断：認めない。一度進めた状態は前に戻せない。**

実務では押し間違いが起きるので、「調理中 → 受付」に戻したくなる場面はある。

しかし戻せるようにすると、遷移が双方向になり組み合わせが増える。
「受渡し完了から調理中に戻せるのか」「キャンセルから復活できるのか」まで決める必要が出る。

①で「戻せなくてよい。押し間違えは運用でカバーする」と確認したため、**一方向のみ**とする。

**判断が変わる条件：** 押し間違いが頻発して運用でカバーできないなら、
**特定の 1 本だけ**（例：受取準備完了 → 調理中）を戻せるようにする。
全遷移を双方向にはしない。
