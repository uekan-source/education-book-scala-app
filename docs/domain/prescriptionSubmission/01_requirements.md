# 処方箋送信アプリ — 要件定義

`Q1`〜`Q42` 回答済み。**5 軸の再走査で出た候補 12 件はすべて処理済み。** 残り：軽微 3 件、調剤明細の連携タイミング（本文 28 の `⚠`）、用語の整理（キャンセル / 削除 / 廃棄）。

## 受け取った要求

> 処方箋をスマホで送れるアプリを作りたい。
>
> うちは全国に 180 店舗、調剤薬局をやっている。いま患者さんは処方箋を持って来店してから調剤を始めるので、20 分も 30 分も待たせてしまう。先に処方箋の写真を送ってもらって調剤を始めておければ、来店したらすぐ渡せる。
>
> 受け取る店舗と、だいたい何時ごろ来るかを選んでもらいたい。
>
> 写真が読めなかったり、うちで扱っていない薬だったりすることがある。そのときは薬局から患者さんに返せるようにしたい。
>
> できあがったら通知を出して、来店してもらう。来ない人もいる。
>
> それと、薬の値段は国が決めていて毎年変わるので、そこは本部で管理したい。

## 前提

要求文に無いが、聞かないと設計が決まらないもの。**空欄にしない。**

- **想定規模**：180 店舗全店で一斉導入（パイロットなし）。3〜5 年で 200 店舗。送信 4,000〜10,000 件/日 → 将来 1 店舗 100 件/日。アカウント 30 万 → 50 万（`Q16`）
- **保存期間**：調剤明細・会計の記録・送信の履歴は最低 5 年。**画像だけ終端から 90 日で自動削除**（`Q25` `Q27`）
- **アクセス境界**：スタッフは所属店舗の送信のみ。患者はアカウント単位（登録した患者全員分）。本部は金額・件数のみで画像は見えない（`Q19` `Q26`）
- **既存資産**：レセコンが店舗ごとに導入済み。ただし **180 店舗でばらばら**（`Q4` `Q6`）
- **法規制・監査**：厚生局の個別指導で記録の提示を求められる。日付・操作者つきで出せる形にする（`Q27`）

### 制度の前提（発注者ではなく制度で決まっていること）

| 前提 | 状態 |
|---|---|
| 処方箋の有効期限は、交付日を含めて 4 日 | 確定 |
| 営業時間外の受付には加算が付く（時間外加算） | 確定。**何をもって受付とするかは制度が決めない**ので `Q3` `Q5` の回答と組で意味を持つ |

> ⚠️ 「原本も 4 日以内に持参する必要がある」は、当初この欄に書いていたが `Q1` で発注者に確認した。
> **確信のないことを前提の欄に置くと、誰も疑わずに実装される。**

| `Q24` | 交付日を入力項目として持つか | **持たない。** 全送信で打ち直す手間の割に使い道が期限判定だけで、それは目視で足りる。打ち間違いは誤判定の元 |
| `Q25` | 画像の保存期間は | **終端（受け渡し完了・廃棄・取り消し）から 90 日で自動削除。** 画像には氏名と薬名（＝病歴）が写る。**削除は自動＝これだけバッチの仕事**（`Q17` はあの 3 つの話で、バッチがいないとは言っていない） |
| `Q26` | アクセス境界の詳細は | スタッフ＝所属店舗のみ／患者＝アカウント単位（登録患者全員分）／本部＝金額・件数のみ、**画像は見えない** |
| `Q27` | 法規制・監査で消してはいけないものは | 調剤明細・会計・送信の履歴は**最低 5 年**。個別指導で**日付・操作者つき**で出せる形に。例外は画像の 90 日だけ |
| `Q28` | 取りに来なかった薬を廃棄するのは現実的でない。棚に戻すのが普通では（受講者の薬事知識からの指摘） | **指摘のとおり。仕様を修正。**「取り置き終了」を記録する（誰の分・いつ・どのスタッフが）。**戻せる薬は棚へ、戻せないもの（一包化・開封済み）は廃棄**──この内訳はシステムに持たない（現場の作業）。ただし**送信の記録は消さない**。未来店は正式受付が無く調剤報酬を請求できない＝丸ごとロスなので、店舗横断でロスを把握する材料になる |
| `Q29` | 差し戻し理由の「扱えない薬」と「在庫を確保できない」は統合できないか | **統合しない。** 恒常（その店では扱う予定がない→即差し戻して近隣店舗を案内）と一時（発注すれば入る→電話で意向を聞く `Q7`）で**対応が違う**。本部の手当ても違う（品揃えの見直し vs 発注運用の見直し） |
| `Q30` | 差し戻し理由は揮発的で、保存する必要が無いのでは | **保存する（`Q20` のまま）。**「3 回も撮り直しさせられた」というクレームで経緯を出せないと店を守れない。個別指導で受付から交付まで日が空いた説明に要る。本部が理由別の傾向を見てアプリの撮影ガイドや注意喚起を直す。送信を 5 年残すのに理由だけ消すと歯抜けになる |
| `Q31` | 差し戻されたまま期限が過ぎた送信は、スタッフが「期限切れで終了」を記録して閉じる、でよいか | **そのとおり。「期限切れ終了」という終わり方を認める。** 閉店時の処理（未来店と同じタイミング）で、差し戻し中リストから期限切れを閉じる。判定は目視（交付日は画像の中。`Q24` と整合）。**患者への通知はしない**（通知は 3 つのまま）。90 日削除の起点もこれで揃う |
| `Q32` | 未来店にした後、期限内に原本を持って来たら、未来店を取り消して進めてよいか | **渡す。未来店から正式受付に進めてよい。** 薬は棚にあり、期限内なら渡さない理由が無い。**未来店になった事実の記録は消さない。** 期限を過ぎていたら `Q15` のとおり渡さない。→ **逆流は差し戻しだけ、が崩れた**（2 本目） |
| `Q33` | 5 枚のうち 1 枚だけ不備のとき、送信全体を差し戻すのでよいか | **送信単位で差し戻す。ただしどの画像が問題かを示して返す。** 患者はその画像だけ差し替えて再送。読める分だけ先に調剤は進めない（受け取りも会計も 1 回。`Q9` と整合）。急ぐ患者には電話で相談（記録は持たない）。→ **差し戻しの記録が対象画像への参照を持つ** |
| `Q34` | 「調剤を始めた」がシステムから見えない。締め切りをスタッフの「調剤開始」記録に置くか、仮受付で締め切るか | **スタッフが「調剤開始」を記録する。仮受付では締め切らない。**`Q11`（仮受付の前後を問わず始める前まで取り消せる）と矛盾するため。現場は朝まとめて仮受付して順に取り掛かるので、その時差の間の取り消しを断る理由が無い（断ればロスが増えるだけ）。これで「調剤中」が観測可能になる |
| `Q35` | 調剤開始前に患者が電話・店頭で「やめたい」と言ってきたら、スタッフが取り消しを代行できるか | **設ける。調剤開始前に限る。** 高齢の患者は電話してくる。**代行したことが分かる形で記録する**（`Q19` と整合）。終わり方は患者自身の取り消しと同じ。別の状態は作らない。調剤開始後の申し出は `Q11` のとおり未来店処理 |
| `Q36` | スタッフの誤操作（誤って差し戻した等）はどう戻すか | **戻せる必要はある。記録は消さず、訂正の操作を重ねる。** 要求は 2 点：①誤操作から復帰できる ②元の操作の痕跡が消えない（誰がいつ何を戻したか）。個別指導で説明できる形なら実現方法は設計に任せる |
| `Q37` | 営業時間変更・臨時休業で、入っている受け取り希望が営業時間外になったら | **薬局から電話して調整する。システムは何もしない**（勝手に差し戻したり時間を動かしたりしない。`Q7` と同じ思想）。変更は事前に決まるので店舗が対象を確認して電話。災害などの当日休業も電話 |
| `Q38` | 退会・患者削除はできるか。記録（5 年保存）とどう折り合うか | **できる。ただし進行中の送信がある間はできない。**「削除」は**新規に使えなくなるだけ**で、過去の送信・調剤・会計の記録は氏名ごと 5 年残る。個人情報の削除請求にも、調剤の記録は法令・指導対応のため消せないと答える |
| `Q39` | 事前登録した薬価は、誤りに気づいたら直せるか | **適用開始前は自由に訂正・削除できる**（まだどの会計にも使われていない）。**開始後は上書きも削除もせず、訂正の登録を重ねる**（いつ・誰が直したか残る。`Q36` と同じ思想）。過去の検算のやり直しは本部の判断 |
| `Q40` | 同じ処方箋の二重送信はどう扱うか | **システムでは検知しない。スタッフが気づいた側を差し戻す。理由に 6 つ目「重複」を足す**（疑義で兼ねない──意味が違うし集計が濁る。追加はまだ作っていない今なら無料）。明らかな重複は電話不要で差し戻してよい |
| `Q41` | 正式受付の後に渡せないと分かったら | **正式受付の記録はそのまま。取り消す操作は作らない。** 原本が正で、食い違いは原本に合わせて調剤し直す。その日に渡せなければ**取り置き（14 日）に乗せて後日渡す**──4 日期限は原本受領で満たしている。会計は渡す日。来なければ取り置き終了 |
| `Q42` | 同じ 30 分枠の件数上限は | **設けない。** 受け渡しは 1〜2 分（調剤済み）でレジ待ちと同じ。枠を締めると患者が店頭に流れてアプリの意味が無くなる。**判断が変わる条件：昼どきの偏りで窓口が回らなくなったら、枠を実体として持つことを検討** |

### 役割の分担（`Q6` `Q13` で確定）

| | どこで |
|---|---|
| 処方内容の入力・調剤・会計の計算 | **レセコン**（既存。店舗ごとに導入済み。**このシステムの外**） |
| 状態の操作（仮受付 / 調剤完了 / 正式受付 / 受け渡し / 差し戻し / 取り消し / 未来店 / 廃棄） | **このシステム。** スタッフまたは患者が操作し、**誰がやったかを記録する**（`Q19`） |
| 調剤明細のデータ | **このシステムが持つ。** レセコンから連携で入る |
| 処方箋画像の自動削除（90 日） | **このシステムのバッチ**（`Q25`。バッチの仕事はこれだけ） |

## 業務フロー

**ブロックはアクターごと**（時間帯などでは増やさない）。番号は通しで、**時系列は主語の中だけ**（実際には交互に起きる）。**所持物 0 のアクター（レセコン・バッチ）にも行を書く**──書かないと連携と削除が設計から消える。

差し戻し・再送・取り消し・未来店・取り置き終了を本文に入れている。**送信の一生を本文だけで読めるようにする**という判断（付録B 論点1 になる予定）。

```
[患者]
 1. 病院で処方箋を受け取る
 2. アプリを起動して、処方箋の写真を撮る
 3. 受け取る店舗と、受け取り時間を選ぶ
 4. 送信する
 5. 差し戻された場合は、撮り直して同じ送信に対して再送する
 6. 調剤が始まる前なら、アプリから送信を取り消す
 7. 完了通知を受け取る
 8. 指定した店舗・時間帯に来店して、処方箋の原本を渡す
 9. 窓口で支払う

[薬局]
10. 送られてきた処方箋の画像を受信する
11. 画像と内容を確認する
12. 不備があれば、理由を選んで差し戻す
13. 不備がなければ、仮受付にする
14. 「調剤開始」を記録し、レセコンで処方内容を入力して調剤する（Q34：ここがアプリ取り消しの締め切り）
15. 在庫を確保できない場合は、患者に電話して意向を聞き、差し戻す
16. 調剤が終わったら、患者に完了通知を送る
17. 原本を受け取って、正式受付にする
18. レセコンで会計して、窓口で代金を受け取る
19. 調剤した薬を渡す
20. 閉店時に、受け取り時間を過ぎても来なかった送信を未来店にする（Q17：自動判定しない）
21. 閉店時に、差し戻されたまま期限が過ぎた送信を「期限切れ終了」にする（Q31：判定は目視）
22. 未来店の後でも、期限内に原本を持って来たら正式受付に進める（Q32）
23. 原本が期限切れだった場合、または調剤開始後に電話で取り消しを申し出られた場合は、
      渡さずに未来店として処理する
24. 未来店の薬を 14 日間取り置く。過ぎたら取り置きを終了して記録する
      （戻せる薬は棚に戻し、戻せないもの（一包化など）は廃棄する）

[本部]
25. 医薬品と薬価を登録する。薬価の改定は、適用開始日を指定して事前に登録する
26. 店舗と営業時間を登録・変更する
27. 店舗をまたいで、金額と件数を検算・分析する

[レセコン]（外部・所持物 0）
28. 調剤明細を、このシステムに連携で送る      ⚠ 未確認：いつ送られてくるのか（質問リスト行き）

[バッチ]
29. 終端（受け渡し完了・取り置き終了・取り消し・期限切れ終了）から 90 日を過ぎた処方箋画像を削除する
```

## 例外・ルール

**送信の終わり方の分岐は本文へ、時間軸に乗らない制約はここへ。**

- 処方箋の期限は、交付日を含めて 4 日
