# 研修の進め方

要件定義からモデル設計までを、機能ごとに 3 ファイルで進める。

## 全体の流れ

**直線ではない。3 ファイルを行き来しながら、何周も回して完成度を上げる。**

```
                    ┌──────── 顧客とのミーティング ────────┐
                    ↓                                    │
        受け取った要求 / 追加のヒアリング                    │
                    ↓                                    │
   ┌────────────────────────────────────────┐            │
   │  01_requirements.md   前提・質問・業務フロー │            │
   │  02_analysis.md       名詞と動詞・ふるい分け │  ←─ 並行 ─→ │
   │  03_design.md         用語・モデル・決めごと │            │
   └────────────────────────────────────────┘            │
                    ↓  01 と 03 を提出                     │
                    └────────────────────────────────────┘
                    ↓  周を重ねて固まったら
        edu/*/model/*.scala     メソッド・検証・WithNoId を足す
```

**要件定義とモデル設計は並行してやる。** モデルに落とそうとして初めて決まっていないことが見つかるので、片方を完成させてからもう片方に進むことはできない。

| 周 | やること |
|---|---|
| 1 周目 | **粗くていいので端まで通す。** 穴を見つけるのが目的 |
| 2 周目以降 | 見つけた穴を質問し、回答を反映して精度を上げる |
| ミーティングのたび | 前提が変わることがある。**変わるのは正常** |

> ⚠️ **教材やこの文書は、何周も回した後の姿を 1 回で見せている。** あの順に 1 回で出てきたわけではない。**1 周目で完成形を目指すと必ず詰まる。**

実際、`PaymentItem`（決済明細）は 3 回作り替わっている。注文明細に単価を持たせ → 揮発データだと分かって決済側に移し → 割引の参照先を商品から明細行に変えた。**モデルだけで回していたので、コストは `sbt compile` 3 回だった。**

手順の中身は[モデル設計の 5 ステップ](#モデル設計の-5-ステップ--要件定義と並行して回す)。

## この研修の中心にある考え方

**エンティティモデルがやり直しの効かない要である。**

コードは書き直せるが、データは書き直せない。正確には、構造の移行はできても、**存在しなかった情報は復元できない**。スタンプカードの設計では次の実例が出た。

- スタンプを独立したエンティティにしていたら、「このスタンプはどのカードに属すべきだったか」は最初から存在しないので、後から親子関係にしても復元できない
- 付与日時を持たずに `createdAt` で兼ねると、過去データを一括登録したときに配られた日時が失われる

処理（バッチ、手順、計算）は間違えてもコードを直せば済む。**この非対称性があるので、モデルに時間を使う。**

裏を返すと、モデルと「型では守れない決めごと」が正確に書かれていれば、その先はかなり機械的に導ける。

## 01_requirements.md — 要件定義

### 書くもの

| 節 | 内容 |
|---|---|
| 受け取った要求 | 依頼文をそのまま引用する。書き換えない |
| **前提** | **要求文に無いが、聞かないと設計が決まらないもの**（次節） |
| 確認したいこと（質問リスト） | 曖昧な点を質問と回答の対で残す |
| 業務フロー | **アクターを先に立ててから**、業務のまとまりごとに番号を振って並べる |
| 例外・ルール | フローに書けない業務ルール |

**業務フローはアクターより後。** 先にフローを書くと、書いたフローの主語しか登場しない。

02 章のフロー例は会員 1 人分だけで、**本部が主語の行が 1 行も無かった。** その結果、販売テンプレートもクーポンの配り方も概念として出てこなかった。

```
[本部]
1. 商品を登録する
2. メニュー構成を組む          ← SalesTemplate
3. 店舗に配る                  ← Shop.templateId
```

**「店舗に配る」と書けば、配られる何かが要る。** 書かなかったから拾えなかった。

本数は業務のまとまりで決まる（1 本に 2 人以上登場してよい）。チェックはこれ。

> **すべてのアクターが、どこかのフローで「主語」になっているか。**

所持物が 0 のアクターも書く。決済サービスのフローを書かないと `IS_PENDING` / `IS_FAILED` が出ないし、分析のフローを書かないと**どのデータを消してよいかが決まらない。**

### 質問の書き方

**中立に聞かない。設計案を提示して合意を取る。**

```
悪い： 有効期限はどう数えますか
良い： 有効期限は「スタンプ 1 個ごと」ではなく「貯めているカード 1 枚ごと」に
      持たせたい。1 個目のスタンプが押された日から数えて 1 年、という理解でよいか
```

こう書くと、相手は「はい／いいえ」で答えられる。判断を相手に丸投げせず、こちらが考えた上で確認する形にする。

### 質問が漏れやすいところ

スタンプカードの設計では、5 つの質問のうち 4 つが会員側（スタンプの数え方、期限、枚数）に寄っていた。**本部側の質問が「登録できるようにするか」の 1 つだけ**だったため、次が漏れた。

- いつからいつまで配るのか（配布期間）
- 登録した後に条件を変更できるのか
- 配った後に期限を切らない運用はあるか

この 3 つは設計が固まった後に指摘され、大きな手戻りになった。

**対策：** 「誰が触るか」を軸に質問を並べて、片側に偏っていないか確認する。設計の最後にやる「触る人と頻度」の表を、**質問リストを作る段階で先にやる**とよい。

これは**アクターを先に立てろ**ということで、[モデル設計の 5 ステップ](#モデル設計の-5-ステップ--要件定義と並行して回す)の ① と同じ。**質問リストを作る前に 1 周しておく。** チェックリストは `docs/reference/curriculum_06_design_patterns.md`。

### 聞くしかない前提

**要求文に 1 文字も書かれていないのに、モデルの形を決めてしまうもの。** 教材でも後から足されたのは、全部この種類だった。

| 前提 | 聞かないとどうなるか |
|---|---|
| **アクター** | 立て忘れた人の所持物は、**作り忘れるのではなく存在に気づかない** |
| **想定規模** | 3 店舗なら `SalesTemplate` は過剰設計、300 店舗なら無いと運用が破綻する |
| **保存期間** | どれが揮発でどれがストックか決まらない。**スナップショットの置き場所が決まらない** |
| **アクセス境界** | `shopId` のような**後から足せない列**が抜ける |
| 法規制・監査 | 「7 年保存」なら消せない。保存期間の線が動く |
| 既存資産 | 何が既にあるか。「既存で足りる」の判定ができない |

質問リストは 2 段構えにする。

```
## 前提（案件が変わっても同じ顔ぶれ。チェックリストで潰す）
## 個別の確認事項（要求文の曖昧さを潰す。毎回違う）
```

**上段が空欄のまま設計に入ると、誰も気づかないまま進む。** 質問すら出ないので、レビューでも見つからない。

とくに規模は、聞き方が決まっている。

| | 3 店舗の個人経営 | 300 店舗のフランチャイズ |
|---|---|---|
| メニュー構成 | 店ごとに手で組んでよい | 本部がテンプレートを作って配る仕組みが要る |
| 店舗独自の商品 | 概念が要らない | 本部の商品と型で区別する必要がある |

**要件が同じでも、規模が違えば正しいモデルが違う。** 聞くのは「いま何店舗ですか」ではなく「**どこまで大きくなる想定ですか**」。

## 02_analysis.md — 思考過程

提出しない。当時どう考えたかの記録なので、後から変更を反映しない。

| 節 | 内容 |
|---|---|
| 名詞と動詞 | 要求文から機械的に拾う |
| 動詞の仕分け | 「状態を変える（書き込む）」と「値を返す（読むだけ）」に分ける |
| 名詞のふるい分け | エンティティ / 属性 / 既存 / 対象外（計算できる・業務の外）に分ける |
| ユビキタス言語 | エンティティの日本語名と英語名 |
| 命名の評価 | 候補を軸ごとに採点する。決め手は「業務の人に通じるか」 |
| コンテキストの判断 | どこに置くか |

### ふるい分けのコツ

**業務に言葉があっても、モデルにするとは限らない。**

- 「カード」と「クーポン」は業務では呼び分けるが、同じモデルの状態違いだった
- 「あと何個か」は計算できるので保存しない
- 「本部」は操作する人だが、誰が登録したかを記録しないのでモデルに現れない

## モデル設計の 5 ステップ — 要件定義と並行して回す

`03` のモデルを作るための 5 ステップ。**`01`〜`02` を書き終えてから始めるのではなく、並行して回す。**

```
① アクター → ② 境界を引く → ③ 所持物を確認 → ④ 流して検証 → ⑤ 確定
     ↑                                          │
     └────── 穴が出たら戻る（質問リストへ） ──────────┘
```

原典は `docs/reference/curriculum_05_model_design.md`。

### 洗い出しの 5 ステップと重なっている

洗い出し（`01`〜`02` を作る手順）と、同じ作業に別の番号が振ってある。

```
洗い出し  : ①業務フロー → ②名詞と動詞 → ③ふるい → ④用語 → ⑤境界を引く
モデル設計: ①アクター                          →  ②境界を引く → ③所持物 → ④検証 → ⑤確定
                                                  ↑ 同じ作業
```

**2 組あると思わなくていい。実体はこの 5 つ。**

```
人を出す        アクター（7 問・6 類型）＋ 業務フローの主語
モノを出す      名詞と動詞・ふるい分け・用語
モノを人に配る  所持物チェック
流して確かめる  業務フローを通す。穴が出たら質問リストへ
書く            03
```

### 境界の引き方が変わった

| | どこから境界を引くか |
|---|---|
| 洗い出し ⑤ | **概念から**（変わる理由が同じものをまとめる） |
| モデル設計 ② | **人から**（アクターの利用範囲がそのまま境界） |

**アクター軸が上位。** アクターで切ると変更の理由とライフサイクルは自動的に揃うので、3 軸を別々に検討しなくてよくなる。

なお 02 章も運用ルールは「**このデータを、日常的に書き換えるのは誰か**」の 1 問だった。**基準は同じで、立てるタイミングが最後から最初に変わった。**

### 各ステップが 03 のどこになるか

| ステップ | 03 のどこ |
|---|---|
| ① アクター・② 境界 | **6. 置き場所（コンテキスト）** |
| ③ 所持物 | リード文のエンティティの表（追加する / 既存で足りる / 既存から動かす） |
| ④ 検証 | **5. エンティティをまたぐルール**。穴が出たら `01` の質問リストに戻る |
| ⑤ 確定 | 3. EntityModel |

### ① アクターは 5 分でいい。ただし飛ばさない

既存システムへの追加なら、アクターは既に立っている。確認するのは**新しく増えるかどうかだけ。**

```
返金機能を足す   → CS・サポートが登場する
承認フローを足す → 承認者が登場する
自動失効を足す   → バッチが登場する
```

**立て忘れると、その所持物は「作り忘れる」のではなく存在に気づかない。** 全員が同じ前提で見ているので、レビューでも出ない。

7 つの問いと 6 類型のチェックリストは `docs/reference/curriculum_06_design_patterns.md`。

### ④ 検証は「新機能のフロー」だけでは足りない

**その新モデルに触る既存フローを全部流す。** キャンセル・返金・退会・締め処理。

スタンプカードで実際に開いた穴がこれだった。

> 使用済みのクーポンがキャンセルで復活すると、販売終了した商品のクーポンが使える状態に戻る

キャンセルは新機能ではない。**既存のフローに新しいモデルを差し込んだから開いた。**

流すときの問いは 3 つ。

> **① 境界をまたぐのはどこか　② コピーか参照か　③ 片方が消えたら、もう片方は無事か**

### 1 機能追加のときの重み

ゼロから作るのと、既存に足すのとで、時間をかける場所が変わる。**実務ではほぼ後者。**

| ステップ | 0 から | **1 機能追加** |
|---|---|---|
| ① アクター | 全部洗い出す | 新しく増えるかだけ確認 |
| ② 境界 | 引く | 既存のどこに入るか選ぶ |
| ③ 所持物 | 全部並べる | **追加 / 既存で足りる / 既存から動かす** ← 本番 |
| ④ 検証 | 業務フロー 4 本 | **新フロー ＋ 既存フローへの影響** ← 本番 |
| ⑤ 確定 | 全モデル通し | 追加分＋関連する既存モデルを並べて |

**③ で一番多い失敗は作りすぎ。** 教材が演習の冒頭で警告している。

> この演習は **すでにあるモデルへの追加** です。**多くは既存で足ります。**

逆に、**既存モデルにフィールドを足して済ませる**のも失敗。`Product` に `shopId` を足して「店舗のものなら `Some`」とすると、全店共通のマスタに店舗固有の行が混ざる。**2 人のアクターが同じものを対等に変更するなら、それは 2 つに割れる合図。**

## 03_design.md — 設計

### 構成

```
リード文（対象・前提・追加するエンティティの表）
1. 用語 — 全体の用語集に追加する呼称
2. ER 図
3. EntityModel（エンティティごと）
4. 区分値の考え方
5. エンティティをまたぐルール（あれば。無ければ節ごと省く）
6. 置き場所（コンテキスト）— 判断 / 理由
---
付録A 今回やらないこと
付録B 判断の記録
```

### 用語の表

「何と呼ぶか」だけでなく**「何と呼ばないか」**を決める。これを書かないと次の会議で言い換えが起きる。

| 呼称 | 何を指すか | 言い換えない |
|---|---|---|
| クーポン | 本部が登録するクーポンの種類 | クーポンマスタ、テンプレート |

### EntityModel

`case class` とコンパニオンオブジェクト（Id・区分値）まで書く。**形だけを書き、メソッドや検証は書かない。**

そのうえで 3 つを添える。

1. **ここで型が語っていること** — 必須か任意かを型がどう表しているか
2. **型では守れない決めごと** — 一意制約、属性どうしの連動、運用ルール
3. **保存されるデータの例** — パターンごとに 1 行、実際に入る値で

### 付録B 判断の記録

論点ごとに「判断 / 理由 3〜6 行 / 代償 / 判断が変わる条件」。

**迷わなかったことは書かない。** 本文に結論も理由も書いてあるものは、論点にしない。論点の固有価値は**採らなかった案とその理由**にある。

「判断が変わる条件」は書いた時点では役に立たないが、後から要件が増えたときに「どこを変えればいいか」が即座に分かる。
